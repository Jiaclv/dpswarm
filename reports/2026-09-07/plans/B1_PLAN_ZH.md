## 3. 增加多少 token 和调用次数

| 参数 | 低调用额度包 | 高调用额度包 | 口径 |
|---|---:|---:|---|
| 团队普通模型调用 `max_calls` | 28 | **160** | 包含 Lead、worker 工作和 finish-only 调用 |
| 每个 worker 工作调用 `worker_calls` | 8 | **48** | 是上限，不是预先划走的专属票池 |
| 团队 CM 调用 `cm_call_allowance` | 12 | **64** | 在普通调用池之外单独计次 |
| Lead 保留参数 `lead_reserve_calls` | 2 | 2 | 保持原策略 |
| 每题求解墙钟上限 | **7,200 秒** | **7,200 秒** | 所有条件一致；API 排队计入 |
| 每容器内存上限 | 1 GiB | 1 GiB | 沿用用户已指定配置 |

token 因子为 600,000／2,400,000；调用额度因子为上表低／高两档。高档普通调用约为原来的 5.71 倍，worker 工作调用为 6 倍，CM 调用为 5.33 倍。最大普通＋CM 票数为每题 40／224 次。达到正确交付条件可以提前结束，不要求用满。

必须保留以下预算语义：

- worker 正常走完本地工作次数且尚未结束时可申请一次 finish-only；提前终止不保证获得该调用。它仍消耗团队普通调用票，不能在 160 次之外额外加算。
- `lead_reserve_calls=2` 会限制 worker 的普通工作，但原 finish-only 豁免规则保留。因此该参数不保证最后必然留给 Lead 两次调用。
- token 预算覆盖所有角色及 CM 的已知用量和待结算／未知调用预约。普通调用预约是 `ceil(messages JSON 字符数 / 3) + 32768`，不是“还有一个 token 就能继续”。CM 的输出上限保持 4096，预约 slack 保持 8192。
- API 返回实测用量可能高于事前估计；334.8M 等数字是累计准入额度，不是假定实际用量、严格账单封顶或全部输出 token。
- 预算停止时同时记录实际已知用量、未知预约、在途预约、剩余普通／CM 票数。必须区分“实际消费接近上限”和“下一次预约无法容纳”。

统一两小时是为了避免把墙钟变化混入本轮 token／调用对照。因此 D00、T00 是**同期低资源参考**，并不精确复现旧 A2 的 1,800 秒环境。与旧 A2 比较时同时披露通道、运行器和调度差别；主要因果比较在本轮内部完成。

## 6. 预注册比较与判断口径

设 `p_i(A)` 为题目 i 在条件 A 的三次通过比例。每题先计算差值，再对六题等权汇总。

| 对比 | 可识别的变化 |
|---|---|
| T10 − T00 | 低调用额度下，单独增加 token |
| T11 − T01 | 高调用额度下，单独增加 token |
| T01 − T00 | 低 token 下，放宽调用额度包 |
| T11 − T10 | 高 token 下，放宽调用额度包 |
| (T11 − T01) − (T10 − T00) | token 与调用额度包的交互；只作小样本诊断 |
| D11 − D00；T11 − T00 | 各自扩大整套资源后的效果，D/T 分开报告 |
| F-T − F-S | 同为 Flash、相同总资源上限下，增加两个 worker |
| S-FF − S-S | 固定 Sol Lead，增加两个 Flash worker |
| S-FF − F-T | 同样两个 Flash worker，只更换 Lead 模型 |
| T11 − S-S；D11 − S-S | 同样高上限下原团队相对 Sol 单体的机会成本 |
| S-FF − T11 | 两个 worker 的模型组合变化；不能细分归功于哪一个角色 |

调用因子同时改变普通票、worker 本地循环和 CM 票，必须称为“调用额度包”，不能只归因于普通调用数。相同上限也不保证相同实际算力或美元开销；团队省下／花掉多少资源要另算。

结果解释模板：

- 若只加 token 已改善，且预算停止减少、生产交付增加，支持原 token 准入约束对这些题的影响。
- 若只加调用额度改善，支持原调用机会不足；继续拆分 ordinary、worker、CM 三类实际瓶颈。
- 若只有 T11 改善，且两种单项放宽仍撞另一上限，支持共同受限的解释。
- 若预算停止减少、耗费增加但正确率不变，说明单纯放宽资源尚未转化为评分收益；检查修复范围和验证质量。
- 若仍然失败，不能据六题三次断言“预算无用”或“模型能力到顶”；必须报告是否仍触顶、是否完整交付和失败类型。

预先定义“重复出现的题级收益”描述标签：同题某对比高侧至少 2/3 成功且低侧 0/3，称为该题的重复改善信号；它不是统计显著性的替代。完整输出所有 0/3、1/3、2/3、3/3，不只展示符合标签的题。

这轮不使用旧“比 R2 多两题且时间≤1.30×”作为自动晋级规则，也不自动扩展新题或更多臂。先回答资源诊断，再分别按成本、延迟和通过率报告取舍。

## 7. 每次都采集什么

**质量与覆盖**：官方 resolved、FAIL_TO_PASS 与 PASS_TO_PASS 节点结果／缺失原因、生产补丁有无、补丁能否应用、公开自测结果。目标节点覆盖率先逐题归一化，再按题等权；同时可报 pooled 节点数，但不能让 Xarray 的多个节点充当独立题目。

**预算与时序**：每次调用的 requested/reported model、角色、通道、输入／缓存／输出／推理／total、已知／未知／在途预约、CM与普通调用分类、起止与排队时间。缓存计价不重复加 token。保留供应商原用量；各供应商未提供的字段为 null。

**阶段进展**：首次生产编辑、首次真实测试、worker 首次交付、Lead 采用、采用后复测、最终冻结的时间与累计资源。保留拒绝预约发生时的余额，以及在途 worker 结算后是否释放了余额；区分预算真正花完与异步预约暂时占满。

**团队按角色拆分**：工作／收尾票数、生产文件 delta、测试文件 delta、测试是否实际执行及原输出、blocked原因、交付／丢弃／采用／最终保留。测试命令未解析时记“未观测／待核对”，不能直接判定没有测试。

**失败多标签**：token admission、普通调用、worker 本地上限、CM上限、墙钟、无生产补丁、部分修复、回归、无有效测试、错误／空交付、采用后未复测、API／协议／环境故障。停止原因与修复失败原因分别记录，可同时存在；`budget_exhausted` 但官方通过仍计成功。

**效率**：每题／每臂实测用量、API 等价费用、真实扣费可得部分、每解成本、生成时间、端到端时间、供应商排队和评分等待。零成功时每解成本记不适用／无穷，不填零。订阅折算与普通 API 实付分栏，不混作同一种现金支出。

**保留→评分链路**：逐个解释新增或被删的生产改动是否触及最终目标路径；采用≠因果贡献。若要离线评分 worker/丢弃补丁，作为探索性候选评分单列、绑定原基线及依赖状态，并在全部生成结束后做；反事实未重放时不得称已证实 review 错误。

## 9. GLM 通道与并发：开跑前先绑定实际权益

## 10. 并行、内存和阶段调度

本次只读快照：Docker 24 CPU、内存约15.21 GiB、无运行容器；宿主可用物理内存约9 GiB。开跑前重新测量，快照不保证后续余量。

计划最多12个episode调度槽，**候选容器总数最多12，每个1 GiB、2 CPU**。单体预约1个、D预约2个、T/F-T/S-FF预约3个；先一次拿齐整队所需名额再启动，不让多个Lead各占一个容器后相互等worker名额。

因此，全是三人团队时最多4队真正同时生成；12个episode槽不等于12个三人团队同时占36个容器。这是当前主机约束，不能把Flash50的API权益当成36GiB环境容量。容器限额不是实际预占，记录cgroup峰值和OOM事件，不只看Docker瞬时工作集。

安排方式：按“题目×重复”构造18个完整十臂块；题目顺序用seed=20260906随机化；臂顺序随机底序后循环轮转，18个块中各臂在每位置出现次数最多相差1。冻结的是启动优先级；真实开始／结束时间由资源及API队列决定，全部记录。不可按中期结果让某臂跳队。

| 阶段 | 正式生成次数 | 内容 | 结束后动作 |
|---|---:|---|---|
| 启动前核验 | 0个正式episode | 无模型资格检查、预算／调度回放，最多8次独立小型通道探针 | 全部符合后进入正式生成 |
| 第一阶段 | 60 | 六题×十臂×第一次重复；首个完整十臂块也是正式数据 | 只审查运行健康和证据完整性 |
| 第二阶段 | 120 | 第二、第三次重复，每次都覆盖全矩阵 | 收束、官方评分和汇总 |

后续启动时，控制器应异步运行并自动推进已冻结的阶段；健康检查通过不需要等用户反复询问才续派。不根据成功率删臂、换题、加预算或增加重复。失败补丁和预算耗尽是结果，不是取消后续正常实验的理由。

准备与生成分时使用资源。每个已派发的候选波全部停止并确认清理后，串行执行该波官方评分，再续派；评分容器1 GiB。控制器不将评分详情写回求解输入。候选资源等待单列；拿齐名额后才启动统一7200秒求解计时。API等待仍计入求解墙钟，并单独展示。

新启动后须独立核查后台PID、日志推进、真实调用事件及容器状态，不把“进程启动命令返回成功”写成“实验正在健康运行”。关机或崩溃后依据账本恢复未开始单元；已开始但中断的生成保留原状态，不自动重跑或偷换重复编号。
