> 历史计划发布副本。计划格数不等于执行数量，实际完成范围和结果见[报告索引](../../README.md)。本文不构成新的实验启动安排。

版本：2026-09-06 / v1。状态：**已获得 C1 并发执行授权，正在实施共同前置与资格检查；正式实验状态以批次账本为准。**

本计划优先用 **GLM-5.3-Flash 承担实现者与测试者**，Lead 用 GPT Sol，CM 用 **DeepSeek-v4-flash**；需要区分模型能力时，可增加 Terra max / Luna max 对照。模型对照独立成组，不能与机制开关同时变动后把差异全归因于机制。

## 1. 要回答什么，现有数据支持到哪里

| 问题 | 现有证据 | 下一步可识别的效果 |
|---|---|---|
| CM 是否有净收益 | 压缩执行成功；但压缩自己消耗根 token，缺 CM-off | 固定模型、普通调用及 token 上限，比较整个系统开/关 CM 的质量、总资源与时间 |
| 增大 token 是否有帮助 | T00→T11 同时改变四种额度，不能分离 | 固定调用纪律，单独提高根 token 上限 |
| 向测试者倾斜资源是否有帮助 | 测试交付增多，没有同步提高官方通过 | 固定总调用额度，只重新分配实现者/测试者的调用额度 |
| 专门的测试者值不值得保留 | 交付被采纳，尚无干净角色对照 | 相同总额度下，保留测试者和把其额度交给实现者的策略价值 |
| Review 决策是否合理 | 能看到 adopt/discard，缺决策时精确反事实评分 | 对可还原状态的每次交付，离线比较采用前后；生产补丁与测试补丁分别判读 |
| Flash 是否限制交付 | 单题历史结果不足以比较模型 | 固定 Lead、测试者和机制，仅替换实现者为 Flash / Terra max / Luna max |

这里先修正两种容易扩大的表述。第一，旧核心实验只有三道诊断题，团队交付较可靠是本批观察，不等于已经证明团队的普遍因果优势。第二，T00→T11 新增 3,064,217 token 中，实现者占 **33.15%**、CM 占 **32.78%**、测试者占 **18.89%**、Lead 占 **15.17%**。测试者用量的倍数增长较大，但新增预算并非主要流向测试者。因而“测试者占比应该更大”是要检验的假设。

旧实验 T00 2/3、T11 1/3、S-S 0/3，且 Xarray 三组都交付、都未通过目标测试；其中还有单体工具协议异常。以上用于选择诊断方向，旧单次结果不填入新实验的重复格。

## 3. P0：所有新实验共同使用的工程前置

以下是启动前要完成的工作，**已获执行授权，实施与验证记录见本轮 preflight 和批次清单**。两臂必须使用相同的修复版本，不用旧错误版本作对照。

1. **真实测试结果。** 对 pytest 经 `tail`、管道或后续命令掩盖退出状态的问题，保留一次真实测试的退出码及原始输出；不能为确认退出码隐式再跑一次。离线校验覆盖“pytest 失败但 tail 成功”“真实通过”“收集错误/超时”“退出码与输出矛盾”。矛盾记异常，不记通过。
2. **工具协议边界。** Codex 暴露的工具与受控执行器支持的工具一致；允许的动作只执行一次，拒绝的动作不执行，混合返回不部分执行。保留违规调用用量。不能用开放全部原生工具或吞掉错误的方式消除异常。
3. **可关闭 CM 的独立实验合同。** 当前大预算实验合同强制 CM=true，底层 runner 虽可关闭，仍需新的合法配置入口。不得直接复用旧臂名却偷偷改变其定义。
4. **DeepSeek CM 路由与资格。** 沿用已执行过的 DeepSeek-v4-flash 路由，新增 ON/OFF 合同明确 `cm_model=deepseek-v4-flash`、`cm_provider=deepseek`，使用独立 DeepSeek 并发池，CM 单独记调用并计入根 token。资格请求使用 `role=cm`、空 tools、4,096 输出上限和合成历史，检查可用摘要、正常结束、完整 usage 及真实 provider 路径；普通 worker 的工具调用探针不能替代 CM 资格。
5. **Review 状态留存。** 每次审查前保存 Lead 精确代码状态、交付 delta、工作区/base、候选摘要、审查决定及采用后状态。仅增加观测，不更改 review 决策策略；事件记录与完整补丁分开保留，不能用截断展示文本替代证据。
6. **跨题滚动调度。** 使用一个共享 provider 锁池和唯一协调器；取消“这一题全部评分完才开始下一题”的串行屏障。保留资源检查、失联租约和重启对账。
Coding 配额在本阶段只覆盖 Flash worker；DeepSeek CM 不属于 GLM Coding Plan，不提高 GLM 的预约系数。两臂按同一 Flash 模型集合与共享根上限检查额度，不按 worker 数重复相加。此前为 GLM-5.3 CM 提出的特殊配额修正不再是本轮启动前置。

启动前形成版本清单：代码与提示词摘要、模型/推理设置、服务层级、适配器、请求输出上限、工具策略、CM 参数、镜像、任务 base、价卡日期、调度版本和评分命令。本文给出的仍是设计参数，不是完成资格验证的声明。

如果正式阶段中途需要改变求解行为、预算语义或模型，停止新格准入并单独记版本；不把变更前后的格子伪装成同一对照。已发生尝试和未知用量保留。

## 4. C1：CM 净收益，首轮 18 次

### 4.1 两个条件

| 条件 | 角色模型 | 根 token | 根普通调用 | Worker 工作调用 | CM |
|---|---|---:|---:|---:|---|
| `FCM_ON` | Sol Lead + Flash 实现 + Flash 测试 | 600,000 | 28 | 每个 8 | DeepSeek-v4-flash，最多 12 次 |
| `FCM_OFF` | 完全相同 | 600,000 | 28 | 每个 8 | 关闭，0 次 |

每个条件每题 3 次，共 9 次；两条件共 **18 次生成、9 个按题/重复编号组织的对照对**。同一对照对相邻准入，在同轮中随机安排先后。调度种子 20260906 只控制顺序，不声称控制 provider 采样随机数。

两臂共同保留现有 worker 的最多一次 finish-only 收尾机会；它仍占根普通调用与 token，不是免费第九次调用。Lead 保留现有根调用 2 次收尾保护。不要把 C1 写成严格的 12/8/8 角色总调用配额——那是后续 B1 的新定义。

每次根墙钟上限 7,200 秒，普通请求输出上限 32,768 token。CM 在估算上下文超过 12,000 token 时触发，按冻结 runner 保留最近 4 个原始消息对象（不是 4 轮对话），执行前核对合法的 assistant/tool 配对边界；摘要提示目标不超过 2,000 token，CM API 输出上限 4,096 token，两者不同。团队记忆、编辑期 curfew、scout distill、bootstrap package 均关闭。

GLM worker 固定走已有 Coding Plan 路径 `https://open.bigmodel.cn/api/coding/paas/v4/chat/completions`；CM 使用独立 DeepSeek 路径 `https://api.deepseek.com/chat/completions`。传输、thinking 与其他角色推理设置在开跑前逐项冻结，不自动回退到其他通道或模型。Flash worker 阵容与旧 Terra/GLM-5.3 团队不同，所以两臂都必须新跑；恢复旧 CM 模型并不让旧成绩成为本轮可复用的对照。

已核对的请求设置为：Sol Lead 请求 `max` effort、`fast` 服务层级；Flash 为 `thinking=enabled`、`reasoning_effort=max`、temperature=1、流式及 tool_stream 开启，900 秒 idle / 960 秒总时限。DeepSeek CM 保持 `thinking=disabled`、temperature=1、非流式、API 输出上限 4,096；请求仍带 `reasoning_effort=max` 字段，不把它解释为开启推理。CM 的超时单独冻结为 120 秒 idle / 600 秒总时限，并受剩余 episode 时间约束。Codex 现有日志为 requested=max、reported=null，后端是否回显确认单列。两臂相同角色的请求参数与适配器摘要一致；已有 DeepSeek CM 执行记录不替代新阶段资格校验，也不证明摘要绝无信息丢失。

### 4.2 “CM-off”具体关闭什么

本实验关闭的是历史摘要压缩，不是全部文本截断。两臂继续使用同样的工具输出边界：环境 stdout 尾部 40,000 字符、stderr 尾部 12,000 字符；runner 在超过 18,000 字符时保留头 12,000 和尾 6,000；可见补丁展示上限 40,000。完整证据另行存储。

OFF 资格检查要求：CM provider 请求数为零、历史摘要替换事件为零、其他辅助摘要开关关闭。不得悄悄引入另一种摘要、丢历史或备用模型来维持可运行性。上下文溢出、输入变大、预约准入失败是要记录的实验结果。

ON 收到截断、断流、空摘要或格式不合法的回复时，保留未压缩历史并记录明确失败事件，不采用坏摘要；用量不完整时保留未知记录，不归零，首次资格不能算通过。真实运行继续采用何种降级行为必须在启动前冻结，不能临时切换 CM 模型。CM 路由或 provider 异常触发停止新准入排障，已有尝试保留。

ON/OFF 的差异允许改变后续求解路径，这是完整 CM 策略的效果。比较的是“是否值得在这个系统中开启 CM”，不是相同轨迹回放下的静态压缩比。即使每次压缩都缩短，也不代表整场 token 更少。

### 4.3 批次、额度和停止边界

首批 6 次为三个题各一对 ON/OFF，计入正式 18 次。检查角色身份、CM 实际开关、GLM Coding/DeepSeek 各自 endpoint、根额度、调用账本、容器隔离、补丁/评分哈希和停止状态。正常的低通过、空补丁、预算耗尽不算健康门失败；不能因为不好看就换题或重跑。

健康门通过后完成其余 12 次。正式生成不自动重试，已准入但异常的尝试保留。模型额度/认证/协议故障先停止新的准入并排障，不用另一模型顶上。每个可冻结候选进行一次官方评分；空补丁也明确保留候选身份和结果，评分基础设施故障保留缺失原因，不伪造失败或成功。

| 首轮上限 | 数量 | 解释 |
|---|---:|---|
| 模型生成 episode | 18 | 不是 18 道题，也不含后续选项 |
| 根 token 上限合计 | 10,800,000 | 18×600,000，是准入上限，不是实际消费预测 |
| 普通调用上限合计 | 504 | 18×28，包含收尾 |
| CM 调用上限合计 | 108 | 仅 9 个 ON 格×12 |
| 普通+CM 调用上限 | 612 | 不把 CM 当免费附赠 |
| 启动前最小模型资格请求 | 最多 3 | Sol / Flash / DeepSeek CM 各一次，单列用量，不进入结果分母 |

不承诺现金费用：Coding Plan 与 Codex 订阅计费不等于 API 价卡。冻结价卡只能给 API 等价估值；实际 token、订阅额度消耗与未知项分别记录。首批结束后用测得用量估剩余成本，不照搬旧 $60 预估。

## 5. 并行与异常调度

目标 **6 个 episode 同时在途**，每个完整团队最多 Lead/实现/测试三个候选容器，每个容器 **1 GiB、2 CPU**。这可能是 18 个容器，不是 6 个。模型请求同时数由 provider 锁另控，不能用 episode 数代替 API 并发。

最近一次只读观察（UTC 2026-09-06 11:36:45）：宿主总内存约 31.19 GiB、可用约 9.09 GiB，Docker VM 总内存约 15.21 GiB。这些值会变化，必须开跑前重读。

先准入 4 个完整团队；至少获得 3 次、间隔 10 秒的健康采样后，仅在“已用内存＋新一对的 6 个容器完整额度”仍满足本批实际占用不超过 12 GiB、宿主可用与 Docker 剩余各至少 2 GiB 时，升到 6 个。若不满足，维持四路跨题滚动，不串成一题一题跑，也不把四路宣传成六路。容器限制之和不是实际预占内存。

| 请求池 | 首轮共享并发上限 | 要求 |
|---|---:|---|
| Codex 账户 | 4 | 所有 Sol/Terra/Luna 共用；可选模型对照也不得各建独立池 |
| GLM Coding Plan | 4 | Flash 实现/测试共用；CM 不占用这个池 |
| DeepSeek | 4 | 所有 DeepSeek CM 请求共用独立池 |

DeepSeek CM 不再直接占用 GLM 请求槽或 Coding 额度；两臂仍共享 worker 池和本地主机，必须保留配对顺序、统一负载与排队记录，不能声称所有运行干扰已消失。

全局模型槽上限 12、每 episode 上限 4，并受以上 provider 限制取更严格值。截图中的 Flash 50 并发不直接视为 Coding Plan 的实测保证；启动前查现有可用额度，结果只用于是否准入，不擅自扩大到 50。

每个新准入波次前检查订阅额度和共享锁；额度不足暂停新准入，保护在途任务，不切付费通道。记录排队、provider 等待、实际生成和评分四种时间。生成与官方评分不重叠，减少本地评分争抢资源对臂间墙钟的污染；首批六次完成及核验后再放后十二次。

单次生成外层看守 7,500 秒、单次评分看守 2,100 秒，阶段新格准入截止 24 小时。达到截止或电脑中断时输出已完成/在途/未准入清单；续跑从同一账本对账恢复，不重复已完成格、不接管仍活跃租约。

首批六次后给出基于实际并发、排队和生成分布的 ETA。Flash 速度与 CM-off 输入长度均未知，不能用旧 9 分钟乘除出保证完成时间。

## 6. R0：已有 Review 的离线审计

先不调用新求解模型或新 reviewer。旧核心 9 格共有 12 个 worker 实例、11 个实际 review 决定；9 个非空交付中，生产 delta 5 个全部采用，测试 delta 4 个为 3 采用、1 丢弃。其余三个为空；T11 Matplotlib 实现者没有 review 决定。

**目前尚未确认能还原多少个精确的审查前状态。** 先做证据资格审查，不能把“有 delta”当“有完整反事实”。需同时具备任务 base、精确 Lead 状态、原始 delta、事件顺序、审查决定、适用性和文件摘要。不能从最终补丁减去 worker delta 来猜审查前状态，也不能夹带之后 Lead 的修复。

对合格的生产交付，同一审查前状态形成不采用/采用两个候选，分别官方评分；上限 5 对、10 次本地评分。同 base、补丁与评分环境摘要完全相同才可复用评分。无法还原原状态但可构造基础版本+delta的，只能另列“独立交付质量”，不能冒称当时的 review 反事实。

测试交付单独核查：是否能收集执行、能否检出 buggy base、是否接受已确认正确的参考候选、断言是否触及相关行为；最多 4 对、8 个测试验证进程。正确参考候选不齐时标记不可判定。仅测试补丁的官方 resolved 不足以评价测试者，因为官方 harness 可能重置或覆盖测试文件。

生产采用的效果分类预先固定：新增官方通过且无回归为“有益”；失去原有通过或增加 P2P 回归为“有害”；二元结果不变但 F2P 增加且无回归为“局部改善”；可见评分完全不变为“未观察到效果”；状态或评分不完整为“未知”。分项测试得分与整体结果同时保留，不能把未知或平局强行二分为“审查正确/错误”。

已有生产样本没有一次拒绝，因此不能估计“拒绝了多少好生产补丁”，也不能给总体 review 准确率。局部采用前后评分只测这一时刻的补丁效应，不包含 Lead 后续适应，因此不是整场审查策略的随机对照。

以上 10+8 是**工作量上限，不是已经具备的有效样本数**。历史审计与新 Flash 团队分列。C1 新增的完整快照可用于同样审计，届时先枚举合格记录再列本地评分清单，不自动启动无上限补评。

## 7. B1：预算与测试者资源，后续可选 36 次

C1 完成后再决定是否进入，不自动排入首轮。四臂共用同一新版本、同一模型组合；每题每臂 3 次，共 **3×4×3=36 次**。

| 条件 | 根 token | Lead 普通调用 | 实现者普通调用 | 测试者普通调用 | 对照用途 |
|---|---:|---:|---:|---:|---|
| `FB_LOW_EQ` | 600,000 | 12 | 8 | 8 | 新的严格角色额度基线 |
| `FB_HIGH_EQ` | 2,400,000 | 12 | 8 | 8 | 只增大 token |
| `FB_HIGH_TEST` | 2,400,000 | 12 | 4 | 12 | 固定总调用，向测试者倾斜 |
| `FB_HIGH_NO_TEST` | 2,400,000 | 12 | 16 | 0 | 不设独立测试者，把额度用于实现 |

角色额度定义为**包含收尾的总普通请求上限**，每个 worker 的最后 1 次收尾额度在其配额内、Lead 的最后 2 次在 12 次内。禁止自动借用未花完的角色配额；根 token 仍共享，CM 仍记根 token。所有臂普通调用合计最多 28、CM 默认保持 DeepSeek-v4-flash ON 且最多 12 次、墙钟 7,200 秒、输出上限和模型相同。若要改变 CM 状态，必须在 B1 冻结前统一修订四臂，不能看到中途结果后再挑。

这需要新增按角色总额度的执行语义以及无测试者的合法 roster/提示词。目前还没有实现，且不同于 C1 的工作调用+额外收尾定义。因此 **36 次都要新跑，C1 的格子不能充当 B1 基线**。

三项对比各回答一个有限问题：

- HIGH_EQ−LOW_EQ：低调用纪律下提高 token 天花板的作用，不能外推到旧 160 次普通调用配置。
- HIGH_TEST−HIGH_EQ：给测试者更多**调用机会**是否改善结果。它不是固定 token 占比实验；模型单次上下文长度不同，实际 token 分配仍需统计。若要研究 token 比例本身，需另立角色 token 配额实验。
- HIGH_NO_TEST−HIGH_EQ：专门测试者与“把同等调用资源交给实现者”相比是否值得，识别的是资源配置策略。不能称为测试信息本身的纯因果贡献，也不能从失败推出测试者毫无帮助。

如果还需要测“测试者的信息而非资源”，另行设计同资源、同已保存状态的测试交付可见/不可见干预。没有该对照时，信息贡献仍列未知；不为了凑出结论把移除角色与重新分配资源的效果混称独立贡献。

DeepSeek CM 与 Flash 使用各自的 provider 并发池，沿用 C1 的统一调度与记账。

本阶段准入总上限为 **70.2M token、1,008 普通调用+432 CM=1,440 调用**；不是预计一定消费这么多。四臂不同时更换模型或增加 checkpoint。交付检查点和语义澄清机制留到新的单变量计划，避免把工程策略同时混入预算试验。

## 8. M1：必要时的 GPT / Terra max / Luna max 模型对照

Flash 是优先模型，不是排除 GPT。Lead 继续 Sol；若要判断 Flash 实现角色是否限制生产交付，可固定测试者为 Flash、机制与角色配额相同，仅替换实现者为 **Flash、Terra max、Luna max**。Sol 作为固定 Lead；若以后要测 Sol 实现者，则用一个明确的替代模型臂，不默认再加第四臂。

这是“实现者模型＋其指定推理配置及适配器行为”的对照，不能声称不同模型拥有相同隐藏推理算力。启动前核对请求中实际模型 ID、max effort、适配器输出上限和返回 usage；不把配置文件上写了 max 当成后端接受了 max 的证据。

M1 默认沿用 C1 的 600,000 根 token、28 次普通调用、每 worker 8 次工作调用加最多一次占根额度的收尾、DeepSeek-v4-flash CM ON/12、7,200 秒；不是 B1 的严格角色总配额。GPT 实现者请求 max/fast。底层路由已支持 Terra/Luna，但旧实验合同没有这些新组合，现有资格探针也没有 Luna，所以必须补合同和资格校验；最多 5 个模型身份各探测一次，单列用量。

完整三模型上限为 16.2M token、756 次普通调用+324 次 CM=1,080 次；仍是上限而非费用预测。

完整的三模型版本需要 **3 题×3 实现者×3 次=27 次同期新生成**，可在预算不足时事先缩成一个 GPT 候选对 Flash 的两臂 18 次。二者是替代方案，不相加，不自动启动。所用 CM、预算、推理配置需在这个阶段冻结前确定，不能边跑边改。

M1 的进入理由是未来使用场景确实需要模型选择，或 C1 显示 Flash 生产交付不足而 CM 对照解释不了；该判断只能触发新的探索阶段，不能追溯改变 C1 假设。若这个阶段较晚启动，使用同期 Flash 对照，不只追加 GPT 格再与过去较快/较慢时段比较。

模型对照不是预算对照的必经步骤。如果先选择它，B1 应暂缓，避免“可选”模块全部自动开跑。即使 M1 在这三题中选出了模型，也需新题确认，不能用同一批既选模型又声称泛化优势。

## 9. 指标、统计与结论规则

首要终点是**官方通过**与**最终可应用的生产交付**，每个都按 planned、admitted、已评分、缺失分开列。测试文件改动和空补丁不算生产交付。已准入但异常的尝试不能从运营分母消失；未能官方评分的保留未知，并报告其最好/最坏逻辑范围，不能全部伪装成已官方判失败。

按题、条件、重复、角色拆分下列观测：

| 层次 | 必须记录 |
|---|---|
| 结果 | resolved、F2P/P2P 原始节点与分母、补丁是否适用、生产/仅测试/空补丁 |
| 停止与交付 | completed、根 token 预约拒绝、普通/角色调用限制、上下文、超时、provider、协议、评分故障；首次生产修改与可交付候选时间 |
| 资源 | 各角色输入/缓存/输出/总 token、已观测/未知/预留、普通/CM 调用、冻结价卡 API 等价费用 |
| 时间 | 排队、provider 等待、生成墙钟、评分墙钟、各调用累计耗时；不把并行累计耗时当墙钟 |
| CM | 触发/跳过/准入拒绝/失败、每次前后上下文、摘要模型用量、最终整场用量 |
| 机制 | 原始交付、review 决定与状态摘要、保留到最终文件的改动、测试命令真实状态、收尾发生位置 |

正式资源优势判定要求每题每条件均已完成预定的 3 次准入，并有完整评分与用量。若 24 小时截止或故障造成两臂准入次数不同，不比较总和来宣称省 token；只报告运营账本、完整配对的描述性结果与缺失范围。已准入的异常尝试仍保留，不能删去以后凑齐“成功样本”。

CM 净 token 比较使用全部角色含 CM 的总用量：`sum(ON total tokens) / sum(OFF total tokens)`，并展示每题三个重复。**提前失败导致更便宜不能算净收益。** 有未知调用用量时，不输出伪精确资源排名；已知下界与预约记录分开，预约不是实际用量。

“生产交付后的通过率”只作描述分解，因为交付本身受处理影响；不能据条件化子集声称各臂语义能力一样。测试节点也不是独立题目，3 次重复不能把三个题扩成九个独立题目。主报告以每题 0—3 次通过和逐次轨迹为主，不用合并九次重复的 McNemar 显著性作晋级证据。

预设一个对称的**工程效率候选**规则：在全部 18 次准入、评分与用量完整的前提下，某条件逐题通过次数都不降低、生产交付总数不减少、全部已准入尝试总 token 至少降低 15%、生成墙钟中位数增加不超过 20%，且用量与评分无影响结论的未知项。满足时仅建议后续验证，不证明总体非劣或自动切换机制。质量/资源互有得失时直接报取舍；都不满足则结论“不确定”。这个规则不决定是否跑完 18 次。

各阶段结束后允许写出的结论示例：

- C1：“在固定 Sol+Flash 团队、60 万 token、三道诊断题上，开启 CM 带来……”；不能写“CM 普遍有效/无效”。
- B1：“在 28 次调用纪律下，多给测试者调用机会带来……”；不能写“最优测试 token 比例已找到”。
- R0：“这几个可还原审查状态中有多少有益/有害/无可见变化”；不能写整体 review 准确率。
- M1：“固定其余角色时某实现模型在本诊断集的交付表现……”；不能写模型榜单排名。

## 10. 交付与执行顺序

启动后的顺序为 P0 工程与离线核验 → 冻结清单 → 最多 3 个最小模型资格请求 → C1 首批 6 次及健康核验 → 其余 12 次 → 完整评分、聚合与独立复核。历史 R0 先做只读资格审查，合格后的本地评分与模型生成错开使用资源。

C1 结案交付：逐题结果 CSV、角色/CM 聚合、调用账本、补丁与评分绑定、故障与缺失清单、验证 JSON、中文分析报告，以及 Python 生成的通过矩阵、交付矩阵、总 token/CM 拆分、停止原因与时间图。题目纵轴沿用本计划的 Xarray→Matplotlib→Pylint 历史难度顺序，不按新结果重新排出更漂亮的图。

本计划文件：

- `PLAN_ZH.md`：可审阅的中文设计。
- `PLAN.json`：设计参数与执行前置，状态仍为 plan-only。
- `C1_PLANNED_RUNS.csv`：首轮唯一默认清单，18 行。
- `B1_OPTIONAL_RUNS.csv`：后续预算分配候选清单，36 行，不参与默认调度。
- `PLAN_VALIDATION.json`：文件、计数和逻辑一致性检查；不是 runtime 资格通过或实验完成证明。

**当前授权范围为 18 次 C1；36 次预算分配和 27 次三模型对照均为后续独立选择，不进入本次启动队列。**
