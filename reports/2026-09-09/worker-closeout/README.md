# Worker 收尾与诊断 · 0.7.6

本轮针对实际 DPH 任务中“文件已写出，worker 随后耗到无法提交报告，团队只返回普通子代理失败”的问题。原案例实现者限额 600,000 token／36 次，10 次调用累计 578,722 token，余 21,278 时触发 WORKER_TOKEN_RESERVATION_DENIED；第 4 次调用已保存 HTML，之后 6 次又消耗 415,121 token。这是历史诊断案例，不是本版效果实验。

## 实现范围

- 在原有独立 worker 限额内，按完整请求成本和剩余调用次数决定提前收尾；最后请求只交付文字，工具不可执行。manual／Auto 的原限额保持，不限额和 Lead 不受新增限制。
- 收尾优先于 DPswarm 主动 CM；未知调用继续保留预约占用，不记为零，不发送越限补救请求。
- 从可信子会话终态、成功工具操作和预算账本提取结构化诊断。区分文件候选、报告和验收；不按目录已有文件猜测来源，不把部分成果改写为任务成功。
- 给 Lead 的运行／状态／复核结果使用有界的紧凑摘要，完整诊断保存在受保护的审计账本；避免多个 worker 同时失败时重复证据超过宿主工具输出上限。摘要明确标注省略，不把它冒充完整记录。
- DPH 展示角色状态、用量与剩余额度、失败原因和候选数量；公开状态不包含任务正文、文件路径、报告或供应商错误正文。

## 验证

完整插件回归 **276/276**、Python 控制服务 **520/520**、原生 DPH **4/4** 场景及浏览器 **4 项**检查通过。详情与源码原始字节哈希见 [VALIDATION.json](VALIDATION.json)。原生探针使用隔离 DPH、真实 Python 控制服务、原生工具和本地确定性模型适配器；不调用付费模型，不计入鹈鹕或 SWE 实验。

## 边界

提前收尾依赖输入估算，无法保证所有突发工具输出、供应商计量差异或进程中断都能正常提交。文件候选是成功工具操作的证据，Lead 仍须核查磁盘现状。静态检查与浏览器渲染、任务验收分别陈述。真实质量、净 token 和成本收益尚未进行新对照实验。

原生场景包括最后一次调用只交付、Code Mode 外层与嵌套工具收尾拦截、写文件后服务失败仍保留候选、极小额度下两角色拒绝但 Lead 收到有效 JSON。CM 的跳过原因明确为 worker_closeout。Code Mode 场景主动注入预算状态过渡，不代表模型自发选择。

联调中修复了真实宿主工具结果嵌套结构导致的候选漏记，以及重复失败诊断超过宿主输出上限的问题。初次测试曾受运行目录、Windows 子进程编码及探针参数影响；最终上述通过结果来自修正环境／探针后的冻结源码。
