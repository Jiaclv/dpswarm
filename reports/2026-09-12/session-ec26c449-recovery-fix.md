## 机制与实现的边界

1. **候选边界的实现错误。** “观察到成功写入”只是事实，不等于“此文件属于交付”。原收集逻辑把诊断记录直接喂给严格快照入口。修复按来源与工作区边界分类，不识别 `verify.js`、TEMP 名称、HTML 类型或某种验证工具；工作区外的可信写入仍保留诊断，显式交付路径和真正依赖仍严格校验。
2. **恢复能力缺失。** 捕获失败只返回异常，已花费的实现者工作与待验证角色没有可恢复的检查点。修复持久化原任务、原交付、故障阶段和未派角色授权；确定所有 worker 已结束后交还 Lead 判断。`dpswarm_resume(checkpoint_id, reason)` 只重试封版和原来从未发行额度的验证角色，不重新实现、不重复发钱、不替 agent 判定通过。
3. **Lead 对恢复能力的推断有误。** `terminated` 并不一概禁止 `dpswarm_rework`：旧代码允许符合条件的 submitted/terminated 实现条目。但旧返工会新派实现者，且本案没有原 tester/reviewer 血缘，因此不能据此声称“仅补完独立验证”已经可用。旧会话缺新检查点，已终止条目不会被此次升级复活。
4. **证据充分性仍是 agent 判断。** 工具给出候选身份、限制、原始证据与失败事实；不按固定截图次数或硬编码任务类型自动验收。部分观察不能扩大成所有要求通过，验收协议仍保留 unknown/blocked 和独立复核。

## 本轮实现范围与限制

新恢复入口只接受当前契约、仍 submitted 的原实现者、可信终止证据、当前宿主原租约和未改变的角色配置。原 run 的验证预算仅允许一次恢复 claim；已发行、已撤销或已花费的角色额度不能再发行。封版重试在 claim 前进行，因此重复封版失败不会消耗验证额度；claim 后的进程崩溃不能无条件再开一次。恢复不会自动验收，也不会修改这份旧 HTML 或旧会话的验收记录。
