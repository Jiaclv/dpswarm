# DPswarm 验收修复与 Luna Max 验证

日期：2026-09-12。状态：本轮源码集成、确定性回归及 Luna Max 已知问题动画回归完成；日常 DPH 尚未升级到本轮源码。

## 已接入的机制

- 新原生任务从宿主的直接用户消息绑定正文及需求；Lead 的计划、编辑范围和历史报告是派生资料。
- 文件任务必须声明交付入口。运行时保存入口、改动文件及可识别的本地依赖，按字节建立不可变候选视图；最多 64 文件、3 MiB。无法识别或封存的必要依赖记 unknown。
- Tester 与 Reviewer 采用唯一 dpswarm-review-v1 JSON 报告。最终报告绑定 candidate_id、manifest_digest、requirement_revision、evidence_revision。
- 用户修订、证据更新、最终审查分别记账；Reviewer 自己的报告不会再次改变它所审查的输入版本。旧报告不能冒充看过新增证据。
- 发现跨返工保留。所有相关发现都需在当前候选明确关闭或裁决；编辑范围不能作为豁免理由。真实用户变更后可说明原发现不再适用，须引用该用户消息并说明需求的变化。
- Python 真实接受事务统一验证候选、实现/验证报告包、需求、发现、当前审查及账本版本；未登记的旧任务维持其原有合同。
- dpswarm_repair_report 只派发同角色的新报告会话，沿用精确模型路线并仅使用原额度剩余量。原报告和发现保留，不发放重置预算。
- dpswarm_amend_task 绑定真实新用户消息到原业务任务；跨 API/审计写入中断后可恢复，避免重复修订。
- staged 的 ready 状态绑定内容清单，受管读取指向固定视图，并记录实际消费版本；未记录的必要上游消费不能被当作已验证。
- 补齐 Python 对分阶段交接、编辑范围和 mailbox 实际事件的审计支持；ready 只有在真实状态转换成功后才公开，读取失败不记作已消费。
- 初次派发前核对完整团队的工作槽位和点数。并行/分阶段计划超出容量时，在模型调用前拒绝，不自动扩大限制。
- 报告修正若未能准入或绑定新会话，撤销未使用的额度分配，保留原报告、成员关联与剩余额度，允许从原条目重新尝试。

## 验证入口及边界

协议回归由 gpt-5.6-luna / max 执行。跨语言测试使用真实 Python HTTP 控制服务和 EventStore；其 native 子代理输出为确定性夹具，不能用作模型质量结果。

当前 DPH 配置没有精确的 Luna Max 原生路由，因此未进行 DPH 原生 Luna 模型调用。真实模型试验使用 Codex gpt-5.6-luna / max 子代理，分别检查旧鹈鹕、生成新动画、抵抗 Lead/旧 Tester 的误导及区分颜色偏好。入口差异须在结论中保留。

所有完整日志保存在 .tmp/acceptance-repair-20260912/。模型用量无法观测时记 null，不以估计数补齐。旧 911/pelican-bicycle.html 保留为故障样本。

## 尚不代表的保证

静态依赖扫描不能证明任意 JavaScript 程序的全部执行依赖。受管工具的 ready/read 约束不是操作系统级写锁。结构化验收要求证据和裁决完整，不能自动证明模型的语义判断正确；模型质量仍需真实渲染与对照样例。

本次补丁未把动画专用 IK 规则写入通用调度器，也未更改用户的模型、并行模式或额度配置。实际安装/加载状态见下文。
