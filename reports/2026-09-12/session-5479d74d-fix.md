## 修复了什么

| 原问题 | 现在的实现 | 保留的边界 |
|---|---|---|
| 用户发“继续”后，新消息门禁要求重新启动团队 | `dpswarm_continue_task` 记录 Lead 明确选择的同任务关系，绑定当前和上一条真实用户消息；保留原合同、任务状态与额度 | 不靠关键词分类；不把正在运行或受阻的任务变成已完成；不允许伪造来源、跨任务重放或循环关系 |
| 实现者返工没有实际变化，仍重跑 tester/reviewer | 比较封版内容、入口、依赖事实、消费版本和需求修订；默认 `verification:auto` 在完整可比且相同时交回 Lead 决策 | 相同内容不等于正确；旧 finding 保留，旧 PASS 不自动绑定到新候选；变化或无法比较时仍验证 |
| 想补验证却只能重新派实现者 | `dpswarm_verify_rework` 只领取该返工决策中尚未发行的验证额度，使用冻结模型与设置 | 持久化原子 claim 防止重复派发；候选/设置变化拒绝；tester 清理不确定时停止后续角色并保留租约 |
| 收尾工具仍可见，worker 继续尝试工具而没有完成报告 | final-only 移除工具 schema；从首次请求即提供条件式收尾指导；重试重新预测；正常输出在原额度内预留报告成本和新增上下文 | 不增加额度；估计不是 tokenizer 保证；预算确实不足时仍拒绝，不靠无限重试收尾 |
| 未知传输失败与重试的预算记录难以解释 | 保留未知预约，修复并发准入重建 call 对象后结算未同步的接缝；每步显示剩余额度与报告估计 | 已观测、未知预约和已承诺分别展示；worker 汇总排除 Lead，不建立可转移的团队剩余池；缓存 token 不等价于普通输入费用 |
| JSON 结果存在却读不到关键数值，UTF-16 被反复误读 | 新增通过宿主文件服务执行的只读 `dpswarm_read_evidence`，支持 UTF-8/UTF-16、JSON pointer、分页和文件哈希绑定 | 不执行文件内容、不直接绕开宿主文件服务；未 ready 的上游拒绝读取，ready 后固定快照并记录消费版本；大小有限制；观测值不是验收结论 |
| 巨大候选 Base64 和原始报告把工具结果冲到截断文件 | 模型视图保留候选身份、哈希、路径和状态，省略文件正文；验收元数据与长报告可以完整分页读取 | 内部控制数据及原报告保持完整；摘要不升级为通过，跨页变化会被识别 |
| 重复尝试不支持的看图能力，或自行制造“禁止浏览器”限制 | 从宿主精确模型路由读取能力声明；有事实才标 supported/unsupported，否则 unknown；澄清用户要求、Lead 方法建议和工作报告的权限差别 | 不写死模型名，不替换用户指定模型；验证方法与充分性由 Agent 判断 |

## 对原诊断的一处更正

325,013 token 的差额有原生 `assistant/attempt` 传输失败记录：该尝试没有 usage，之后才重试。它不是可以直接清除的“重复计费”。修复保留这个未知预约，改善重试预测与收尾预留。相关原分析和会计记录已补上更正，历史账本没有改写。

独立复核还发现：输出裁剪阶段使用的较高输入估计，可能在派发预约阶段被较低的字符估计覆盖。本轮要求预约与实际冻结请求采用的计量依据一致，并用未知失败、重试和冷恢复测试约束；不是把未知消耗估为零。

## 为什么仍然是 Agent harness

代码负责事实、权限、身份、版本、预算与一次性授权。Agent 负责判断当前消息属于原任务还是新需求、哪些证据仍相关、需要补什么检查、如何修复以及是否足够交付。新增判断入口不以“鹈鹕”、HTML、浏览器工具名或固定检查次数选择业务流程。

`verification:auto` 的暂停只说明输入没有变化，既不关闭 finding，也不代替 reviewer 判定。Agent 可以要求继续修复，明确执行当前候选验证，或如实报告剩余阻塞。完整接受仍受原有候选绑定与结构化验收事务约束。
