## 1. 判断与设计边界

这次是三类问题叠加：模型执行错误（错误 SVG 坐标、错误检查器、错误结论）；harness 提供的责任、来源与证据信息不够一致；预算收尾实现的预测和真实请求不一致。不能把全部问题归为模型能力，也不能靠写死一套任务流程解决。

目标：让 Agent 更容易作出有依据的判断，让已经得到的有效事实能够复用，让程序守住身份、版本、权限、资源与记录的一致性。**控制面不判断鹈鹕应该怎样运动，也不决定每个任务必须经过哪些检查。**

| 层次 | 应负责什么 | 不应承担什么 |
|---|---|---|
| Agent 的语义判断 | 需求怎样理解、采用什么实现、如何验证、缺陷是否相关、是否值得补查/返工、在授权内何时结束 | 无依据改用户要求、替换用户指定模型、声称未做过的验证 |
| Harness 的决策支持 | 提供可信用户原文、当前职责、可用能力与观测、证据索引、候选变化、预算事实；在需要作决定时提供简短引导 | 固定每轮必须几次测试、几次重试、多少轮返工；把所有任务变成同一个 checklist |
| 程序硬约束 | 身份/来源、版本/引用、权限、预算结算、状态转换、记录缺失与前后不一致 | 用关键词、固定像素阈值或通用规则代替质量判断；将 schema 合法当作内容正确 |
| 可选工具与适配层 | 提供可靠的脚本执行入口、取证/引用能力、任务无关的故障信息 | 为本案内置 SVG 1200 周期、鹈鹕腿型或 Chrome 必经流程 |

固定团队是用户已经选定的协作约束。Agent 在该约束内仍须自主求解。当前 Auto 是预算选择维度，不是自主拓扑模式。若以后要让 Lead 自选角色、跳过配置角色或改变串并行，那应是单独提案，不借这次修复暗中改变产品约定。

## 3. 具体归因

| 日志现象 | 归因 | 当前状态与处理方向 |

| Lead、Tester、Reviewer 重复读取、重写检查器 | Harness 职责提示矛盾与证据复用不足；某些补查本身合理 | 当前源码仍有交付元数据要求 Lead independently verify；先消除冲突，再引导按缺口补查 |

| 像素差被称为视觉验收和完整无缝证明 | 代理指标被当成目标证据；属于证据充分性判断错误 | 不写死必须截图或必须视觉模型；让 Agent 明确当前方法能/不能支持哪些要求，必要未知不偷换成通过 |
| 每次生产返工又运行测试、评审 | 现有固定配置的成本放大因素，并非本次单独的程序故障 | 先让各角色复用证据并只新增必要工作；格式问题已有 report-only repair。是否改变角色派发策略另行讨论 |

## 4. 拟议实施顺序

### P0：冻结真实基线，区分已有修复与本次增量

交付：源码与安装版关键文件哈希、模式与角色配置、故障日志引用、已有补丁清单；明确 legacy 与 strict 任务的行为差异。

不停止服务、不覆盖旧日志、不把旧任务自动迁移成新合同。将本次日志保存为可回放故障夹具；借用真实数据做协议测试，不执行历史命令。

完成条件：每项后续改动都能说明是新修复、补齐旧修复，还是验证已实现能力。先选完整匹配的隔离 JS/Python 组合，避免只替换几段提示却混用不兼容控制服务。

### P1：先修预算收尾的实际请求一致性

已确认源码接缝：
- [budget.js:35](../../dpswarm-dsh-plugin/lib/budget.js:35)：实际收尾保留工具 schema。
- [budget.js:135](../../dpswarm-dsh-plugin/lib/budget.js:135)：收尾输入预测按 tools=[]。
- [budget-runtime.js:591](../../dpswarm-dsh-plugin/lib/budget-runtime.js:591)：输出仍能被 remaining-input 限制到很小。
- [budget-runtime.js:637](../../dpswarm-dsh-plugin/lib/budget-runtime.js:637)：兼容路径允许一次工具尝试加最终报告。

拟改：让预测、准入和实际请求共享同一份请求组成；覆盖实际工具列表、提示、历史、可能的工具拒绝结果和剩余报告请求。不能只改注释，也不能只提高常数。

保留现有模型兼容性：此前移除工具 schema 曾导致 DSML 格式问题，所以不直接一律删工具。如果宿主支持可靠的 report-only 请求控制，先离线验证；否则按照实际保留 schema 的路径计量并提前进入收尾。

给 Agent 显示当前剩余额度、下一步输入成本估计、收尾可行性及估计的不确定性；预算提醒是决策事实，不是让 Agent“把额度用满”的目标。更早保存候选和必要观察；无法在原额度内可靠取得报告时，明确 incomplete，保留已保存证据，继续/补报告由 Lead 按授权选择。

不静默降低用户选定的 effort，不重置 grant，不偷偷发额外模型请求，也不承诺有限输出一定能获得有用文字。

同时修正报告提取的语义：[worker-diagnostics.js:114](../../dpswarm-dsh-plugin/lib/worker-diagnostics.js:114) 会回退查找最后一条含正文的 assistant 消息。本次最终响应只有推理，于是旧的“准备运行 Node 检查”进度文字被诊断成 report_available。保留这段恢复信息，但将最终报告、进度摘录、截断响应分别标记；只有真正的报告才进入报告解析与补交流程。已有 report-only repair 仍使用原剩余额度，额度不足时明确阻塞，不因有该工具就保证可恢复。

完成条件：重放本次 tester 边界时，预测与实际使用同一份请求组成，保留估算误差而不宣称等于供应商精确计费；正常、未知 usage、工具拒绝、冷恢复、report repair 等路径不双算、不超预算；报告缺失不能假称已报告。

### P2：统一验证职责提示，并改成围绕决策的引导

接缝：role-guidance.js、index.js 的工具描述、fixed-team.js 的 evidence_kind / next / report 元数据。

当前冲突例子：[role-guidance.js:49](../../dpswarm-dsh-plugin/lib/role-guidance.js:49) 把验证判断交给 Reviewer，但 [fixed-team.js:725](../../dpswarm-dsh-plugin/lib/fixed-team.js:725)、[847](../../dpswarm-dsh-plugin/lib/fixed-team.js:847)、[1363](../../dpswarm-dsh-plugin/lib/fixed-team.js:1363) 仍普遍要求 Lead 再验证。

拟改：从已有的 Reviewer 配置、当前审查状态与显式 takeover 状态，统一生成当前责任说明；删除互相冲突的重复文字。独立 Reviewer 已有有效证据时，Lead 主要检查报告是否回答原需求及是否存在冲突；有缺口或可疑方法时仍可补查、质疑并交回原验证者，不禁止 Lead 看代码或运行工具。

Harness 在相关决策点简短引导 Agent：
- 新增条件是否来自用户目标，还是自己的实现偏好？
- 下一步具体要减少哪个未知，已有证据为什么还不够？
- 重复同一方法前，候选、环境或假设发生了什么变化？
- 当前反馈应修作品、补报告，还是重新判断检查方法？
- 原要求满足后，继续投入的预期收益是否足以支持下一步？

这些不要求每步输出长篇反思，不额外派一个固定 Manager，不固定“失败几次就停”。

完成条件：不同配置和状态下，系统提示、工具说明与返回体中的验证责任一致；仍允许有依据的独立质疑。

### P3：把可复用事实放到已有交接与证据接口

优先扩展现有 audit / dpswarm_report / acceptance / mailbox，不新建第二套状态机或知识库。

候选相关记录尽量包含：检查目标、实际输入版本、使用的方法/命令或工具事件引用、完成/错误状态、结果摘要、覆盖说明、未验证项。环境相关记录包含角色/模型、权限上下文、探测对象、时间、失败类别与适用条件；不得把旧进程、旧权限、其他模型的观测直接当当前事实。

当前已经有约 600 字符交付摘要和报告分页，本项是在其基础上补事实选择与状态，不是重新发明摘要系统。事实默认给紧凑摘要和可回查引用，详细输出按需读取。保留原文与命令结果，不让截断摘要代替原始证据；不要把历史长报告和诊断账本反复完整灌进 Lead。

Agent 决定是否复用或重跑。典型重跑理由是候选变了、环境变了、结果过期、检查方法有漏洞、结论冲突、关键输出缺失；同一环境中重复失败若没有新信息，Agent 应选别的方法或明确未知。

程序只校验存在性、来源、版本匹配及状态，不把“该命令 exit=0”自动升级为“需求正确”。实际工具调用只能证明检查执行过；其数学判据和覆盖是否有效仍须语义审查。

完成条件：后续 Agent 能读到本次图像能力失败、浏览器权限失败以及已经成功的脚本执行方式；环境改变后可以重新探测；Reviewer 可发现已有检查器本身错误。

### P4：补上证据充分性与最终表达的 harness 引导

复用当前 strict acceptance 的 requirement/finding/candidate/review，不重新造 schema 总体系。必要时仅为 evidence 增加可选、有版本的工具事件/文件结果引用；先检查兼容和体积，字段不应强迫所有任务采用同一检查方式。

引导验证 Agent 说明：这条证据对应哪个原要求、证明了什么、不能证明什么、有没有把代理指标当作目标。对自己新写的检查器，按风险选择解析/覆盖核对、人工抽样或能区分错误候选的反例；不强制每个廉价检查都附带一套测试。

区分缺陷与建议由 Agent 作判断并留下依据。不能硬编码“1 像素无所谓”；也不能把所有非零偏差都变成必修。Lead 的不要改某处是编辑指令，不是用户豁免。确实要放宽用户要求时，只能依据可信用户修订；普通方案调整无需逐项向用户审批。

交付时把当前候选、必要要求结论、相关发现裁决与未验证范围整理成可核对事实给 Lead。Lead 自由组织最终回答，但应与这些事实相符；如“必修问题已解决，某项不属于原要求”不能写成“检查输出为零”。程序不靠自然语言关键词匹配宣称能自动发现全部矛盾，也不增加每次都调用的隐藏终审模型。

完成条件：协议测试防旧版本/缺记录被接受；模型行为评估能分别检查“错误裁决”与“正确裁决但最终说错”。保留“真实截图、模拟 DOM、静态推导、视觉观察”之间的证据边界。

### P5：分层验证，再决定接入日常运行

先做确定性回归，覆盖预算实际请求、责任提示一致、证据版本与环境变化、报告缺失与补交、legacy/strict 兼容。它们只证明程序合同。

随后在用户批准的模型与预算下做小规模配对行为评估。任务至少覆盖几种不同工作类型：代码修复、视觉产物、数据或文档分析；故障类型包括需求扩写、错误检查器、权限变化、重复失败、证据冲突、预算紧张。不得只对鹈鹕样例微调后宣布机制改善。

冻结任务、可用工具、角色/路由、effort、预算口径，比较原版本与仅修 harness 版本；记录任务质量、已知缺陷误放行、无信息重复动作、报告缺失、最终结论一致性，以及 Lead/worker/CM 的 token 与时间。对语义结论做人工或独立审计，不能用模型自己的 PASS 当客观分数。样本量只支持试点结论，不先承诺通用提升比例。

通过后才准备匹配的安装组合、回滚清单与真实请求核对；在明确授权和无活动任务的条件下切换日常宿主。当前这轮不执行安装或真实模型评估。

## 5. 本计划刻意不做的扩建

- 不把 SVG、浏览器截图、像素采样、固定测试数写进通用调度器。
- 不固定返工上限来强迫接受，也不把“遇到失败”自动等价成停止全部工作。
- 不自动切换模型、增加预算或跳过用户配置的 Reviewer。
- 不为了减少重复而禁止 Reviewer 重读文件或挑战 Tester。
- 不增加常驻新角色，也不以本次缺陷修复名义重写自主拓扑。
- 不把严格依赖封存能力仅覆盖部分文件格式，包装成任意工程都已可完整验收；相关扩展按实际任务需求另列适配工作。

## 6. 建议本轮讨论结论

建议先确认 P0–P4 的修复方向：**补已有控制面，把 harness 的事实输入、责任说明、取证与收尾做准确；把实现策略、验证方法和投入取舍保留给 Agent。**

P5 的真实模型组合、运行预算和日常安装时机在准备好可审阅补丁与验证结果后落实。现有验收修复的部署验证与本次新增修复分别记账，避免混成一个“已经全面解决”的结论。
