## 先给结论

这次成功落盘并完成了正式验收，比“有文件但无候选/无法验收”更进一步；但它用了 16 个串行子代理、约 52 分 51 秒主轮运行时间、至少 1350.4 万可核算 token。最终的两个正式验收都是主代理显式接管，而不是独立复核者给出通过判定。

开销由几类问题叠加：初版实现与自测模型不一致；第一次返工未写文件仍重走下游；continue 被按新消息绑定为新任务；验证方法未经校准、文件读回适配失败；长上下文及预留规则使代理在取得关键证据前进入只能写最终报告的状态。没有证据表明这次又发生了早前的 storage 注入错误，或最终候选始终不存在。

“全部是无效折腾”也不准确：初始测试/复核确实发现了真实缺陷，两轮有效修改修复了腿与云，新验证队也确实产生了可用的浏览器证据。问题在于有用工作之间夹入了大量重复调度、重复验证和证据读回失败。

## 4. 每个关键转折到底错在哪里

### 4.0 用户要求与 Lead 自加约束需要分开

原始用户只要求“创建一个 HTML，内容是 SVG 绘制一个鹈鹕骑自行车的 2D 动画，放到本目录”。Lead 将其展开成单文件、自动循环、身体与脚踏协调等目标；其中不少是合理的设计选择。但它又在派发正文加入仅使用 SMIL/CSS、不能打开浏览器、不能创建测试或其他文件等限制，这些并非用户指定。

初始实现者因此主要依靠静态数学检查，后续测试者根据 trusted user_request 判断用户并未禁止浏览器验证，才使用真实渲染。这里一方面说明可信用户来源与 Lead 指令分层有价值，另一方面也暴露出 Lead 把实现选择写成强限制，压缩了工作代理选择验证方法的空间。harness 应让代理区分用户硬约束、委派写入范围与可调整的方法建议；不能让 Lead 添加的实施细节自动升级为用户授权边界。

### 4.1 初版：测试通过的是另一种运动，不是已写入的 SVG

初始实现者的第 8 步采用 world = local + (pedal − foot) 的平移模型，按半径 34 估计腿顶在身体附近。但实际 SVG 层级中，腿没有放在脚掌反向自转的子组内，而是随父组绕五通旋转，相关端点半径达到 166，纵向范围可到 y=526，超过地面 y=440。

所以问题不只是“没看截图”，而是自测模型和真实渲染变换不一致。首测试者取得真实 Chrome 帧后，橙色像素统计在道路下方发现 809/851 像素，并由复核者重算 SVG 层级确认。此处多代理复核有实际价值。

这是具体实现错误，加上实现者的验证判断错误。通用 harness 应要求代理说明“测试怎样绑定真实执行路径”，对复杂变换使用真实运行结果或直接从实际产物解析；不应硬编码“SVG 都必须做 2160 相位检查”。

### 4.2 第一次返工：算完不等于写完，系统却继续派下游

返工实现者消耗 477,429 token 计算新几何与角度，但没有写入交付物。后续测试者和复核者合计又用 680,908 token 检查相同错误版本。它们保持了证据诚实，没有把未写入的方案判为成功；但调度缺少基于“新候选/新证据有没有产生”的判断。

第二次返工时，Lead 明确要求优先写入、小步验证，实现者约 47 秒便完成修改。这说明前次并非完全缺乏实现能力，而是计算、保存、验证的优先级和预算使用不合理。

适合 agent 的改进是给 Lead 返回候选哈希变化、已保存修改、复核可复用范围和剩余阻塞，让它决定继续实现、检查既有版本或收尾。不能一律规定“无文件变更就失败”：有些复核发现本来就是误报，或者只需新增证据。

### 4.3 第二次返工后：F1 已解决，F2 是新的真实缺陷

腿修复为身体锚定的双段结构，用 25 个角度采样值驱动。该轮测试者首次明确提出、复核者随后确认：云副本 x 方向相隔 400，但 y 在 86 与 128 之间交替；实际图案的重复间隔因此是 800，动画却在位移 400 时回到起点，形成接缝跳变。

第三次返工把副本统一到同一高度并更新相关注释，3 次定点编辑形成最终文件。不能把“又发现一个问题”简单视为复核者故意加码；这个 F2 有明确的周期不一致证据。

### 4.4 中断恢复：工具中断、子代理终止、任务结束是三个状态

主轮中断时，第三次返工并没有整体撤销。云修复已完成，测试者也完成了运动学部分；复核者随后继续运行并错误退出。Lead 恢复后先查状态是对的。

但 continue 是一条新 user message，当前源码直接用最近的用户消息 ID 和内容哈希生成 binding。它没有表达“这是对同一任务的继续”这一语义判断，因而 pwsh 被新 TEAM_REQUIRED 拦住。再启动新团队时，旧条目又触发 RUN_PENDING。主代理先接管旧候选、结清旧测试者，然后才启动新队。

当前源码提供的 amendBinding 还要求旧任务已 settled，而且现有说明面向真实的需求变更；不宜声称 Lead 只要随手调用 amendment 就一定能合法解决 continue。这里需要明确的任务继续/修改/新建关系，由 agent 根据可信用户指令判断并提出绑定，运行时验证来源、作用域和不能跳过未决状态。不能靠写死 continue、继续、go on 等字符串解决。

### 4.5 新验证队：先验证测量方法，才谈动画是否失败

Lead 给出按 --virtual-time-budget 截图、比较同一时间与跨周期像素的具体配方。新测试者发现，相同 t600 的两次原始截图实际相差 10,464 个像素，其中上半区 3,693、云区域 542。此时不能把“重复截图不同”直接定性为动画不稳定：启动、载入和动画计时未被精确对齐。

测试者/复核者改用暂停 SMIL、设置明确相位、暂停 CSS 的渲染工具，得到受控相位帧。这个调整有价值，但它验证的是固定相位下的渲染和周期位置关系；不等于已经执行并观看了自然连续播放的每一帧。

通用机制应将用户要的性质与代理选择的测量配方分开。测量配方的重复性失败时，允许 agent 校准/更换方法并解释覆盖范围；不必通过重做产物来“修复”测量工具。

### 4.6 证据已经算出来，却没被读成结论

复核者的 analysisA.json 生成成功，大小 65,728 字节。Windows PowerShell 重定向产生 UTF-16LE 编码，通用 read 或按 UTF-8/Node 默认方式读取造成障碍。报告补全子代理修好了编码判断并得到顶层键，但获取具体数值前又被 final_only 禁止工具。

Lead 后来成功读出了数值，所以这不是证据从未生成，也不是只能重跑实现团队。它是工具输出编码与读回适配、报告闭环和预算阶段安排共同造成的失败。与其要求模型不断重新发明读文件方法，harness 可以提供明确编码、JSON 状态、简洁的机器可读摘要和分页引用；agent 仍负责判断数值说明什么。

另外，两份下游报告把“同样的 PNG 文件大小”写成确定性/逐字节相同，是过强推断。真正支持可重复性的证据是 Lead 后来读到的 0 像素差，不能用前面的文件大小论证替代。

### 4.7 预算：提前停车，多数时候不是把额度花成零

16 位子代理中，12 位可见 final_only/预算收尾状态。首实现者结束仍剩 241,326 token；新测试者剩 179,632；新复核者剩 211,353；报告补全最后剩 68,145。写成“全部预算已耗尽”会误导排查。

当前代码会预留下一步输入、最终报告输入、估计安全余量，以及可能的被拒工具尝试后的报告空间；当这些无法同时容纳时，工具通道关闭。长历史让“再做一次小读回”也需要重付大段上下文输入，故剩余几万 token 未必能容纳完整下一轮。硬预算保护本身有必要，问题是代理到收尾前还没完成最小证据闭环，且收尾模式下仍尝试工具，进一步消耗输入。

第 12 位复核者尤其不能叫 zero-call：它已经有 4 次明确 usage 调用，再在第 5 步失败。Lead 的“admission/zero-call”类描述不能取代原始调用记录。

其异常还涉及 325,013 token 的未知用量预留：可见实际 usage 为 251,680，但控制面 committed 为 576,693，剩余仅 23,307。最后一步请求估算需要 89,619，因无法预留而拒绝。不能说它实际花掉了 576,693，也不能随意释放未知占用来绕过预算；需要带调用身份的结算/恢复证据。修复时进一步核对原生 attempt：子代理 98f6 的 L29 记录 TRANSPORT 失败且没有 usage，L30–32 随后重试。这解释了比成功响应多一笔的未知占用；它不是第 5 步请求被拒的费用。没有供应商最终用量，仍不能将这笔预留计作实耗或直接清零。

方向应是提前暴露可用预算与下一步预估，提示代理优先保存和读取关键证据，缩短控制面返回，支持在原授权余量内携带紧凑上下文继续。不能简单把预算限制去掉，也不能用固定步数强制所有任务按同一种顺序结束。

### 4.8 上下文膨胀与观测盲区

主代理单步 token 从约 14.9K 增长至约 256.6K。后期只读键名、处理条目或呈现文件，也会再次携带庞大的历史。第二个正式团队开始到结束，主代理可核算 3,519,865 token，子代理 13–16 为 2,620,180，合计 6,140,045，约占全团队 45.5%；此时交付文件已经不再修改。这段包含有用的浏览器补证，不能全部叫浪费，但成本确实集中在验证和控制面收尾。

ZIP 中有 6 个大型工具结果出现宿主 spill 截断，省略字节分别为 12,102、22,645、54,958、2,389、26,123、105,629。最后一次仅“补全报告”的返回就省略超过 100KB。一些返回已不是完整可解析 JSON；这影响代理准确区分当前状态、进度文本、最终报告和完整诊断。

更适合的接口是短而稳定的状态摘要、当前候选/版本、当前决定、缺失证据、可执行操作及明确分页引用，把完整历史按需展开。这里的结构可以确定，具体选择哪一步仍由 agent 判断。

## 6. 机制与实现问题如何分层

| 层面 | 本次证据 | 优先改进方向（建议，未实施） |
|---|---|---|
| 产物实现/代理验证 | 腿 SVG 层级与自测公式不一致；云图案实际周期错误 | 要求测试绑定真实产物/执行路径，先验证测量方法，再判断产品 |
| 任务身份机制 | continue 新消息产生新 binding；普通工具被拦；结清旧条目后新开整队 | 给 agent 明确的继续/修订/新任务决策接口，运行时验证可信来源与状态迁移 |
| 返工调度机制 | 返工 1 未写字节却继续两位下游 | 暴露候选变化和可复用证据，由 Lead 判断下一个角色及范围 |
| 工具与宿主适配 | 无图像能力仍调用 read_image；JSON 编码导致结果读不回 | 提供模型能力、明确编码和结构化小结果；失败信息随候选/任务继承 |
| 预算与上下文 | 提前 final_only、反复尝试被禁工具、长回执重复入上下文 | 进度感知的预算提示、紧凑交接、稳定分页结果；保留硬授权上限 |
| 验收证据表达 | 两次合法 Lead 接管；部分像素/几何结论仍可能外推 | 分别记录证据生产者、判定者、方法覆盖、未验证项；接管对用户透明 |
| 可观测性 | UI 5.2M 为 Lead；工具 spill 缺段；没有最后完整状态快照 | 同时展示主代理与全团队用量；短状态摘要和最后完成事实投影 |

优先处理任务连续性、无新候选时的调度判断、证据读回和上下文膨胀，再调优预算收尾。单纯增加 token 或增加更多角色，会延长相同循环。通用 harness 负责可信状态、能力、预算、证据与操作边界；任务如何拆、采用什么验证法、是否需要再改，继续交给 agent 判断。
