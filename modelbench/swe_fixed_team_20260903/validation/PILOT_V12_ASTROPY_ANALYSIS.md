## 2. 判定：装配 CM 的外部效度

1. **A2 vs A3 = 装配无独立贡献（第二个任务复现）。** 通过率同 3/3；成本差在两个任务上方向不一致且幅度都在噪声内（sphinx：A3 省 3.1%；astropy：A2 省 2.5%）；worker input 差 11%（133.5k vs 150.4k，3 rep 噪声内，方向可解释为装配包给了起点信息但不足以宣称效应）；CM 调用同量级（4.3 vs 3.3）。**与 v10 合并：在"一难一易"两个任务上，装配三件套对通过率与成本均无独立贡献——"降级为可选组件（默认 off、按臂开启）"的结论置信度提升，可写进 LIMITS。**
2. **"上下文瓶颈任务"假设落空，且教训有方法论价值。** 事前代理（问题陈述长 + repo 大）没有预测到实际上下文压力：astropy 上 solo 从容通过（Lead input 仅 238–311k，sphinx 为 432k）、CM 池最高用到 7/12 且零拒绝、零 token 死亡。原因：问题陈述里直接给出了复现脚本与期望行为——**长陈述自带先验，反而降低探索需求；真正的上下文瓶颈（sphinx-8035）陈述仅 725 字符但定位路径长**。"陈述长度"是反向或无关代理，"定位路径长度"才是正解且难以事前观测。后续选任务应改用本实验自身的无偏信号（如同配置早期 run 的 worker input 分布）或官方公开通过率等外部证据。
3. **团队协议的价值是条件性的，不是无条件的。** sphinx（难）：solo 0/3 全死于 token 准入，团队 3/3——协议救场；astropy（易）：solo 3/3 且最省（333k vs 团队 ~400k，省 ~17%），团队零通过率增益、纯付成本。**"何时组队"本身成为决策变量**——这正面支持 DPswarm "由 Lead 判断任务难度再组队"的设计方向（当前实验是协议强制组队，无法测试该判断）。
4. **team_execution_valid 与 worker 收尾在易任务上 100% 正常**（6/6 run 全 True、12/12 worker completed）——v10/v11 观察到的收尾随机性是任务难度相关的，不是协议的固有缺陷。
