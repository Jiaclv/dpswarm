# rev11 修复计划：压缩宵禁 + 交付保底（2026-09-04）

依据：`validation/TRAJECTORY_FORENSICS_20260904.md`（五路轨迹法医学，全部有事件级证据）。
原则：每项改动对应一条同题对照证据；全部机制开关走 `LIMITS`/`limits_override`，默认 ON 但可单臂关闭做消融；旧批工件不受影响（审计读工件不读 runner 行为），rev11 只影响新批次。

## 改动清单（五项，全在 `runner.py`，审计侧一处）

### F1 压缩宵禁（edit-phase curfew）——证据最强，排第一
- **证据**：v13 同题同预算对照——池 6（压缩止于第 9 步）2/2 通过，池 24（压缩全程侵入）0/2 空补丁；v8 的 `cm_skipped("low remaining call budget")` 隐性护盾解释了 v8✅→v10❌ 翻转。赢家 27–31% token 在实现期，空补丁 run 实现期 = 0。
- **改动**：新增 per-agent `edit_detected` 标志。检测点 = 工具批次执行处（`loop()` 内 tool 调用分发，约 `runner.py:660-697`）：用保守正则分类每条 bash 命令文本（`write_text`、`open(..., 'w')`、`sed -i`、`cat >`、`>>`、`git apply`、`apply_patch`、`tee ` 等），首个命中即置位并发 `worktree_edit_detected` 事件（带匹配模式与 call_id；漏检 fail-open = 旧行为，可接受）。在 `_maybe_compress_context`（`runner.py:349`）的早退段加：若该 agent `edit_detected` 为真 → 发 `cm_skipped(trigger_role, reason='edit_phase_curfew')` 并 return（复用现有 cm_skipped 事件类型）。
- **开关**：`LIMITS['cm_edit_curfew'] = True`。lead 与 worker 统一适用。

### F2 CM 输出截断修复
- **证据**：56/85 次 CM 调用 `stop_reason=length`，截掉的恰是"未决问题/下一动作"尾部。
- **改动**：`runner.py:45` `'cm_max_tokens': 2048` → `4096`。`AssemblerBrief(token_budget=2000)`（:398）不动（摘要目标长度不变，只摘掉 API 硬顶）。

### F3 LEAD_RESERVE 豁免 closing call
- **证据**：v11 deepseek 的收尾调用被 `closing_call_not_admitted [LEAD_RESERVE]` 拒绝（修复没交付）；v11-he1 的 Lead 全程 0 次 review——reserve 保护的方向与实际死因相反。
- **改动**：`_call`（:313）加 `closing=False` 形参；`remaining_calls <= lead_reserve_calls` 的拒绝分支在 `closing=True` 时跳过。`_closing_call`（:702）调用处传 `closing=True`，并更新其 docstring 中"It never bypasses … Lead reserve"的过时表述。

### F4 交付保底与失败阶段机器可读标记
- **证据**：8 个失败 run = 6 没写出 / 2 写出未交付 / 0 交付未合入；v11-he1 双份有效 delta（2,597B+3,878B）被 `worker_cleanup_discarded` 物理丢弃仍判空补丁；法医学靠人工读盘还原，审计不可见。
- **改动**（runner.py）：
  - `worker_cleanup_discarded` 事件（:930）加 `delta_bytes`（worker delta.patch 已先于 cleanup 落盘，:849-850，读文件大小即可）。
  - `patch_frozen` 事件（:935）加 `patch_bytes`、`lead_edit_detected`、`lead_first_edit_ordinal`。
  - run 结果字典（:997 附近）每个 worker 加 `death_phase`：`adopted | delivered_not_adopted | edited_no_delivery | no_edit`（由 finish 状态 + review 决策 + delta_bytes 确定性推导）；run 级加 `lead_death_phase`：`edited | no_edit`。
- **改动**（audit_results.py）：per-run 增加 `delivery_forensics` 块（上述字段 + cm_skipped 计数），旧批缺字段置 null、不报错。

### F5 探索→编码推进提示
- **证据**：6/8 失败是"从没开始写"；探索-编码转换没有任何 deadline 约束。
- **改动**：runtime status banner（:626-633）在该 agent 零编辑且 token 已耗 >50% 时追加中性字段（如 `'edit_status': 'no edits yet'`）。只陈述预算与编辑状态事实，不给方案性提示（不影响评分公平）。
