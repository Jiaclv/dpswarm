# Matplotlib worker 调用预算与完成状态：事后有界分析

结论：四名 GLM/Flash worker 都交出了非空 delta，但最后一轮只调用 bash，没有调用 finish；硬性 8 轮上限随后将其标记为 `local_call_limit`，并按生命周期规则阻止正式 adopt。这不等于四份补丁均无价值或均错误。另一方面，不能把它们全部解释成“只差一个无关紧要的完成标记”：部分测试 worker 的末段测试仍有失败/错误，单份 patch 的正确性没有被独立官方评分。

**首先纠正预算可见性。** 实际冻结 system prompt 明确写明 worker 至多 8 次调用，并要求显式 finish；每轮状态又提供 `local_call` 和 `local_limit`。四名 GLM/Flash worker 最后一次真实 native wire request 均为 **8 / 8**。没有单独名为 `local_remaining` 的字段，但已有等价的本轮序号/上限信息，不能称为隐藏本地预算。它们最后一轮开始时全队还分别剩 **12、9、16、5** 次调用，墙钟余量均超过 1,200 秒；此次终止不是全队 token/调用数或墙钟耗尽。见 [静态worker预算说明](<K:/秋招/项目/DPswarm/modelbench/swe_fixed_team_20260903/pilot_v2/source_snapshot/modelbench/swe_fixed_team_20260903/runner.py:199>)、[逐轮本地计数与全局预算banner](<K:/秋招/项目/DPswarm/modelbench/swe_fixed_team_20260903/pilot_v2/source_snapshot/modelbench/swe_fixed_team_20260903/runner.py:287>)。

**机械约束的确存在，边界也很明确。** worker 循环最多执行 8 次采样；一个回合内的全部工具执行并写入反馈后，只有成功执行 finish 才返回对应状态，否则第 8 回合之后直接 `local_call_limit`。没有第 9 次专用收尾采样，也没有给 worker 单独预留 finish 回合；源码中的剩余 2 次全局调用预留是给 Lead 集成使用。四名 GLM/Flash worker 的第 8 回合已经选择 bash，因此无法再由第 9 回合阅读这次 bash 的新反馈并决定 finish；但 finish 在此前以及第 8 回合始终是合法工具，并非无论模型如何选择都会被阻止完成。两名 Sol worker 分别在第 4、6 回合主动调用 finish，获得 completed。见 [Lead专用预留](<K:/秋招/项目/DPswarm/modelbench/swe_fixed_team_20260903/pilot_v2/source_snapshot/modelbench/swe_fixed_team_20260903/runner.py:248>)、[执行finish及8轮后终止](<K:/秋招/项目/DPswarm/modelbench/swe_fixed_team_20260903/pilot_v2/source_snapshot/modelbench/swe_fixed_team_20260903/runner.py:336>)。

**delta 证据限制“无有用补丁”的解释。** 两个 GLM/Flash implementation worker 的 delta SHA-256 完全相同：`d90258463035a063dbabb8e861cfcd2f9ddd84f94bff5bd81fd920e8cc34cf28`，都只修改 mlab.py 的两条窗口归一化表达式。两个测试 worker 也都有 test_mlab.py 的非空变更，且文件哈希均与 delivery/result 匹配。两个测试 worker 的最终 delta 仅包含测试文件修改，不能假定自动获得了另一 worker 的生产修复；若在未修生产基线上运行，测试失败也可能是预期的回归测试行为；本次仅末两轮检查不足以将所有失败判为无效测试，也不足以证明整份测试 delta 可直接采纳。Sol 两份 delta 同样各为生产文件/测试文件的独立修改，但其 completed 是显式完成工具触发的生命周期状态，不是对各自 delta 的独立正确性认证。
