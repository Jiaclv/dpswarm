# 迷你记账字段参考手册

**版本**：v1.0
**适用范围**：迷你记账（MiniLedger）交易记录数据模型
**目标读者**：前后端开发工程师、测试工程师、数据运维人员

---

## 前言

本手册是迷你记账系统中交易记录（Transaction）核心数据字段的唯一权威参考文档。系统当前版本定义了四个核心字段：`id`、`amount`、`currency`、`tags`。每个字段按照统一结构，从「定义」「类型」「约束」「示例」「常见错误」五个维度进行完整描述，旨在为开发、测试、数据迁移与运维工作提供一致的判定依据，降低因字段理解不一致而引发的数据缺陷。

阅读约定如下：

1. 文中「必须」「不得」「禁止」为强制性要求，违反即视为数据非法；「建议」「推荐」为最佳实践，不强制。
2. 所有示例均以 JSON 片段呈现，字段名与实际存储层保持一致。
3. 「常见错误」小节中给出的错误码为系统标准返回码，测试用例应与其对齐。
4. 本手册正文之后附有一行完整性校验和（CHECKSUM），用于确认文档在分发与存储过程中未被篡改或截断。任何使用方在引用本手册前，应先核对该校验和。

## 第一章 id 字段

### 1.1 定义

`id` 是交易记录的全局唯一标识符，用于在系统全生命周期内无歧义地定位一条交易记录。它是整条记录的主键，贯穿创建、查询、更新、删除、对账、审计等所有环节。一旦分配，任何情况下都不得变更或复用——即使记录被逻辑删除，其 `id` 也永久保留在归档存储中，不会被重新分配给新记录。

`id` 在业务上承担三重职责：其一，作为数据库主键与索引键，支撑点查询性能；其二，作为跨系统对账与幂等控制的关联键，外部回调、重试请求均凭 `id` 判重；其三，作为审计日志中的引用标识，保证任意操作可追溯到具体记录。

### 1.2 类型

- 存储层：定长字符串（CHAR(26)），采用 ULID（Universally Unique Lexicographically Sortable Identifier）格式。
- 应用层：JSON 中的 `string` 类型。
- 结构说明：ULID 共 26 个字符，由两部分组成——前 10 个字符为 48 位毫秒级时间戳的 Crockford Base32 编码，后 16 个字符为 80 位随机数的 Crockford Base32 编码。字符集为 `0123456789ABCDEFGHJKMNPQRSTVWXYZ`（不含 I、L、O、U 四个易混淆字母）。

选择 ULID 而非自增整数或纯 UUIDv4 的原因：与自增整数相比，ULID 支持多节点无协调生成，不存在分布式发号瓶颈；与 UUIDv4 相比，ULID 按时间字典序递增，作为 B+ 树主键索引时写入局部性好，避免页分裂，且天然携带创建时间信息。

### 1.3 约束

1. **必填性**：创建记录时 `id` 必须存在且非空；服务端负责生成，客户端请求体中若携带 `id`，服务端必须忽略并以服务端生成的值为准。
2. **唯一性**：全表唯一，含逻辑删除记录在内不得重复。
3. **格式**：必须恰好为 26 个字符，字符集限定为 Crockford Base32 的 32 个合法字符，不得出现小写字母之外的非法字符；系统在读取时统一按大写处理，写入时必须存储为大写。
4. **不可变性**：创建后任何接口不得修改 `id`。
5. **时间成分校验**：前 10 字符解码后的时间戳不得晚于服务器当前时间加 60 秒钟偏移容限，不得早于系统上线日（2024-01-01T00:00:00Z）。
6. **索引要求**：作为聚簇主键存储；对账归档表中需另建唯一二级索引。

### 1.4 示例

合法示例：

```json
{ "id": "01J9XQ4T8ZC5K2M7B3V9N6R1PW" }
```

该 id 前 10 位 `01J9XQ4T8Z` 解码为某毫秒级时间戳，后 16 位为随机部分，长度与字符集均合法。

批量场景下的时序示例（按创建先后排列，字典序严格递增）：

```
01J9XQ4T8ZC5K2M7B3V9N6R1PW
01J9XQ4T90A2F5H8J3L6M9P2S5W
01J9XQ4T91B7C4D9E2F5G8H1J4M
```

非法示例及原因：

```json
{ "id": "01j9xq4t8zc5k2m7b3v9n6rpw" }   // 含小写，写入前未规范化为大写
{ "id": "01J9XQ4T8ZC5K2M7B3V9N6R" }     // 仅 24 字符，长度不足
{ "id": "01J9XO4T8ZC5K2M7B3V9N6R1PW" }  // 含非法字符 O（Crockford Base32 排除）
{ "id": null }                           // 缺失，违反必填性
```

### 1.5 常见错误

1. **大小写混用**：客户端生成或中转环节将 ULID 转为小写，导致唯一索引比对失败，报错 `ERR_ID_FORMAT`（E1001）。预防措施：所有入口统一执行 `toUpperCase()` 后再校验。
2. **易混淆字符未解码**：用户手工录入时把 `I` 输成 `1`、`O` 输成 `0`。查询侧建议启用宽松解码（将 I/L→1、O→0 映射后再匹配），但写入侧严格禁止此类字符，报错 `ERR_ID_CHARSET`（E1002）。
3. **客户端抢先生成 id 并信任**：客户端携带自定义 id 且后续逻辑直接使用，与服务端实际落库值不一致，引发「幽灵引用」。规范要求客户端永远以响应中的 id 为准。
4. **时钟回拨导致时间成分异常**：NTP 回拨后生成的 ULID 时间戳早于已有记录，破坏字典序递增假设。生成器必须实现单调性保障（同一毫秒内递增随机部分，回拨时挂起等待），否则报 `ERR_ID_MONOTONIC`（E1003）。
5. **归档后 id 复用**：某些迁移脚本清理软删除记录后重新发号，导致历史审计日志指向错误记录。规范明确：id 永不复用，审计归档表必须保留全部 id。
6. **误将 id 当作业务时间**：虽有时间成分，但它是生成时刻而非交易发生时刻，业务时间应使用独立的 `occurredAt` 字段（不在本手册四个核心字段范围内，此处仅作提示，防止误用）。

## 第二章 amount 字段

### 2.1 定义

`amount` 是交易的金额字段，表示本条交易记录涉及的货币数量。其符号约定为：支出（资金流出）记为负数，收入（资金流入）记为正数，转账类记录在双方各自生成方向相反的记录。金额恒以「货币的最小单位」（即最小可分单位，如人民币的分、日元的圆）的整数倍表示的十进制数值存储，配合 `currency` 字段确定实际价值。

`amount` 是记账系统中最核心、也是历史上出错代价最高的字段。它的正确性直接决定账户余额、报表汇总与对账结果。因此本字段的所有约束均为强制性，任何环节不得为便利而放宽。

### 2.2 类型

- 存储层：`DECIMAL(19,4)`，即整数部分最多 15 位、小数部分固定 4 位。不使用任何浮点类型（FLOAT/DOUBLE）。
- 应用层：JSON 中序列化为 `string`（推荐，见下述说明）或数值字面量。
- 语言层约定：服务端内部一律使用任意精度十进制类型（如 Java `BigDecimal`、Python `Decimal`、Go `decimal` 库）参与运算，禁止使用二进制浮点数做任何金额运算。

选择 `DECIMAL(19,4)` 的理由：4 位小数可覆盖全部 ISO 4217 现行货币（最多 4 位小数，如科威特第纳尔 KWD、突尼斯第纳尔 TND）以及多数加密资产的记账需求；19 位总精度保证最大绝对值约 10^15 个最小单位，远超单账户现实业务量。JSON 层推荐序列化为字符串，是为了规避 JavaScript `Number` 的 IEEE 754 双精度截断问题——超过 2^53 的整数或高精度小数经 `JSON.parse` 后会静默失真。

### 2.3 约束

1. **必填性**：`amount` 必须存在，不得为 null、缺失或空字符串。
2. **精度**：小数位数不得超过 `currency` 字段定义的该货币小数位数（exponent）；多于部分必须拒绝而非静默舍入。例如 CNY（2 位小数）下 `10.999` 非法，`10.99` 合法。
3. **取值范围**：绝对值必须大于 0（`0` 与 `0.00` 均非法，零额交易应被上游拦截）；绝对值上限为 999,999,999,999,999.9999（15 位整数 + 4 位小数）。
4. **符号语义**：支出为负、收入为正，符号由业务方向决定，录入侧不得通过额外布尔字段重复表达方向后再取绝对值，防止符号与方向字段矛盾。
5. **格式规范**：字符串形式不得包含千分位分隔符、货币符号、空格或全角字符；负号只允许出现在最前端且只有一个；小数点为半角 `.`。
6. **禁止科学计数法**：`1.5e3`、`-2E-2` 等形式一律拒绝。
7. **运算安全**：任何汇总、拆分、汇率换算必须在十进制类型下进行；金额拆分（如分摊）若不能整除，尾差处理规则必须显式声明并保证各分项之和等于原额。

### 2.4 示例

合法示例：

```json
{ "amount": "-128.50", "currency": "CNY" }   // 支出 128 元 5 角
{ "amount": "3500",     "currency": "CNY" }   // 收入 3500 元，可省略小数部分
{ "amount": "-0.05",    "currency": "CNY" }   // 最小非零金额
{ "amount": "12.345",   "currency": "KWD" }   // KWD 为 3 位小数货币，合法
```

非法示例及原因：

```json
{ "amount": 128.501,  "currency": "CNY" }  // 小数 3 位，超出 CNY 的 2 位限制
{ "amount": "1,280.00", "currency": "CNY" } // 含千分位逗号
{ "amount": "¥128.00",  "currency": "CNY" } // 含货币符号
{ "amount": "0.00",   "currency": "CNY" }  // 零额，非法
{ "amount": "1.5e2",  "currency": "CNY" }  // 科学计数法
{ "amount": null }                          // 缺失
```

### 2.5 常见错误

1. **二进制浮点污染**：前端用 JavaScript `Number` 累加金额后回传，出现 `0.1 + 0.2 = 0.30000000000000004` 类失真，落库精度校验失败，报 `ERR_AMOUNT_PRECISION`（E2001）。对策：前端亦应以字符串或整数（最小单位）处理金额。
2. **隐式舍入**：服务端在入库前对超精度金额做 `round()` 而非拒绝，导致用户看到的金额与入账金额相差分位，引发客诉。规范要求：超精度即报 `ERR_AMOUNT_SCALE`（E2002），把修正权交还用户。
3. **符号与方向字段打架**：记录同时含 `amount=-50` 与 `type=income`，汇总逻辑取不同侧导致余额虚减。校验器必须在写入前做一致性断言。
4. **千分位与全角字符混入**：移动端输入框未过滤全角句点「．」或用户粘贴带格式的文本，报 `ERR_AMOUNT_FORMAT`（E2003）。输入层应白名单过滤 `[0-9.\-]`。
5. **汇总溢出与尾差**：大账期汇总时误用 32 位整数承载最小单位计数导致溢出；拆分场景尾差塞入最后一笔导致单笔金额与用户感知不符。对策：汇总用 64 位及以上；尾差按明确规则（如「首笔吸收」）并展示分摊明细。
6. **跨币种直接相加**：未做汇率折算就把不同 `currency` 的 amount 相加，报表数值错误。任何聚合必须先统一币种并在记录中保留折算依据。

## 第三章 currency 字段

### 3.1 定义

`currency` 是交易金额的计价货币代码，采用 ISO 4217 三字母字母代码表示，与 `amount` 联合确定金额的真实价值。迷你记账支持全部 ISO 4217 现行货币代码以及代码 `XXX`（表示「无货币」场景，本系统中仅限内部清算占位记录使用，禁止用于用户可见交易）。

`currency` 决定三件事：金额的合法小数位数（exponent）、展示时的符号与格式、以及跨币种汇总时的折算路径。它与 `amount` 构成不可分割的语义对——脱离币种谈金额是本系统明令禁止的做法。

### 3.2 类型

- 存储层：`CHAR(3)`，存储 ISO 4217 字母代码（alphabetic code），大写。
- 应用层：JSON 中的 `string` 类型。
- 代码结构：前两位为 ISO 3166-1 国家/地区代码，第三位通常为货币名称首字母（如 CNY 中国人民币、JPY 日本日元、USD 美国美元、EUR 欧元为特例）。
- 附带元数据：系统维护一张货币参照表，每行包含代码、英文名、中文名、小数位数（exponent，取值 0/2/3/4）、是否活跃。参照表随版本发布冻结快照，运行期只读。

### 3.3 约束

1. **必填性**：`currency` 必须存在且非空，不存在「无币种金额」。
2. **格式**：恰好 3 个大写拉丁字母 A–Z，不得含数字、符号或空白；读取时统一大写规范化后再校验。
3. **参照表校验**：必须命中货币参照表中的活跃代码；已退市代码（如已被克罗地亚欧元替代的 HRK）按版本策略拒绝或告警。
4. **与 amount 的一致性**：`amount` 的小数位数不得超过参照表中该货币的 exponent；例如 JPY（exponent=0）下 `amount="100.5"` 非法。
5. **不可变性**：交易创建后 `currency` 不得修改；如需换币，业务上应作废旧记录并新建，保留完整轨迹。
6. **禁用代码**：测试专用代码 `XTS` 仅限测试环境；`XXX` 仅限内部清算占位；两者在生产环境用户交易中必须拒绝，报 `ERR_CURRENCY_FORBIDDEN`（E3004）。
7. **批量一致性**：一次批量导入中若含多币种，每条记录必须各自携带 currency，不得以文件级默认值静默继承。

### 3.4 示例

合法示例：

```json
{ "amount": "-88.00", "currency": "CNY" }
{ "amount": "-1200",  "currency": "JPY" }    // JPY 零小数位
{ "amount": "9.999",  "currency": "KWD" }    // KWD 三位小数
{ "amount": "25.00",  "currency": "EUR" }
```

非法示例及原因：

```json
{ "amount": "100", "currency": "cny" }      // 未大写（写入侧）
{ "amount": "100", "currency": "C" }        // 长度不足
{ "amount": "100", "currency": "USDT" }     // 4 个字符，非 ISO 4217 法币代码
{ "amount": "100", "currency": "XTS" }      // 测试代码，生产环境禁止
{ "amount": "10.5", "currency": "JPY" }     // JPY 零小数位，10.5 超精度
{ "amount": "100", "currency": "ZZZ" }      // 不在参照表中
```

### 3.5 常见错误

1. **小写未规范化**：第三方回调传小写代码，直接与索引比对失败，报 `ERR_CURRENCY_FORMAT`（E3001）。规范：入口统一 `toUpperCase()`。
2. **把加密货币代码当法币录入**：如 BTC、USDT 不是 ISO 4217 代码，参照表校验失败，报 `ERR_CURRENCY_UNKNOWN`（E3002）。若业务未来支持数字资产，须扩展参照表而非绕过校验。
3. **exponent 配置错误**：参照表中某货币小数位数维护错误（如把 KWD 配成 2 位），导致跨币种换算后金额系统性偏差。对策：参照表纳入代码评审与回归测试，变更须走审批。
4. **退市货币未随版本更新**：HRK 于 2023 年被欧元取代后仍被接受，后续对账无汇率可查。对策：参照表按版本冻结，退市代码给出宽限期与替代建议。
5. **多币种汇总未折算**：报表直接对原始 amount 求和，把美元、日元、人民币混加成一个无意义数字。规范：汇总必须声明目标币种、使用当日汇率快照并在报表中披露汇率来源与时间。
6. **创建后改币种**：用户「编辑交易」时切换币种但金额未换算，等于把 100 元改成 100 美元。因约束 5 的不可变性，此类请求直接拒绝，报 `ERR_CURRENCY_IMMUTABLE`（E3005）。

## 第四章 tags 字段

### 4.1 定义

`tags` 是交易的标签集合，用于对交易进行多维度、非排他的业务分类与检索标注。与单一「分类」字段不同，`tags` 允许一条交易同时归属多个语义维度，例如一笔「出差聚餐」可同时打上 `餐饮`、`出差`、`团队建设` 三个标签，从而在「按用途统计」与「按项目统计」两个视角下都被正确纳入。

`tags` 的设计原则是「开放但受控」：标签可由用户自建，但必须通过规范化校验与数量上限控制，防止标签爆炸、同义碎片化与注入类安全问题。标签不参与金额与余额计算，仅服务于检索、统计聚合与个性化报表，因此其错误通常不会导致资金风险，但会显著影响统计口径的一致性。

### 4.2 类型

- 存储层：记录表内以 JSON 数组存储；另建标签维表（tag_id 主键、name 唯一索引）与关联表（transaction_id + tag_id 联合唯一），支撑按标签反查与计数。
- 应用层：JSON 中的 `array<string>`，元素为标签名字符串，保持用户录入顺序返回（但语义上集合无序，比较时应做无序比较）。
- 元素约束：单个标签名 1–24 个字符（按 Unicode 码点计），去除首尾空白后不得为空；同一记录内标签名去重后存储（比较在 Unicode NFC 规范化与大小写折叠之后进行）。
- 上限：单条记录最多 10 个标签。

### 4.3 约束

1. **必填性**：`tags` 字段本身必须存在，允许为空数组 `[]`（表示无标签），但不得为 null 或缺失。这一「存在但可空集合」的设计使读取方无需做存在性分支判断。
2. **数量上限**：数组长度 ≤ 10，超出报 `ERR_TAGS_TOO_MANY`（E4001）。
3. **元素规范化**：录入时执行三步处理——去除首尾空白、Unicode NFC 规范化、NFKC 兼容折叠（全角转半角等）——之后校验非空与长度。
4. **去重**：规范化后同一条记录内不得出现重复标签，重复时系统静默去重（不报错），以去重后集合为准。
5. **字符白名单**：标签名不得包含控制字符（U+0000–U+001F、U+007F）、不可见零宽字符（U+200B–U+200F 等）以及任何行终止符；命中报 `ERR_TAGS_INVALID_CHAR`（E4002）。
6. **保留前缀**：以 `sys:` 开头的标签为系统保留命名空间，用户请求创建该前缀标签时报 `ERR_TAGS_RESERVED`（E4003）。
7. **长度与统计**：存储的每个标签名按 UTF-8 编码后不得超过 72 字节，防止维表索引超长。
8. **删除语义**：删除标签采用「解除关联」而非物理删除维表行，历史统计基于关联快照，保证旧报表可复现。

### 4.4 示例

合法示例：

```json
{ "tags": ["餐饮", "出差"] }
{ "tags": [] }                                  // 空集合，合法
{ "tags": ["Coffee", "早餐", "通勤"] }
{ "tags": ["  报销  "] }                         // 录入后规范化为 ["报销"]
{ "tags": ["出差", "餐饮", "出差"] }              // 去重后存储为 ["出差", "餐饮"]
```

非法示例及原因：

```json
{ "tags": null }                                 // 必须为数组，不得为 null
{ "tags": ["餐饮", "餐饮", "餐饮", "餐饮", "餐饮", "餐饮", "餐饮", "餐饮", "餐饮", "餐饮", "餐饮"] }  // 11 个，超上限
{ "tags": ["宴会\n邀请"] }                        // 含换行控制字符
{ "tags": ["sys:auto"] }                         // 保留前缀
{ "tags": ["a"] }                                // 长度为 1 虽合法；此例若为 ""（空串）则非法
{ "tags": "餐饮" }                               // 类型错误：字符串而非数组
```

### 4.5 常见错误

1. **null 与空数组混淆**：部分客户端以 `null` 表示「无标签」，读取方按数组遍历导致空指针，报 `ERR_TAGS_TYPE`（E4004）。规范：无标签一律写 `[]`。
2. **全半角与 NFC 差异导致假性不同标签**：全角「ＣＦＥ」与半角「CFE」、组合变音字符与预组合字符在未规范化的系统里会被当成两个标签，统计口径分裂。对策：严格执行约束 3 的规范化流水线。
3. **零宽字符注入**：恶意或误粘贴的零宽字符使两个视觉相同的标签实际不同，规避审核或分裂统计。白名单校验（约束 5）必须前置。
4. **超上限不报错而静默截断**：早期版本对超过 10 个标签静默保留前 10 个，用户标签无声丢失。现行规范要求显式报错。
5. **按标签统计时未排除已删除交易**：报表联查维表时遗漏 `deleted_at` 过滤，统计结果偏大。标准查询必须带软删除过滤条件。
6. **同义标签碎片化**：`外卖`、`外送`、`takeout` 并存导致分类统计失真。建议提供标签合并工具与推荐标签列表，属产品最佳实践而非强制校验。

## 第五章 字段间联合约束

除各字段自身约束外，四个字段还存在以下联合校验规则，由统一的记录校验器在写入前原子执行，任一失败则整条记录拒绝落库：

1. **金额-币种精度联动**：`amount` 小数位数 ≤ 参照表中 `currency` 的 exponent（见 2.3 约束 2 与 3.3 约束 4，属双字段联动，任一侧变更都需重新校验）。
2. **完整性原子性**：四字段校验顺序为 id → currency → amount → tags，前者通过才校验后者，但落库以全部通过为前提，禁止部分写入。
3. **幂等写入**：相同 `id` 的重复创建请求返回既有记录（幂等语义），不产生重复数据、不覆盖已有 `amount`/`currency`/`tags`。
4. **校验失败错误码汇总**：E1001–E1003（id）、E2001–E2003（amount）、E3001–E3005（currency）、E4001–E4004（tags），测试用例应覆盖全部错误码路径。
