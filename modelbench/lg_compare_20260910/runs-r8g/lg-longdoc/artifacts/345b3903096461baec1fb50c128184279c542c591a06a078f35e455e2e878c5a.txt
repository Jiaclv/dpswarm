# 《迷你记账字段参考手册》

- 文档版本：v2.0（重写修订版）
- 适用范围：迷你记账系统的数据录入、接口对接与数据校验环节
- 字段覆盖：`id`、`amount`、`currency`、`tags` 四个核心字段
- 阅读对象：客户端开发、后端开发、测试工程师、数据录入人员
- 约定说明：本文所有示例中出现的金额、账户标识均为虚构数据，不指向任何真实账户。手册正文按「定义—类型—约束—示例—常见错误」五小节结构逐字段展开，供各岗位在开发、联调、验收时按需查阅。

## 前言与使用说明

迷你记账系统是一套面向个人与小团队的轻量级记账工具，其数据模型围绕「一笔交易记录」展开。每一笔交易记录由四个核心字段共同刻画：`id` 唯一标识一笔交易，`amount` 表达交易的金额数值，`currency` 声明金额所使用的货币单位，`tags` 则为交易提供可自由组合的分类标签。四者缺一不可，任何一个字段录入或传输出错，都会导致记账数据不可用、对账失败或统计失真。

本手册的组织方式非常固定：每个字段一章，每章包含五节——定义、类型、约束、示例、常见错误。定义一节回答「这个字段是什么、为什么存在」；类型一节回答「它在系统内外的数据形态是什么」；约束一节回答「哪些值合法、哪些值非法、边界在哪里」；示例一节给出可直接套用的合法与非法样例；常见错误一节汇总实践中高频出现的错误模式，并给出规避建议。

开发人员在编写序列化与反序列化逻辑时，应重点阅读每个字段的「类型」与「约束」两节；测试人员在设计用例时，应以「约束」与「常见错误」两节为用例来源；录入与运营人员在手工补录数据时，应优先对照「示例」与「常见错误」两节自查。手册末尾附有四字段要点汇总表，可作为快速核对清单使用。文中出现的所有校验规则均为硬性规则，凡违反硬性规则的数据一律视为脏数据，须拒绝入库并回溯修复。

## 1. id 字段

### 1.1 定义

`id` 是一笔交易记录的唯一标识符，用于在整个系统生命周期内无歧义地指向某一条具体的记账数据。它的职责是「身份认定」：无论是客户端本地存储、服务端数据库持久化、接口报文传输，还是导出报表与日志追踪，凡是需要引用某一笔交易的地方，都通过 `id` 来定位。

`id` 一经生成即不可变更。即使交易的其他字段（金额、标签、备注等）后续被修改，`id` 也必须保持原值不变，这是「同一笔交易」这一概念在数据层面的锚点。换句话说，判断两条记录是否指向同一笔交易，唯一依据就是 `id` 是否相同，而不是金额、时间或其他任何业务字段是否相同。

`id` 的设计目标是全局唯一且不可预测。全局唯一保证不同设备、不同批次、不同用户产生的记录不会发生键冲突；不可预测则可以避免外部攻击者通过枚举连续编号推测系统内记录总量与增长速度。因此系统推荐使用基于随机数的第四版 UUID（UUIDv4）作为 `id` 的生成方案，而不推荐使用自增整数或基于时间戳的简单拼接串。

### 1.2 类型

在系统内部与各接口契约中，`id` 的规范类型为**字符串（String）**，具体格式为标准 UUID 字符串，即由连字符 `-` 分隔的 32 个十六进制字符，形如 `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`，整体长度固定为 36 个字符（32 个十六进制位加 4 个连字符）。五个分组的位数依次为 8、4、4、4、12，这是判断一个字符串是否为格式合法 UUID 的第一道检查。

选择字符串而非数值类型，理由有三。其一，UUID 的取值空间为 2^122（扣除版本与变体位），远超任何整数类型的表达范围，字符串是承载它的自然容器；其二，字符串在各语言、各存储引擎、各传输协议中的兼容性最好，无需担心大整数溢出或精度丢失；其三，UUID 天然支持客户端离线生成，多端并发创建记录时无需向服务端申请编号，简化了离线记账场景的实现。

需要注意两点类型边界。第一，虽然 UUID 本质上是 128 位二进制数，但在迷你记账的所有公开接口与存储字段中，它一律以小写十六进制字符串形式出现，禁止以二进制大对象、Base64 编码或整数拆分形式传输。第二，`id` 字段禁止为 `null`、禁止为空字符串、禁止缺省，反序列化时若发现 `id` 缺失，应立即拒绝该条记录并返回校验错误。

### 1.3 约束

`id` 字段需同时满足以下约束，缺一即为非法：

1. **非空约束**：不得为 `null`、`undefined`、空字符串或仅含空白字符的字符串。
2. **格式约束**：必须匹配标准 UUID 格式 `^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$`，五个分组的字符数依次为 8、4、4、4、12，四个连字符位置固定，不得多、不得少、不得移位。
3. **大小写约束**：系统统一使用小写十六进制字符。传入大写字母的 UUID 在入库前必须统一转换为小写，转换后不得改变其指向的记录。
4. **唯一性约束**：在同一数据集（同一用户账本）内，任意两条已存在的记录不得拥有相同的 `id`。写入前须做唯一性检查，检测到重复时应拒绝写入并上报冲突。
5. **不可变约束**：记录创建后，其 `id` 在任何更新操作中都不允许被修改。任何试图通过更新接口改写 `id` 的请求都应被拒绝。
6. **版本约束**：推荐使用 UUIDv4（第三分组以 `4` 开头）。历史数据中允许存在其他版本的 UUID，但新生成的记录一律使用 v4。

### 1.4 示例

合法示例：

```text
id = "3f9c2a7e-8b1d-4c6a-9e2f-5d0b7a1c8e34"
```

该字符串共 36 个字符，五个分组分别为 `3f9c2a7e`（8 位）、`8b1d`（4 位）、`4c6a`（4 位，以 `4` 开头，符合 v4 版本特征）、`9e2f`（4 位）、`5d0b7a1c8e34`（12 位），全部为小写十六进制字符，四条约束全部满足，可直接入库。

另一个合法示例：

```text
id = "9e5f0d3a-2c4b-4a18-b7d6-1e9a3c5f7b21"
```

非法示例与原因对照：

| 非法值 | 违反的约束 | 说明 |
|---|---|---|
| `""` | 非空约束 | 空字符串，无任何身份信息 |
| `"12345"` | 格式约束 | 自增整数风格，长度与格式均不达标 |
| `"3f9c2a7e8b1d4c6a9e2f5d0b7a1c8e34"` | 格式约束 | 缺少 4 个连字符，无法通过格式校验 |
| `"3f9c2a7e-8b1d-4c6a-9e2f-5d0b7a1c8e3"` | 格式约束 | 末组仅 11 位，少一个字符 |
| `"3F9C2A7E-8B1D-4C6A-9E2F-5D0B7A1C8E34"` | 大小写约束 | 大写形式，须转小写后方可入库 |

### 1.5 常见错误

实践中围绕 `id` 的高频错误包括以下几类。

**错误一：自行拼接编号。** 部分开发者为图省事，用「用户 ID + 日期 + 序号」拼接出形如 `u1001-20240501-003` 的标识。这类标识虽可读性好，但既不符合 UUID 格式约束，又在多端并发时极易重复。正确做法是调用标准 UUIDv4 生成库，而不是手写拼接逻辑。

**错误二：重复使用 `id`。** 复制一条记录再修改金额后重新入库，却忘了生成新的 `id`，导致两条不同交易共享同一标识，后续按 `id` 查询、更新、删除时行为不可预测。复制记录的所有场景都必须强制重新生成 `id`。

**错误三：更新时改写 `id`。** 前端在编辑表单中把 `id` 一并放入可编辑控件，用户误改后提交，造成「改了一个字段却换了身份」的隐蔽事故。编辑接口应将 `id` 列为只读，更新逻辑中发现 `id` 与库中原值不符时直接拒绝。

**错误四：大小写混用导致查重失效。** 同一 UUID 以大写形式重复写入，因字符串比较区分大小写而绕过了唯一性检查。入库前统一转小写，并在唯一性索引上按小写值建索引，可彻底规避。

**错误五：连字符缺失或错位。** 手工录入或从外部系统粘贴时丢失连字符，或分组位数抄错（例如首组写成 7 位或 9 位）。录入工具应提供格式实时校验，粘贴后立即高亮格式问题。

**错误六：用 `id` 承载业务含义。** 有人试图从 `id` 中解析出日期或用户信息。UUIDv4 是随机值，不含任何业务语义，任何基于 `id` 反推业务信息的逻辑都是错误的。

## 2. amount 字段

### 2.1 定义

`amount` 表示一笔交易的金额数值，是记账系统的核心业务字段。它的符号约定为：收入记为正数，支出记为负数，零金额交易（如赠品入库、待定交易占位）记为 `0`。这一符号约定贯穿全系统的统计口径——账户余额等于其名下所有交易 `amount` 的代数和，月度收支报表的正负号也直接来源于此。

`amount` 与 `currency` 是强绑定的成对字段：金额数值本身没有意义，必须与货币单位组合才构成完整的金额表达。`12.50` 只有在声明了 `currency = "CNY"` 之后，才是一笔完整的记账金额。因此系统规定，任何一笔交易记录中 `amount` 与 `currency` 必须同时存在、同时校验，只写其一即为非法记录。

需要特别强调 `amount` 的精度语义。记账场景对精度极为敏感，一分钱的偏差在对账时都会被放大为账目不平。因此 `amount` 绝不允许使用二进制浮点类型（如多数语言中的 `double`/`float`）进行运算与存储——`0.1 + 0.2 !== 0.3` 这类浮点误差在逐笔累加后会累积成肉眼可见的账目差错。系统全链路要求以十进制精确运算（整数的最小货币单位、或语言内置的 decimal 类型）处理金额。

### 2.2 类型

在存储与传输层面，`amount` 的规范类型为**十进制定点数（Decimal）**。具体实现方式因层面而异：

- **存储层**：数据库字段类型使用 `DECIMAL(18, 4)`，即总共 18 位有效数字、其中 4 位小数。整数部分最多 14 位，足以表达 99 万亿级别的累计金额；4 位小数则兼容少数使用千分之一货币单位（如巴林的费尔）结算的场景，并为汇率折算预留精度。
- **传输层**：接口报文中 `amount` 以**字符串形式**的十进制数表达，例如 `"amount": "-45.80"`。用字符串而非 JSON number 传输，是为了绕开各语言 JSON 解析器对浮点数的默认处理，避免在解析瞬间就引入精度损失。
- **运算层**：任何涉及金额的加、减、乘、除运算，必须使用语言的 decimal 库（如 Java 的 `BigDecimal`、Python 的 `decimal.Decimal`），禁止使用二进制浮点运算后再四舍五入。

数值的合法形态为普通十进制记数法，可带正负号、可带小数点，不允许使用科学计数法（如 `1.2E3`）、千分位分隔符（如 `1,234.50`）、货币符号（如 `￥45.80`）或空白字符。全系统的小数位上限为 4 位，超出部分不接受舍入，直接判定为非法值。

### 2.3 约束

`amount` 字段需满足以下硬性约束：

1. **非空约束**：不得缺省、不得为 `null`，也不得为空字符串。
2. **数值约束**：必须是可被十进制定点数完整表达的数值，正数、负数、零均合法；禁止 `NaN`、无穷大、科学计数法。
3. **精度约束**：小数位数不得超过 4 位。`-45.80`、`0.0005` 合法；`3.14159` 非法，且不得以「四舍五入到 4 位」的方式自动修复——必须由调用方自行决定业务舍入后再提交。
4. **量级约束**：单笔金额的绝对值不得超过 `99999999999999.9999`（整数 14 位 + 小数 4 位），超出即为溢出，拒绝入库。
5. **符号语义约束**：收入为正、支出为负。录入方向（收入/支出）与符号不一致的记录，统计结果将反向，故前端录入与后端校验须双重核对方向与符号的对应关系。
6. **格式约束**：不得携带货币符号、千分位逗号、空格或前后导空白；整数部分的前导零只允许保留一个（`007.50` 非法，`7.50` 合法）。

### 2.4 示例

合法示例：

```text
amount = "-45.80"    // 支出 45.80 元（负号表示支出）
amount = "12800"     // 收入 12800 元（整数可省略小数点）
amount = "0.0005"    // 小额结算，4 位小数，处于精度上限内
amount = "0"         // 零金额占位交易
amount = "+99999999999999.9999"  // 量级上限边界值，合法
```

非法示例与原因对照：

| 非法值 | 违反的约束 | 说明 |
|---|---|---|
| `"45.80 元"` | 格式约束 | 混入货币符号与汉字 |
| `"1,280.00"` | 格式约束 | 千分位逗号不允许 |
| `"1.28e4"` | 数值约束 | 科学计数法不允许 |
| `"3.14159"` | 精度约束 | 小数 5 位，超出 4 位上限 |
| `""` / `null` | 非空约束 | 金额缺失，无法参与任何统计 |
| `"100000000000000"` | 量级约束 | 整数 15 位，超出 14 位上限 |

### 2.5 常见错误

**错误一：用浮点类型存金额。** 这是最经典也最致命的错误。`0.1 + 0.2 = 0.30000000000000004` 的浮点误差逐笔累积后，月度对账会出现几厘到几分的系统性偏差。规避方法只有一个：存储用 `DECIMAL`，传输用字符串，运算用 decimal 库，全程杜绝 float/double。

**错误二：符号方向写反。** 录入界面选择了「收入」却存了负数，或导出时为「让数字好看」而强行取绝对值，导致余额统计与实际相反。方向与符号的映射必须在录入层强制绑定，后端不再二次猜测。

**错误三：超出 4 位小数。** 汇率折算等场景天然产生多的小数位（如 `100 ÷ 3 = 33.3333...`），调用方必须先按业务规则（银行家舍入或四舍五入，由业务明确指定）舍入到 4 位以内再提交，而不是寄希望于系统自动截断。

**错误四：字符串带修饰符。** 从表格或网页复制的金额常带 `￥`、`,`、空格甚至全角字符，直接入库会破坏解析。导入管道必须先做格式清洗与正则校验，非法即报错，不做静默清洗。

**错误五：忽略 `amount` 与 `currency` 的成对性。** 批量导入时只给了金额没给币种，或整批记录漏填币种后默认按本币处理。凡 `currency` 缺失的记录，`amount` 一律不得参与任何统计。

**错误六：前端用浮点输入框采集金额。** 输入控件绑定浮点类型，用户尚未提交时精度就已丢失。金额输入应以字符串形式采集，提交前仅做格式与范围校验。

## 3. currency 字段

### 3.1 定义

`currency` 声明一笔交易金额所使用的货币单位，是 `amount` 的语义补充——没有币种的金额只是裸数字，无法参与跨币种汇总、报表呈现与合规申报。`currency` 的取值采用 **ISO 4217 三位字母货币代码**，如 `CNY`（人民币）、`USD`（美元）、`EUR`（欧元）、`JPY`（日元）。

引入 `currency` 字段的根本动机是支持多币种记账：出境消费、海淘结算、外币理财等场景下，账本中会同时存在多种货币的交易。系统在进行任何跨币种统计时，须先按当日汇率将各币种金额折算为记账本位币再求和；而折算是否正确，完全取决于每笔交易的 `currency` 是否准确。因此 `currency` 是一个「错了就全局错」的字段，其准确性要求与 `amount` 同级。

此外，`currency` 还决定了金额的**小数位惯例**。ISO 4217 为每种货币定义了标准小数位数（如 `CNY`、`USD` 为 2 位，`JPY`、`KRW` 为 0 位，`BHD`、`KWD` 为 3 位）。系统在展示层会依据币种代码套用相应的小数位格式，在校验层允许超出惯例位数但仍受 4 位总上限约束，以兼容特殊结算场景。

### 3.2 类型

`currency` 的规范类型为**字符串（String）**，固定长度 3，内容为 ISO 4217 规定的三位大写拉丁字母代码。它在存储层通常以 `CHAR(3)` 定长字符存储，在传输层以普通 JSON 字符串出现。

关于类型的三个明确边界：

1. **代码 vs 符号**：字段值必须是 ISO 代码而非货币符号。`"CNY"` 合法，`"¥"`、`"￥"`、`"$"`、`"€"` 均非法——符号存在一对多问题（`$` 可指美元、加元、澳元等），不具备唯一性。
2. **代码 vs 名称**：`"人民币"`、`"RMB"` 均非法。`RMB` 是常见误写，并非 ISO 4217 代码，正确代码为 `CNY`。类似地，英镑应写 `GBP` 而非 `UKP`，瑞士法郎应写 `CHF` 而非 `SFR`。
3. **大小写**：规范形态为全大写。传入小写（`"cny"`）或混合大小写（`"Cny"`）的值，入库前必须统一转为大写；唯一性索引与统计分组均按大写形态执行。

系统在启动时会加载一份内置的 ISO 4217 代码表（含代码、英文名、中文名、小数位数），`currency` 的合法性校验以这份代码表为准。代码表随版本更新维护，废弃代码（如已退市的 `ZWL` 津巴布韦元等按 ISO 公告处理）会被标记而非直接删除，以保障历史数据仍可解析展示。

### 3.3 约束

`currency` 字段需满足以下约束：

1. **非空约束**：不得缺省、不得为 `null`、不得为空字符串。`amount` 与 `currency` 必须成对出现。
2. **格式约束**：必须恰好为 3 个拉丁字母（`^[A-Za-z]{3}$`），经大小写归一后与内置 ISO 4217 代码表中的有效代码精确匹配。
3. **大小写约束**：规范形态为全大写；非大写输入须在入口处归一化，未归一化导致的重复统计视为实现缺陷。
4. **有效性约束**：不得使用 ISO 4217 保留给测试与特殊用途的代码作为真实交易币种，包括 `XTS`（测试用货币）、`XXX`（无货币）以及以 `X` 打头的非具体国家代码（`XAU`、`XAG` 等贵金属代码），除非产品明确开启贵金属记账功能。
5. **一致性约束**：同一账本在设置中声明的「记账本位币」应与多数交易的 `currency` 一致；折算、汇总逻辑一律以每笔交易自身的 `currency` 为准，不得假定全账本单一币种。
6. **不可变约束的例外**：与其他字段不同，若录入时选错币种，允许通过「冲正 + 重录」流程更正，但不允许原地改写 `currency` 而不重算折算结果，以免历史汇率快照失真。

### 3.4 示例

合法示例：

```text
currency = "CNY"   // 人民币，2 位小数惯例
currency = "USD"   // 美元，2 位小数惯例
currency = "JPY"   // 日元，0 位小数惯例
currency = "KWD"   // 科威特第纳尔，3 位小数惯例
```

非法示例与原因对照：

| 非法值 | 违反的约束 | 说明 |
|---|---|---|
| `"¥"` | 格式约束 | 货币符号不是 ISO 代码 |
| `"RMB"` | 有效性约束 | 常见误写，非 ISO 4217 代码，应为 `CNY` |
| `"人民币"` | 格式约束 | 货币名称，非三位字母代码 |
| `"usd"` | 大小写约束 | 须归一化为 `"USD"` 后方可入库 |
| `"US"` | 格式约束 | 仅 2 位，长度不足 |
| `"XXX"` / `"XTS"` | 有效性约束 | ISO 保留代码，禁止用于真实交易 |

### 3.5 常见错误

**错误一：`RMB` 与 `CNY` 混用。** `RMB` 是中文语境的习惯称呼，不是 ISO 代码。混用会造成同一币种在统计分组中被拆成两组。入口处建立别名映射（`RMB → CNY`）并在校验时提示纠正。

**错误二：用货币符号代替代码。** 界面上显示 `¥`、`$` 没有问题，但落库与传输必须是代码。从支付渠道回调报文中提取币种时尤其注意：部分渠道回传符号或中文名，须先转代码再入库。

**错误三：假设账本只有一种币种。** 代码里写死 `currency = "CNY"` 或在汇总时忽略币种直接相加，一旦出现外币交易，汇总额立即失真。任何求和运算前都必须按 `currency` 分组或先折算。

**错误四：忽略零小数位币种。** 对 `JPY` 金额也格式化为两位小数（`¥1,000.00`），展示歧义。展示层应根据币种小数位惯例动态格式化。

**错误五：大小写不归一。** 上游系统传小写代码，本系统未归一直接入库，与既有大写数据形成重复分组。归一化必须发生在写入之前的最前端。

**错误六：使用保留代码。** 测试环境用 `XTS` 造数后未清理，数据同步到生产导致统计异常。测试数据须使用显式隔离的测试账本，禁止借用保留代码混入生产数据。

## 4. tags 字段

### 4.1 定义

`tags` 是一笔交易的分类标签集合，用于在固定科目体系之外提供灵活的多维归类。一笔「在超市买咖啡豆」的支出，可以同时打上 `食品`、`超市`、`自用` 三个标签，后续按任一维度检索与统计都能命中这笔交易。相比单一科目的树状归类，标签是网状结构，更贴合个人记账中「一笔消费多重属性」的真实需求。

`tags` 是一个**集合型字段**：它承载零个或多个标签，而非单个值。系统将其建模为**字符串数组**，数组中每个元素为一个标签。标签与科目（category）的分工是：科目由系统或账本预定义、一笔交易通常只归一个主科目，承担报表主口径；标签由用户自由创建、可多可无，承担个性化检索与交叉分析。`tags` 为空数组是合法的——不打算做精细化分类的用户可以完全不使用标签。

标签本身是由用户自定义的短文本，其内容由用户自主决定，系统只约束其形态（长度、字符集、去重），不约束其语义。为了跨设备同步与搜索体验，系统对标签做了规范化约定：统一去除首尾空白、按创建顺序保留、区分大小写但建议用户统一小写或统一中文。

### 4.2 类型

`tags` 的规范类型为**字符串数组（Array of String）**，即 `string[]`。在 JSON 报文中形如 `"tags": ["餐饮", "通勤", "工作日"]`。

类型的细化规定如下：

1. **容器类型**：必须为数组。即便只有一个标签，也必须写成单元素数组 `["餐饮"]`，而非裸字符串 `"餐饮"`。反之，不打算打标签时应写空数组 `[]`，而非 `null`、空字符串或省略字段。这一规定消除了「单值/数组」的双形态歧义，简化所有消费方代码。
2. **元素类型**：数组每个元素必须是字符串，不允许数字、布尔、对象、嵌套数组混入。
3. **元素内容**：每个标签为非空短文本，长度（按 Unicode 码点计）下限为 1、上限为 24；允许中文、英文字母、数字、连字符 `-`、下划线 `_`；不允许首尾空白、不允许仅由空白或标点构成、不允许包含制表符与换行符。
4. **顺序语义**：数组内元素按创建/录入顺序排列，第一个标签可视为「主要标签」。统计与展示接口按原顺序输出，排序需求由消费方自行实现，不在存储层强制排序。
5. **容量上限**：单笔交易标签数量上限为 **10 个**。超出上限的写入请求被拒绝，防止标签字段被滥用为准备注栏。

### 4.3 约束

`tags` 字段需满足以下约束：

1. **存在性约束**：字段必须存在且为数组，允许空数组 `[]`，不允许 `null`、不允许缺省、不允许裸字符串。
2. **元素合法性约束**：每个元素为字符串，去首尾空白后长度在 1–24 码点之间，且不得为纯空白或纯标点。
3. **唯一性约束**：同一数组内标签不得重复，重复以「去空白后精确相等（区分大小写）」判定。`["食品", "食品"]` 非法；`["食品", "食品外送"]` 合法，二者是不同标签。
4. **数量约束**：数组长度不超过 10。
5. **字符集约束**：单个标签内不得出现换行符、制表符、逗号、竖线等会干扰导出格式的分隔字符；不得以 `#` 开头（系统在展示层自动为标签渲染 `#` 前缀，存储值不携带）。
6. **规范形态约束**：写入前统一执行「去除元素首尾空白」的规范化；规范化后为空的元素视为非法，拒绝写入。

### 4.4 示例

合法示例：

```text
tags = []                                  // 不使用标签，合法
tags = ["餐饮"]                             // 单标签，必须包装为数组
tags = ["餐饮", "工作日", "公司附近"]         // 多标签，按录入顺序排列
tags = ["coffee", "2024", "self-use"]       // 英文与数字混排，合法
tags = ["旅行-东京", "购物_伴手礼"]           // 含连字符与下划线，合法
```

非法示例与原因对照：

| 非法值 | 违反的约束 | 说明 |
|---|---|---|
| `"餐饮"` | 存在性约束 | 裸字符串，必须包装为数组 |
| `null` | 存在性约束 | 空标签应写 `[]`，不得写 `null` |
| `["餐饮", "餐饮"]` | 唯一性约束 | 数组内元素重复 |
| `["  ", "会议"]` | 元素合法性约束 | 首元素去空白后为空 |
| `["这一条标签实在是太长了已经远远超过二十四个字符的上限值了"]` | 元素合法性约束 | 单个标签超 24 码点 |
| `[" food ", 123, true]` | 元素类型约束 | 混入数字与布尔；首元素另含首尾空白 |

### 4.5 常见错误

**错误一：单标签不包数组。** 上游把 `tags` 当可空字符串处理，无标签时传 `""`、有标签时传裸字符串，导致下游类型判断崩溃。统一约定：数组是唯一合法形态，空即 `[]`。

**错误二：标签重复。** 复用模板创建记录时把上一笔的标签原样带入又手动补了一遍，形成重复元素。写入前做一次去重校验，发现重复直接报错而非静默去重，让上游修正模板。

**错误三：标签被当作备注。** 用户把一句话备注塞进标签，触发 24 码点上限报错。引导文案须明确：标签是短词，长文本应写入备注字段。

**错误四：把标签当成科目。** 团队用标签代替科目做主口径报表，一旦有人不打标签，报表就漏数据。主统计口径必须建在科目上，标签只用于辅助交叉分析。

**错误五：带分隔符入库。** 标签内含逗号或竖线，导出 CSV 时被误拆列。字符集校验须在写入前拦截这些字符。

**错误六：大小写双版本并存。** `["Coffee", "coffee"]` 被当成两个标签，检索时分裂成两簇。系统区分大小写但建议用户统一小写；产品可另提供「合并标签」工具处理历史存量。

## 5. 附录：四字段要点汇总表

| 字段 | 规范类型 | 关键约束 | 最重要的禁止事项 |
|---|---|---|---|
| `id` | 字符串（UUIDv4，36 字符） | 非空、五组位数 8-4-4-4-12、小写、全局唯一、不可变 | 禁止自增编号与更新改写 |
| `amount` | 十进制定点数（传输用字符串） | 非空、≤4 位小数、绝对值 ≤ 14 位整数、收入正/支出负 | 禁止二进制浮点运算与科学计数法 |
| `currency` | 字符串（ISO 4217，3 位大写字母） | 非空、代码表精确匹配、与 `amount` 成对出现 | 禁止货币符号、`RMB` 等非标准代码 |
| `tags` | 字符串数组 | 必为数组、元素 1–24 码点、去重、≤10 个 | 禁止裸字符串、`null`、数组内重复 |

四字段联合校验的最低集合为：`id` 通过 UUID 正则、`amount` 通过十进制定点正则且在量程内、`currency` 命中代码表、`tags` 为合法数组。四项全部通过，记录方可进入入库流程；任一失败，整条记录拒绝并返回对应字段的校验错误码，不做部分入库。

本文档为《迷你记账字段参考手册》完整正文，覆盖 `id`、`amount`、`currency`、`tags` 四个字段，每字段均含定义、类型、约束、示例、常见错误五个小节。各岗位在开发与验收中如发现本文档与最新接口契约不一致，以最新契约为准并反馈修订本文档。
