# 迷你记账字段参考手册

**版本**：v1.0
**适用范围**：迷你记账系统的数据字段 id、amount、currency、tags
**说明**：本手册面向开发、测试与数据维护人员，逐一阐述四个核心字段的定义、类型、约束、示例与常见错误，供接口对接、表结构设计与数据校验时参考引用。

---

## 第一章 字段 id

### 1.1 定义

id 是迷你记账系统中每一条记账记录的唯一标识符。它的核心职责是在系统全域范围内无歧义地指向某一条具体的账目记录，是所有记录级操作（查询、修改、删除、对账、审计追溯）的主键依据。无论用户在哪个终端、哪个渠道录入账目，系统都会为每条记录分配一个全局唯一的 id，作为该条数据在整个生命周期中不可变更的“身份证号”。

id 与业务含义解耦：它不承载任何金额、日期、分类等业务语义，纯粹服务于记录的定位与引用。这意味着任何外部系统（如导出工具、统计报表、消息通知）引用某条账目时，都必须通过 id 来锚定，而不是通过金额加日期之类的组合猜测定位——因为后者的组合完全可能出现重复。

在分布式或多端同步场景下，id 还承担冲突消解的作用：当同一记录在两个设备上发生并发修改时，同步引擎依据 id 识别“这是同一条记录”，再依据版本或时间戳决定保留哪一方的变更。因此，id 的唯一性与稳定性是整个系统数据一致性的基石。

### 1.2 类型

id 的标准数据类型为 64 位无符号整数（Unsigned BIGINT），在 JSON 接口中以字符串形式传输（例如 `"id": "7001234567890123456"`），以规避 JavaScript Number 类型在超过 2^53 − 1 时出现精度丢失的问题。

若采用字符串主键方案（部分部署形态支持），则为定长或近定长的字母数字串，长度 16–26 个字符，仅含 0–9、a–z、A–Z，区分大小写。存储层面：整数方案占用 8 字节，字符串方案按字符集占用 16–26 字节；数据库中应建立主键索引或唯一索引。

在编程语言中的推荐映射：Java 中为 `long`（序列化为字符串），Go 中为 `uint64` 或 `int64`，Python 中为 `int`，TypeScript/JavaScript 中一律按 `string` 处理。

### 1.3 约束

1. **全局唯一**：在整个系统范围内（含逻辑删除的数据）不得重复。重复 id 视为严重数据缺陷。
2. **非空**：id 不允许为 null、空字符串或缺省。任何缺少 id 的记录在写入时必须被拒绝或由系统自动补齐。
3. **不可变**：记录创建后 id 永不更改。即使记录内容被修改、被归档、被软删除，id 保持不变。
4. **单调递增趋势**（整数方案）：id 生成应大致随时间递增，以利于 B+ 树索引的写入性能，但不要求严格连续，允许存在空洞。
5. **格式合法**：整数方案下取值范围为 [1, 2^64 − 1]，0 与负数非法；字符串方案下不得包含空格、中文、控制字符与 URL 特殊字符。
6. **禁止复用**：已删除记录的 id 不分配给新记录，以保证历史日志、外部引用的长期有效性。
7. **传输表示**：JSON 输出必须是字符串；接口层应拒绝将 id 以纯数字形式返回给前端。

### 1.4 示例

- 合法示例（整数方案，JSON 传输）：

```json
{
  "id": "7001234567890123456",
  "amount": "-45.50",
  "currency": "CNY",
  "tags": ["餐饮", "午餐"]
}
```

- 合法示例（字符串主键方案）：`"id": "tx_9fK3mQ7xR2pL8vN4"`——前缀 `tx_` 为可选的业务前缀，主体 16 位字母数字。
- 批量查询示例：`GET /api/v1/records?ids=7001234567890123456,7001234567890123457`
- 数据库建表片段：`id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY`（单体部署）或应用侧雪花算法生成后直接插入。
- 反例（非法）：`"id": 0`、`"id": -1`、`"id": ""`、`"id": "abc def"`（含空格）、`"id": 7001234567890123456`（JSON 中裸数字，存在精度丢失风险，禁止输出）。

### 1.5 常见错误

1. **JSON 中以数字类型输出长 id**：前端 JavaScript 解析时末几位被截断为零，导致后续按 id 查询 404。修正：序列化层统一将 id 转为字符串。
2. **删除后复用 id**：旧日志或第三方缓存仍指向该 id，复用后引用错乱到新记录。修正：id 只增不复用。
3. **用“金额 + 日期”推断记录身份**：两笔同日同额的记录被误当作同一条，造成重复记账或漏记账。修正：一切定位操作以 id 为准。
4. **多端各自生成自增 id 且未加机器位**：同步时两台设备各有一笔 id=1024 的记录，合并冲突。修正：采用雪花算法等含机器标识的分布式 id 方案。
5. **对 id 做大小写不敏感比较**（字符串方案）：`tx_Abc` 与 `tx_abc` 被误判为同一条。修正：比较时严格区分大小写。
6. **索引缺失**：id 列未建索引，按 id 查询退化为全表扫描，账目量增长后接口超时。
7. **校验时用浮点接收 id**：整型 id 被 float 承载，超过 2^53 后精度丢失。修正：所有 id 一律按整数或字符串处理。

## 第二章 字段 amount

### 2.1 定义

amount 表示一笔账目的金额数值，是记账系统中业务语义最核心的字段。它记录该条账目涉及的货币数量，配合符号或独立方向字段表达资金流向：正数代表收入（资金流入），负数代表支出（资金流出），零通常表示零元账目（如赠品、报销冲抵等场景）。

amount 与 currency 字段联合才构成完整语义：“amount=100, currency=JPY”与“amount=100, currency=CNY”是价值完全不同的两笔账。因此在任何展示、统计、汇总场景中，都不允许脱离 currency 单独解读 amount。

需要特别强调：amount 表达的是**账面记录金额**，而不是账户余额，也不是经过汇率换算后的本币金额。汇率换算属于报表层职责，记录层必须忠实保存交易发生时的原始金额与原始币种。

### 2.2 类型

amount 的规范类型为**定点十进制数**，标准精度为：总精度 19 位，其中小数位最多 4 位（DECIMAL(19,4)）。小数 4 位是为兼容日元（0 位小数）、第纳尔（3 位小数）等特殊币种及加密资产场景预留的通用精度；对于人民币、美元等 2 位小数币种，第 3、4 位应为 0。

存储与运算层面**严禁使用二进制浮点类型（float / double）**，因为 0.1、0.01 等十进制小数无法被二进制浮点精确表示，会在累加运算中产生累积误差。推荐实现：

- 数据库：`DECIMAL(19,4)` 或 `NUMERIC(19,4)`；
- Java：`java.math.BigDecimal`；
- Go：`shopspring/decimal` 或以最小单位整数（分、厘）存储的 `int64`；
- Python：`decimal.Decimal`；
- JSON 传输：以**字符串**形式传输（推荐）或最多 4 位小数的数字字面量，禁止出现科学计数法。

### 2.3 约束

1. **非空**：amount 必填，不允许 null 或缺省。
2. **精度上限**：小数位不得超过 4 位；超出部分必须由调用方按业务规则舍入后再提交，服务端可配置为拒绝或按“四舍六入五成双”舍入。
3. **数值范围**：绝对值不得超过 10^15（即千万亿级），防止超出 DECIMAL(19,4) 容量并给统计聚合留出余量。
4. **符号语义**：正数=收入，负数=支出，0=零元账目；禁止用字符串"+""-"前缀表达方向（方向由数值符号唯一决定）。
5. **与 currency 绑定校验**：小数位数不得超过 currency 声明的该币种默认小数位（可配置放宽，但默认校验），例如 CNY/USD/EUR 默认 2 位，JPY 默认 0 位。
6. **格式约束**：JSON 中不得使用科学计数法（如 `1e3`）、不得携带千分位逗号、不得携带货币符号（"¥"、"$"），货币信息一律由 currency 字段承载。
7. **审计不可抵赖**：amount 一经写入，修改需留存修改前后的完整审计日志，禁止静默改写。
8. **聚合一致性**：任何汇总（日报、月报）必须基于同一精度规则舍入，“先逐笔舍入再汇总”与“先汇总再舍入”二者只能选定其一并全局统一，文档中默认前者。

### 2.4 示例

- 合法示例：

```json
{
  "id": "7001234567890123457",
  "amount": "-128.50",
  "currency": "CNY",
  "tags": ["交通", "打车"]
}
```

表示一笔 128.50 元人民币的支出。

- 收入示例：`"amount": "8500.00", "currency": "CNY"`。
- 零元账目：`"amount": "0", "currency": "CNY", "tags": ["赠品"]`。
- 零小数位币种：`"amount": "-1200", "currency": "JPY"`——日元账目，合法，且不应出现 `-1200.00` 之外的更多小数。
- 数据库定义：`amount DECIMAL(19,4) NOT NULL CHECK (amount > -1000000000000000 AND amount < 1000000000000000)`。
- 反例（非法）：`"amount": -12.99999`（5 位小数）、`"amount": "1,280.00"`（千分位）、`"amount": "¥88"`（携带货币符号）、`"amount": 1.5e3`（科学计数法）、`"amount": null`。

### 2.5 常见错误

1. **用 float/double 存储或运算金额**：0.1 + 0.2 = 0.30000000000000004，月度汇总出现分级误差。修正：全面切换 DECIMAL / BigDecimal / Decimal。
2. **前后端精度不一致**：后端存 4 位小数，前端展示截断 2 位且未声明舍入规则，用户对账时发现“少了半分钱”。修正：展示层明确舍入规则并在 UI 上注明。
3. **符号约定混乱**：部分模块用正数表示支出、绝对值加 type 字段表示方向，与本手册规范冲突，接入后收入支出颠倒。修正：接入前按本手册统一符号语义。
4. **脱离 currency 汇总**：把 100 CNY 与 100 JPY 直接相加得 200。修正：汇总前必须按币种分组或先换算。
5. **字符串比较金额**：`"9.5" > "10.00"` 在字符串比较下为真。修正：先解析为十进制数值再比较。
6. **四舍五入在循环中反复进行**：逐层聚合多次舍入导致误差放大。修正：只在最终输出点舍入一次，或全局统一“先舍入再聚合”并不再二次舍入。
7. **千分位、货币符号混入提交数据**：客户端把格式化后的展示文本直接回传。修正：展示与数据分离，提交前清洗。

## 第三章 字段 currency

### 3.1 定义

currency 表示一笔账目所使用的货币币种，与 amount 共同构成完整的金额语义。它的存在使迷你记账系统能够支持多币种记账、按币种分组统计以及报表层的汇率换算。

currency 采用国际通用的 **ISO 4217 货币代码**体系：三字母代码中前两位通常源自国家/地区代码，第三位为货币名称首字母（如 CNY = CHina Yuan，JPY = JaPan Yuan，USD = United States Dollar）。每个代码还对应一个 ISO 4217 数字代码（如 CNY=156）和该币种的默认小数位数（exponent），本手册的校验规则将引用这一“默认小数位”元数据。

currency 字段只表达币种标识本身，不包含汇率。汇率是随时间变化的外部数据，由报表与换算模块按“交易日期 + 币种对”查询汇率服务获得，绝不写入 currency 字段。

### 3.2 类型

currency 的数据类型为**定长字符串，长度恒为 3 个字符**，字符集限于 ISO 4217 规定的大写拉丁字母 A–Z。

- 数据库：`CHAR(3)`，配合 CHECK 约束或外键关联币种字典表 `currency(code CHAR(3) PRIMARY KEY, numeric_code SMALLINT, minor_units TINYINT, name VARCHAR(64), status ...)`；
- 编程语言：Java/Go/Python 中均以字符串常量或枚举表示，禁止用整数代码做内部主表示；
- JSON 传输：大写三字母字符串，如 `"CNY"`；
- 校验依据：系统内置 ISO 4217 币种字典（含停用币种标记），升级时随字典版本更新。

### 3.3 约束

1. **非空且必填**：每条账目必须显式声明币种；系统不做“默认币种自动补全”的静默行为，缺省时接口应返回校验错误（客户端可在表单层预填用户偏好币种，但提交报文中必须显式携带）。
2. **格式严格**：长度恰好为 3，全大写 A–Z，不含数字、空格、符号；`"cny"`、`"CN Y"`、`"¥"`、`"156"` 均非法。
3. **字典内有效**：必须是系统币种字典中存在的代码；字典外的代码一律拒绝。已停用币种（如因货币改制退场的代码）仅允许存量数据保留，禁止新增使用。
4. **与 amount 小数位联动**：amount 的小数位数不得超过该币种字典中的 minor_units（默认可配置放宽至 4 位）。
5. **不可变**：账目创建后 currency 不得修改；币种记错时应作废原记录另立新记录，保留审计链。
6. **同质聚合前提**：跨币种求和无意义，任何 sum/avg 聚合必须先按 currency 分组，或显式声明换算汇率来源与日期。
7. **展示规范**：展示层符号（"¥"、"$"、"€"）仅为呈现形式，符号与币种的映射必须经由字典完成，禁止在数据层写死“$ 就是 USD”。

### 3.4 示例

- 合法示例（多币种账目）：

```json
{
  "id": "7001234567890123458",
  "amount": "-25.00",
  "currency": "USD",
  "tags": ["订阅", "软件"]
}
```

```json
{
  "id": "7001234567890123459",
  "amount": "-3600",
  "currency": "JPY",
  "tags": ["旅行", "购物"]
}
```

- 批量按币种统计示例：`GET /api/v1/summary?group_by=currency&month=2025-06`
- 字典表片段：

| code | numeric_code | minor_units | name | status |
|------|--------------|-------------|------|--------|
| CNY  | 156          | 2           | Chinese Yuan | ACTIVE |
| USD  | 840          | 2           | US Dollar | ACTIVE |
| JPY  | 392          | 0           | Japanese Yen | ACTIVE |
| KWD  | 414          | 3           | Kuwaiti Dinar | ACTIVE |

- 反例（非法）：`"currency": "cny"`（小写）、`"currency": "RMB"`（非 ISO 代码，人民币的正确代码是 CNY）、`"currency": "US"`（2 位）、`"currency": "USDT"`（4 位，且属加密资产，不在默认字典）、`"currency": ""`。

### 3.5 常见错误

1. **使用 "RMB" 表示人民币**：RMB 不是 ISO 4217 代码，校验直接失败或被存为脏数据。修正：统一使用 CNY。
2. **大小写混用**：写入 `"cny"`，与 `"CNY"` 在严格比较下判为不同币种，统计分组裂成两组。修正：服务端提交前统一 toUpperCase 校验或直接拒绝小写。
3. **把汇率写进 currency 字段**：如存成 `"CNY@7.2"`，破坏类型约定且汇率过期失效。修正：汇率另立字段/服务，按交易日期快照。
4. **跨币种直接求和**：报表出现“美元+日元=若干”的荒谬结果。修正：强制按币种分组，跨币种合计必须走换算管道并标注汇率日期。
5. **忽略零小数位币种**：给 JPY 记 `-1200.50`，造成半日元这种不存在金额。修正：按字典 minor_units 校验。
6. **修改存量记录币种**：直接 UPDATE currency 导致历史账目与凭证、对账单不符。修正：作废重录。
7. **硬编码货币符号映射**：`"$"` 一律显示美元，导致 CAD、AUD、HKD 用户困惑。修正：符号由字典与地区设置共同决定。

## 第四章 字段 tags

### 4.1 定义

tags 是账目的标签集合，用于对一笔账目附加一个或多个自由分类标记，是记账系统中灵活度最高的组织维度。与刚性、树状的账户/分类体系不同，tags 是扁平、多值、可叠加的：一笔“和同事聚餐后打车回家”的账目可以同时打上“餐饮”“社交”“打车”三个标签，从而在统计时同时进入三个视角的汇总。

tags 的典型用途包括：项目化记账（如“装修”“婚礼”）、临时性标记（如“待报销”）、人群维度（如“给孩子”）、地点维度（如“出差-上海”）等。标签体系鼓励用户按自己的生活方式生长，系统只负责提供结构与校验，不预置业务含义。

tags 是搜索与筛选的主要入口。系统应支持按标签的等值筛选、多标签交集/并集筛选，以及标签维度的时间序列统计。正确设计 tags 的结构约束，直接决定这些能力是否可靠。

### 4.2 类型

tags 的数据类型为**字符串数组**，即有序的字符串列表，JSON 中表示为 `array of string`。

- 单个标签：UTF-8 字符串，长度 1–32 个字符（按 Unicode 码点计），首尾空白不计入（写入前由系统 trim）。
- 数组长度：每条账目 0–10 个标签；空数组 `[]` 表示“无标签”，与缺省等价。
- 数据库存储：关系库采用“账目-标签”多对多关联表 `record_tag(record_id, tag_id)` + `tag(id, name UNIQUE)` 的规范化结构；文档库可内嵌数组但需同时维护标签字典集合以保证统计性能。
- 大小写策略：标签名以**写入首次形态保留显示**，但**匹配与去重按 NFKC 归一化 + 转小写后的规范化键**进行，即“咖啡”与“咖啡 ”（多空格）视为同一标签，“Coffee”与“coffee”视为同一标签。
- 排序语义：数组内顺序不承载业务含义，接口返回时按规范化键的字典序排序，保证幂等。

### 4.3 约束

1. **类型严格**：必须是字符串数组；`"餐饮"`（裸字符串）、`{"tags": "餐饮"}`、`[1, 2]`（数字数组）均非法。
2. **去重**：同一账目内规范化后相同的标签只保留一个；重复提交不报错，静默去重。
3. **数量上限**：最多 10 个标签，超出整笔请求拒绝并提示。
4. **单标签长度**：1–32 码点；空标签 `""`、纯空白标签、超长标签均拒绝。
5. **禁用字符**：标签内不得包含控制字符（U+0000–U+001F、U+007F）；建议但不强制限制逗号 `，,` 与竖线 `|`，因其常被导出 CSV 的下游误当作分隔符。
6. **引用完整性**：账目引用的标签名必须能解析到标签字典中的条目；删除标签字典条目时若仍有账目引用，默认阻止或标记“已归档”而非物理删除。
7. **批量操作原子性**：为账目追加/移除标签的接口必须整体原子生效，不允许半成功状态。
8. **规范化确定性**：同一输入永远映射到同一规范化键（NFKC + trim + lower case），保证统计口径唯一。

### 4.4 示例

- 合法示例：

```json
{
  "id": "7001234567890123460",
  "amount": "-268.00",
  "currency": "CNY",
  "tags": ["餐饮", "聚餐", "待报销"]
}
```

- 空标签数组（合法，表示无标签）：`"tags": []`。
- 筛选示例（交集）：

```
GET /api/v1/records?tags=餐饮,待报销&match=all
```

返回同时含“餐饮”与“待报销”的账目；`match=any` 则为并集。

- 统计示例：`GET /api/v1/summary/by-tag?month=2025-06` 返回各标签当月支出合计。
- 规范化示例：提交 `[" Coffee ", "coffee", "咖啡"]`，规范化后保留为 `["coffee", "咖啡"]`（前两者合并）。
- 反例（非法）：`"tags": "餐饮"`、`"tags": [null]`、`"tags": ["", "  "]`、`"tags": ["a\u0007b"]`（含控制字符）、`"tags": ["t1","t2","t3","t4","t5","t6","t7","t8","t9","t10","t11"]`（超 10 个）。

### 4.5 常见错误

1. **把 tags 当单一字符串提交**：`"tags": "餐饮,聚餐"` 被当成一个 32 码点以内的整体标签，统计出现名为“餐饮，聚餐”的怪标签。修正：提交前按数组拆分。
2. **依赖大小写区分做标签拆分**：用户以为“Coffee”与“coffee”是两个标签，统计却合并为一类，或反之在严格比较接口中查不到。修正：理解“显示保留原样、匹配按规范化键”的双轨策略。
3. **标签无限增殖**：自动打标的脚本每天生成带日期的标签（“20250601”），一年产生数百个碎片标签，统计失去意义。修正：建立标签命名规范，定期归并，必要时限制新增权限。
4. **物理删除仍被引用的标签**：关联表出现悬空引用，报表漏算。修正：软删除/归档 + 引用检查。
5. **导出 CSV 未转义**：标签含逗号，下游按逗号切分后列错位。修正：导出时严格转义或禁止标签使用逗号。
6. **用 tags 表达本应结构化的信息**：把日期、金额区间塞进标签，试图用标签做账期统计。修正：日期、金额用专用字段，标签只承担自由分类。
7. **去重时机错误**：展示层先去重、写入层不去重，数据层积累重复标签，不同客户端看到数量不一致。修正：写入层统一规范化去重，下游不再自行处理。
