# 迷你记账字段参考手册

本手册面向迷你记账系统的开发者、测试人员与数据维护人员，对系统核心数据模型中的四个关键字段——id、amount、currency、tags——逐一展开说明。每个字段按「定义、类型、约束、示例、常见错误」五个小节组织，力求让读者在接入、校验、排查问题时能够直接对照本手册执行。手册末尾附有完整性校验和一行，供交付流程校验使用。

## 字段一：id

### 1.1 定义

id 是迷你记账系统中每条账目记录的唯一标识符。它的职责是在整个数据集合中无歧义地指代一条记录：查询、更新、删除、关联对账等一切以记录为对象的操作，都必须通过 id 来定位目标。id 在记录创建时生成，一经写入便不再变更。它不承载任何业务语义——不表达金额、时间、类别等含义，只承担「标识」这一单一职责，因此任何试图在 id 中编码业务信息的做法都应被禁止。系统内所有对账目记录的外部引用（如导出文件、日志、错误提示）均应携带该 id，以便快速定位问题记录。

### 1.2 类型

id 的类型为字符串。选择字符串而非整数，是为了兼容多种生成策略：数据库自增序列、UUID v4、雪花算法的十进制或十六进制输出、带前缀的业务编号（如 "TX-20240101-000123"）均可无损落入字符串。字符串长度上限为 64 个字符，最小长度为 1 个字符。字符集限定为 ASCII 字母、数字、连字符（-）与下划线（_），不允 许空格、斜杠、点号及其他特殊符号，以避免在 URL 路径、文件名、日志拼接等场景中引发转义或截断问题。系统对外接口中，id 一律以 UTF-8 编码的 JSON 字符串传输，即使其内容全部是数字，也不得省略引号。

### 1.3 约束

id 受到以下强制约束：第一，全局唯一性。同一账本内不允许出现两条 id 相同的记录，存储层须以 id 建立唯一索引，重复写入必须被拒绝并报错。第二，不可变性。记录创建后 id 不得被更新，任何试图修改 id 的请求都应视为非法操作。第三，非空性。id 不允许为空字符串、纯空白字符串或 null。第四，字符集与长度限制如 1.2 节所述，超出 64 字符或含有非法字符的 id 在入口层即被拒绝。第五，大小写敏感性。系统按大小写敏感方式比较 id，"abc" 与 "ABC" 视为两个不同标识符，接口文档中必须显式告知调用方这一点，避免对账时因大小写差异误判为重复或丢失。

### 1.4 示例

合法示例一："a3f8c2e1-9b4d-4c7a-8e2f-1d6b9c0a5e43"（UUID v4 格式，含连字符，长度 36，字符集合法）。合法示例二："TX-20240615-000789"（带前缀的业务编号，含字母、数字与连字符，长度 18）。合法示例三："82736451829047561029"（纯数字雪花 ID 以字符串形式存放，长度 20，注意引号不可省略）。合法示例四："ledger_a_backup_01"（含下划线与字母，长度 18，可用于环境隔离场景）。反例一：82736451829047561029（无引号，会被解析层当作超精度整数处理，存在精度丢失风险）。反例二："tx 2024 0615"（含空格，字符集非法）。反例三：""（空字符串，违反非空约束）。每个示例在接入测试时都应通过字段校验器逐条验证，反例必须全部被拒。

### 1.5 常见错误

错误一：省略引号。客户端把纯数字 id 当作数字类型发送，长整数在 JavaScript 等环境中超过安全整数范围后被静默截断，导致查询永远找不到目标记录。规范做法是 id 永远以字符串传输。错误二：在 id 中编码业务含义，例如把日期、用户号拼进 id，后续业务规则变更时被迫改 id 格式，触碰不可变性红线，引发大规模数据迁移。错误三：大小写混淆。对账脚本用大小写不敏感的方式比较两套系统的 id，把 "Abc123" 与 "abc123" 误判为同一条，造成漏记。错误四：拼接注入。id 未经参数化校验直接拼入 SQL 或日志模板，非法字符突破字符集约束后形成注入或日志伪造。防御方式是入口层严格执行 1.3 节约束，再进入业务逻辑。

## 字段二：amount

### 2.1 定义

amount 表示一条账目记录的金额数值，是记账系统中最核心的业务字段。它记录该笔账目所涉及货币的数量，正负号表达资金方向：收入记为正数，支出记为负数；转账场景下，转出账户侧记录负值，转入账户侧记录对应正值，两方绝对值必须相等才能通过对账。amount 只表达数量本身，不包含货币种类信息——币种由 companion 字段 currency 表达，二者共同构成完整的金额语义。amount 不承担分类、备注、时间等职责，任何把折扣、汇率、手续费等信息塞进 amount 的做法都会破坏单一语义，应通过独立字段或关联记录表达。

### 2.2 类型

amount 的类型为十进制定点数，序列化时以字符串形式传输（如 "123.45"），存储时使用数据库的 DECIMAL 类型，建议精度为 DECIMAL(19,4)：整数部分最多 15 位，小数部分固定 4 位。选择定点数而非浮点数，是因为 IEEE 754 二进制浮点无法精确表示 0.1、0.01 等十进制小数，累计求和时会产生肉眼可见的误差，这在记账场景中不可接受。接口层面禁止以 JSON number 直接传输 amount，必须加引号以字符串到达，由服务端解析为 BigDecimal 或等价的十进制类型。小数位数的舍入规则采用银行家舍入（round half to even），舍入只发生在最终展示与结算汇总环节，中间计算全程保持 4 位小数精度不提前舍入。

### 2.3 约束

约束一：不可为零。金额为 0 的账目没有记账意义，入口层拒绝 amount 为 "0" 或 "0.0000" 的记录。约束二：绝对值上限。单笔金额绝对值不得超过 999999999999999.9999（15 位整数 + 4 位小数），超出即拒绝，防止溢出与洗钱类异常大额。约束三：精度对齐。小数位数超过 4 位时，若第三位之后全为零可自动规整；若含有效数字则拒绝，禁止服务端静默舍入用户输入。约束四：方向一致性。转账类记录中，正负必须与账户方向字段匹配，转出为负、转入为正，不得同号。约束五：非空。amount 不允许为 null 或空串。约束六：与 currency 联动校验，不同币种有不同的常见小数位（日元 0 位、美元 2 位），超出该币种最小单位的小数位应触发告警而非直接拒绝，交由业务规则裁决。

### 2.4 示例

合法示例一："128.50"——日常餐饮支出记为 "-128.50"，收入记为 "128.50"，两位小数符合人民币惯例。合法示例二："0.0001"——四位小数，可用于积分、加密货币等高精度细分单位场景。合法示例三："999999999999999.9999"——合法上界值，恰好命中上限，应被接受。反例一：128.5（无引号的 JSON number，进入浮点解析路径，违反类型约束）。反例二："12.34567"——七位小数且末位非零，超出 4 位精度上限，应被拒绝。反例三："0"——零金额，违反非零约束。反例四："1e5"——科学计数法字符串，格式非法，入口层应拒绝并提示改写为 "100000"。反例五："-0.00"——负零，语义上等同零金额，同样违反非零约束，需在比较时显式处理。

### 2.5 常见错误

错误一：浮点运算。开发者在客户端用 float 或 double 计算 "0.1 + 0.2" 得到 0.30000000000000004 后直接提交，服务端因精度非法而拒单。正确流程是前端仅做展示格式化，所有金额运算在服务端用十进制库完成。错误二：舍入时机错误。逐笔先舍入再求和，与先求和再舍入的结果出现分级差异（即对账差额），规范是全程保留 4 位小数，仅在结算点舍入一次。错误三：忽略币种小数位。对日元记录写入 "1000.50"，日元最小单位为元（0 位小数），此类记录在报表汇总时产生虚假分位金额。错误四：正负号约定不一致。老接口以正数表示支出、靠方向字段判断，新接口以符号表达方向，混用后报表收支颠倒。迁移期必须在接口版本上隔离两套约定，并逐条核对历史数据。错误五：字符串金额带千分位逗号，如 "1,234.56"，未剥离逗号直接解析导致解析失败或被截断为 "1"。

## 字段三：currency

### 3.1 定义

currency 表示一条账目记录所使用的货币种类，与 amount 配对出现，二者共同构成完整的金额语义。currency 的存在使系统天然支持多币种记账：同一账本内可以并存人民币、美元、欧元、日元等不同币种的账目，报表与汇总结算时再按用户指定的汇率基准进行折算。currency 只回答「这是哪种货币」这一个问题，不携带汇率、折算规则、计价基准等信息——汇率属于独立的外部参照数据，按时间戳关联，绝不写入 currency 字段本身。这个边界划分保证了货币定义的稳定性：货币代码几十年不变，而汇率时刻波动，二者生命周期截然不同，必须分离存储。

### 3.2 类型

currency 的类型为定长字符串，长度固定为 3 个字符，取值限定为 ISO 4217 三字母货币代码，且仅接受大写字母 A–Z。系统启动时加载一份内置的 ISO 4217 代码表（约 180 个有效代码），所有写入的 currency 值必须在表内命中，未命中即拒绝。此约束意味着 "人民币"、"元"、"$"、"CNY "（含尾部空格）、"cny"（小写）等写法一律非法，唯一合法形态是形如 "CNY" 的大写三字母代码。对于代码表中的历史遗留代码（如已被欧元替代的 "FRF"），系统保留识别能力但默认拒绝新增写入，仅在读取历史数据时放行，并在报表中标注「已停用币种」。

### 3.3 约束

约束一：格式约束。必须恰好 3 个大写字母，长度不等、含数字、含小写、含空格均拒绝。约束二：值域约束。必须在内置 ISO 4217 代码表内，防止 "XXX"、"QQQ" 之类的无效代码入库。约束三：非空约束。currency 不允许为 null 或空串，每条账目必须显式声明币种，不存在「默认币种隐式补全」——显式声明可避免跨地区部署时默认值不一致引发的错账。约束四：配对约束。currency 必须与 amount 同时出现、同时更新，二者视作一个原子语义单元，任何只更新其一的请求整体拒绝。约束五：汇总约束。跨币种求和是非法操作，任何聚合计算必须先按币种分组或先折算，聚合引擎遇到混合币种直接求和时应抛出异常而非静默相加数值。

### 3.4 示例

合法示例一："CNY"——人民币，两位小数惯例，配合 amount "-58.00" 表示一笔 58 元支出。合法示例二："USD"——美元，常见于跨境消费记录，如 amount "-12.99" 配 "USD"。合法示例三："JPY"——日元，零小数位惯例，amount 应为 "-3500" 这类整数值。合法示例四："EUR"——欧元，两位小数。合法示例五："CHF"——瑞士法郎，代码表内有效，虽不常见但完全合法。反例一："cny"——小写，违反大写约束。反例二："RMB"——民间惯用缩写，不在 ISO 4217 代码表内，是最高频的真实误用，应提示改用 "CNY"。反例三："CN"——只有两位，长度非法，且这是国家代码而非货币代码。反例四："CNY "——尾部带空格，须先 trim 再校验，trim 后合法则接受，原文入库仍存 trim 后形态。反例五："USDT"——四位字符，超长，且稳定币不在 ISO 4217 表内，须走单独的资产字段而非 currency。

### 3.5 常见错误

错误一：使用 "RMB" 代替 "CNY"。人民币的 ISO 4217 代码是 CNY，"RMB" 仅是口头与民间书写习惯，很多中文应用未经校验直接入库，导致后续对接国际支付渠道时映射失败。防御方式是代码表硬校验加一层常见别名提示。错误二：大小写混用。接口调用方传小写 "usd"，服务端未做大写归一即入库，与既有的 "USD" 数据在同一账本中形成两个「币种」，汇总时同币种被拆成两组。规范是入口层统一 toUpperCase 后再校验。错误三：跨币种直接求和。报表引擎对 "100 CNY + 50 USD" 直接相加得 150，报表数字完全失真。聚合前必须显式分组或声明汇率折算基准日。错误四：把汇率写进 currency 相关逻辑，例如约定 "currency=USD 时 amount 已折算为人民币"，这种隐式约定随需求演进出无数例外，最终无人说得清某条记录的金额到底是原币还是折算值。错误五：遗漏币种字段的历史迁移，老版本数据无 currency 列，批量补默认值时按服务器时区猜地区，把港币用户的记录补成了 CNY。

## 字段四：tags

### 4.1 定义

tags 是账目记录的标签集合，用于在不改变核心数据模型的前提下为账目附加任意维度的分类信息。与固定的科目分类字段不同，tags 是开放式的：用户可以自建「早餐」「报销」「旅行-东京」「待核对」等任意标签，一条账目可同时挂多个标签，从而支持多角度的检索与统计。例如「出差期间的餐饮」可以同时打上 "餐饮" 与 "出差" 两个标签，月底按 "出差" 汇总、按 "餐饮" 分析习惯，两条统计线互不干扰。tags 只承担「标注」职责，不参与金额、币种等核心语义；标签本身是纯文本标记，不携带权重、颜色、层级之外的复杂结构，层级语义通过命名约定（如 "旅行-东京"）表达而非结构嵌套。

### 4.2 类型

tags 的类型为字符串数组，JSON 形态如 ["餐饮","出差"]。数组元素为非空字符串，单个标签长度 1–20 个字符（按 Unicode 码点计数，中文、emoji 各计 1），允许中文、字母、数字、连字符、下划线与常用 CJK 字符；禁止前导与尾随空白，允许标签内部含空格但连续空格会被规整为单个。数组本身长度上限为 10 个标签，超出拒绝；数组内标签经大小写敏感、去空白后的精确匹配去重，重复标签只保留首个出现顺序。空数组 [] 是合法值，表示「无标签」；null 与缺失字段的语义不同：缺失表示沿用旧版数据形态，null 视为非法输入拒绝写入，接口文档必须写明这一区分。

### 4.3 约束

约束一：结构约束。必须是数组，不接受以逗号分隔的单一字符串（如 "餐饮,出差"），类型不符直接拒绝，避免各端自行 split 造成分隔符歧义。约束二：数量约束。数组长度 0–10，超出 10 个拒绝，防止标签泛滥导致统计维度失控。约束三：单标签约束。每个元素非空、长度 1–20、无首尾空白、不含控制字符。约束四：去重约束。同一数组内不允许出现语义重复标签，服务端在精确匹配去重后若长度仍超限则拒绝。约束五：保留前缀约束。以双下划线开头的标签（如 "__system"）为系统保留命名空间，用户写入一律拒绝。约束六：删除联动约束。删除一个全局标签时，历史账目上的该标签保留为孤儿标签并在报表中如实呈现，不静默抹除，保证历史报表可复现。

### 4.4 示例

合法示例一：["餐饮"]——单标签，最简形态。合法示例二：["餐饮","出差","报销"]——三标签，覆盖「这笔钱花在餐饮上、发生在出差期间、可报销」三个维度，可分别参与三条统计线。合法示例三：["旅行-东京","2024暑期"]——命名约定表达层级与时段。合法示例四：[]——空数组，表示无标签，是合法值。合法示例五：["Aa","aa","A a"]——三个标签在大小写敏感与空格敏感规则下互不重复，全部合法，用于验证比较规则的边界。反例一："餐饮,出差"——字符串而非数组，结构非法。反例二：["餐饮","餐饮 "]——第二个元素尾随空格，规整后与首个重复，若去重后合法则只保留 "餐饮"；但若原始写入未通过 trim 预处理则整体拒绝。反例三：["__system_internal"]——命中保留前缀，拒绝。反例四：null——非法，与缺失语义不同。

### 4.5 常见错误

错误一：以逗号拼接字符串代替数组，如 "餐饮,出差"。标签本身含逗号时（"东京,浅草"）各端 split 结果不一致，数据在多端同步后标签集合漂移。规范是接口层只收数组。错误二：大小写处理不一致。移动端按大小写敏感去重、服务端按不敏感去重，同一用户在两端看到不同数量的标签。比较规则必须全端统一并在文档写死。错误三：把高频变化的信息放进标签，例如把 "2024-06" 这类月份标签逐月新建，两年后标签表膨胀数百项，筛选器不可用。时间维度应使用账目日期字段过滤，标签只放稳定语义。错误四：静默删除。升级时脚本清洗「不规范标签」直接从历史记录中移除，导致历史账目的标签集合与用户记忆不符，引发客诉。正确做法是孤儿标签保留并标注。错误五：数量超限静默截断，客户端只发前 10 个标签丢弃其余且不提示，用户以为全部保存成功。超限必须显式报错由用户决定取舍，而非服务端替用户做主。
