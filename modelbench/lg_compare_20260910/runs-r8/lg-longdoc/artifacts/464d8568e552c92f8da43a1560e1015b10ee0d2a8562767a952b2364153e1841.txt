# 迷你记账字段参考手册

**版本：v1.0**
**适用范围：迷你记账（Mini Ledger）数据层核心字段规范**
**文档目的：统一 id / amount / currency / tags 四个核心字段的定义、类型、约束、示例与常见错误认知，供前后端开发、测试、数据迁移及运维人员共同遵守。**

---

## 第一章 字段总览

迷你记账作为一款轻量级记账工具，其数据模型围绕“一笔交易记录”展开。每一笔交易记录在持久化时，必须携带四个核心字段：`id`、`amount`、`currency`、`tags`。这四个字段共同构成了一条记账记录的最小完备集：

- `id` 回答“这笔记录是谁”——它提供唯一性标识，是所有关联、索引、同步与幂等控制的基石；
- `amount` 回答“这笔记录金额是多少”——它是记账业务的核心数值，直接决定账目平衡与统计结果；
- `currency` 回答“这笔记录用什么货币计价”——它决定了金额的语义边界，缺少币种的金额是没有意义的数字；
- `tags` 回答“这笔记录如何归类与检索”——它承载用户的分类诉求，是查询、报表与个性化统计的入口。

四个字段看似简单，但在实际开发与使用中，围绕它们产生的缺陷占了记账模块缺陷总量的相当大比例。典型问题包括：主键冲突、浮点精度丢失导致账目对不平、货币代码大小写不一致导致同币种被拆成两类、标签越界导致存储膨胀、标签排序不确定导致前端渲染闪烁等。本手册逐字段展开五个小节——定义、类型、约束、示例、常见错误——力求把每一个字段的边界条件讲透。

阅读本手册时，请注意以下三条全局约定：

1. 本手册描述的序列化格式以 JSON 为准，但类型约定同样适用于数据库列定义与内部对象模型；
2. 所有涉及“必须”的表述为硬性要求，违反即为缺陷；所有涉及“建议”的表述为最佳实践，违反需在评审中说明理由；
3. 示例中给出的 JSON 片段均为单字段或局部片段，实际完整记录结构以数据模型文档为准。

## 第二章 id 字段

### 2.1 定义

`id` 是一笔交易记录的唯一标识符，在整个系统生命周期内（包括跨设备同步、导出、备份恢复等场景）保持不变。它是记录的主键，承担以下职责：

**唯一性锚点。** 任何两条不同的记录不得拥有相同的 `id`。当用户在离线状态下的手机端记账，随后数据同步到云端与平板端时，`id` 是判断“这是同一条记录还是两条冲突记录”的唯一依据。

**幂等性保障。** 客户端因网络重试而重复提交同一条创建请求时，服务端依据 `id` 判重：若 `id` 已存在则返回既有记录而非新建，从而避免网络抖动导致同一笔账被记两次。

**外部引用目标。** 编辑、删除、关联附件、评论、分期计划等功能都通过 `id` 引用目标记录。日志、审计与问题排查也以 `id` 为线索串联事件。

**排序稳定性的次级依据。** 当两条记录业务时间相同时，常以 `id` 作为追加的稳定排序键，避免分页查询在相邻请求间出现记录跳变或重复。

从语义上说，`id` 是纯粹的标识，**不含任何业务含义**。它不表示创建顺序（尽管特定生成算法可能恰好递增，但不能依赖这一点），不编码用户信息，不携带时间信息（不要为了“看一眼就知道是哪天的账”而在 `id` 里塞日期）。

### 2.2 类型

`id` 的规范类型为**字符串**，采用格式 `v1.<时间戳毫秒>-<随机段>-<节点段>`，例如 `v1.1719443200000-x7Kp9qR2-nodeA3f`。各段说明：

- **版本前缀 `v1.`**：预留的格式版本号，未来若更换生成算法，新记录可用 `v2.` 前缀，解析器据此兼容历史数据；
- **时间戳段**：64 位 Unix 毫秒时间戳的十进制表示，取自生成时的本机时钟（同步后不做回改）；
- **随机段**：8 个字符，取自密码学安全随机源，字符集为 `[A-Za-z0-9]`；
- **节点段**：设备或服务节点的短标识，用于大幅降低分布式场景下的碰撞概率。

选择字符串而非整数的原因：客户端离线优先的架构意味着记录往往在客户端生成 `id`，数据库自增整数在此场景下要么暴露集群细节、要么需要中心化发号；字符串型、客户端可独立生成的方案消除了这一依赖。所有对外接口（HTTP、导出文件）中，`id` 一律以字符串传输，即使某些历史数据恰好形如纯数字。

存储侧：数据库中以定长或限长字符串列存储（最大 64 字符），建立唯一索引。索引类型建议使用哈希索引或默认 B+ 树均可，等值查询是唯一访问模式，禁止对 `id` 做范围或模糊查询——那不是它的职责。

### 2.3 约束

1. **全局唯一且永久不变。** `id` 一经生成，禁止在任何场景下被修改。用户“删除再重建”产生的必须是一条新记录、新 `id`。
2. **长度：14 至 64 字符。** 下限保证各段不缺失，上限防止滥用 `id` 携带冗余数据。
3. **字符集：`[A-Za-z0-9.]`，且必须以 `v` 开头。** 禁止空格、中文、表情符号、控制字符。该字符集在 URL path、文件名、JSON key 值等场景均无需转义。
4. **区分大小写。** `AbC123` 与 `abc123` 是两个不同的 id。序列化、存储、比较全链路必须保持字节级一致，禁止任何环节做大小写折叠。
5. **禁止复用已删除记录的 id。** 即便记录被物理删除，其 `id` 也不得分配给新记录，否则外部缓存、导出文件中的旧引用会指向错误数据。
6. **客户端生成优先。** 创建请求必须由客户端预先填好 `id`，服务端不得在创建路径上静默替换客户端 id（那会破坏幂等）。
7. **非空、非全空白。** 空字符串、`null`、`undefined` 均为非法值，创建时缺失直接拒绝。

### 2.4 示例

合法示例：

```json
{ "id": "v1.1719443200000-x7Kp9qR2-nodeA3f" }
```

```json
{ "id": "v2.1719443205432-000000Ab-edge07" }
```

```json
{ "id": "v1.1700000000000-Zz9Zz9Zz-local01" }
```

非法示例（并附原因）：

```json
{ "id": 1719443200000 }          // 类型错误：数字，非字符串
{ "id": "1719443200000" }        // 缺少版本前缀与随机段
{ "id": "v1.1719443200000-x7Kp9qR2 nodeA3f" }  // 含空格
{ "id": "" }                     // 空字符串
{ "id": "v1.1719443200000-x7Kp9qR2-节点A" }    // 含非 ASCII 字符
```

幂等交互示例：客户端 A 发送 `POST /records`，body 含 `id=v1.1719443200000-x7Kp9qR2-nodeA3f`；网络超时后重试同一请求，服务端发现该 id 已存在，返回 `200` 与既有记录（而非 `201`），不产生新行。

### 2.5 常见错误

**错误一：用数据库自增整数当对外 id。** 表现：接口返回 `"id": 42`。危害：离线创建无法预生成 id，分库分表后冲突，导出再导入后 id 变化导致外部引用断裂。纠正：对外一律使用字符串 id，自增列只能作为内部物理主键。

**错误二：用 `user_id + 自增序号` 拼接复合 id。** 表现：`"id": "u8817-1042"`。危害：跨用户共享（如家庭账本）时复合语义崩溃；序号重置后碰撞。纠正：id 不承载归属信息，归属由独立的关联字段表达。

**错误三：大小写被中间层规范化。** 表现：某网关把 id 统一转小写，导致 `x7Kp9qR2` 与 `x7kp9qr2` 被视为同一条，两条真实记录被错误合并。纠正：全链路按字节精确比较，任何规范化处理视为缺陷。

**错误四：时间回拨导致的时间段重复加短随机段不足。** 表现：设备时钟回调后生成的 id 与历史 id 时间段相同，随机段碰撞概率上升。纠正：随机段使用密码学安全随机源且不少于 8 字符；检测到时钟回拨时在随机段中加入单调计数器。

**错误五：删除后复用 id。** 表现：用户删除一条记录后立即新建，新记录拿到了旧 id，手机上残留的本地缓存把新记录渲染成旧内容。纠正：id 生成器永不回收已发布的 id。

**错误六：在 URL 中未对 id 做 path 段校验。** 表现：`GET /records/<id>` 直接拼接，攻击者传入 `../../admin` 造成路径穿越。纠正：入口处校验 id 匹配 `^v\d+\.[A-Za-z0-9.\-]{10,61}$`，不匹配即返回 400。

## 第三章 amount 字段

### 3.1 定义

`amount` 是一笔交易的金额，是记账系统的核心业务数值。它记录“多少钱发生了变动”，配合记录类型（支出/收入/转账）表达资金流向。

**语义约定：`amount` 恒为非负数。** 本系统中金额的“方向”由记录类型字段表达，`amount` 只表达“量”。支出 50 元记为 `amount=50` + 类型“支出”，而不是 `amount=-50`。这一约定消除了“负数支出到底是支出还是收入”这类历史遗留的歧义，使所有统计可以直接对 `amount` 求和按类型分组。

**精度语义：十进制精确数。** 金额是十进制概念，生活中不存在“0.1 元的三分之一”这类需要无限小数的记账场景；所有合法金额都能表示为有限小数。因此 `amount` 在计算与存储中必须保持十进制精确，禁止用 IEEE 754 二进制浮点数承载。

**币种依赖性。** `amount` 的数值只有结合同记录的 `currency` 才有完整语义。"100"本身无意义，"100 CNY"才是完整的一笔金额。因此 amount 与 currency 必须原子地写入、读取与校验，二者不可分离处理。

**与“分”的关系。** 内部计算与存储建议以最小货币单位（如分）的整数进行，`amount` 是对外的人读表示。两者换算必须无舍入误差（见约束部分的小数位数规则）。

### 3.2 类型

**对外 JSON 类型：字符串形式的十进制数**（推荐）或十进制精确数类型。规范形式为：

```
^(0|[1-9]\d*)(\.\d{1,8})?$
```

即：无符号、无前导零（单独的 0 除外）、整数部分至少一位、小数部分 1 到 8 位。

选择“字符串承载十进制数”的原因：JSON 的 `number` 类型按惯例由 IEEE 754 双精度浮点实现，`0.1 + 0.2 !== 0.3` 的精度缺陷在金额累加场景是致命的——1000 笔 0.1 元的记录求和可能出现 99.99999999999983，账目对不平。字符串序列化配合各端 Decimal 类型解析，可全程无损。

**内部类型：** 服务端与数据库以**整数**存储——按币种最小单位换算后的整数（CNY/USD 等两位小数币种存“分”，JPY 等零位小数币种存“元”，支持八位小数的加密或特殊币种存最小单位）。整数运算天然精确，汇总、分摊、对账全部在整数域完成，仅在展示层转换为人读字符串。

**展示类型：** 前端展示时格式化为 `#,##0.00` 等本地化格式，但编辑回传、接口传输、存储的永远是规范形式，展示格式不得回写。

**明确禁止的类型：** `float`、`double`、`FLOAT`、`DOUBLE`、`REAL` 数据库列型；JavaScript `Number` 直接参与金额运算；任何把金额转二进制浮点再转回十进制的链路。

### 3.3 约束

1. **数值范围：0 ≤ amount ≤ 999,999,999,999.99999999**（最大约一万亿，八位小数）。超出即拒绝，防止溢出与恶意值。
2. **恒非负。** 负数、带正负号的字符串（`+50`、`-50`）均为非法。
3. **小数位数不得超过所属币种的法定小数位。** CNY/USD/EUR 为 2 位，JPY/KRW 为 0 位，BHD/KWD 等为 3 位。校验时须结合 `currency` 联合判定：`amount="10.5"` 配 `currency="JPY"` 非法，配 `currency="CNY"` 合法。这是 amount 与 currency 的联合约束，任一字段变更都必须重新校验。
4. **禁止科学计数法。** `1e5`、`5E-3` 均非法，必须写为 `100000`、`0.005`。
5. **禁止千分位分隔符与货币符号。** `"1,234.50"`、`"¥50"` 非法，分隔符与符号只属于展示层。
6. **零值合法但需业务确认。** `amount="0"` 在类型上合法（如报销冲销、赠品入账），但创建接口应在响应中携带零值提示标记，避免用户误操作。
7. **不可变性与修正方式。** 已入账记录的 `amount` 原则上不可修改；确需更正时走“红冲/反向记录”流程，保留审计轨迹，而非原地 UPDATE。
8. **分摊求和守恒。** 多人多账户分摊一笔金额时，各分摊项按最小单位整数分摊，最后一份承接全部余数，保证分摊项之和严格等于总额，不差一分。

### 3.4 示例

合法示例：

```json
{ "amount": "50",       "currency": "CNY" }   // 整数元
{ "amount": "50.00",    "currency": "CNY" }   // 两位小数补齐
{ "amount": "0.01",     "currency": "CNY" }   // 最小单位
{ "amount": "12345.67", "currency": "USD" }
{ "amount": "3000",     "currency": "JPY" }   // 零小数位币种
{ "amount": "1.234",    "currency": "BHD" }   // 三位小数币种
{ "amount": "0",        "currency": "CNY" }   // 合法零值
```

非法示例：

```json
{ "amount": -50 }              // 负数
{ "amount": "50.001", "currency": "CNY" }   // 超出币种小数位
{ "amount": "1e5" }            // 科学计数法
{ "amount": "1,234.50" }       // 千分位分隔符
{ "amount": "¥50" }            // 货币符号
{ "amount": "007.5" }          // 前导零
{ "amount": 0.1 }              // JSON number（浮点）承载，禁止
```

精度对比示例：对 `0.1` 累加 1000 次——二进制浮点得到 `100.00000000000014`；十进制精确计算得到 `100.00`。后者才允许进入账目。

### 3.5 常见错误

**错误一：用浮点数类型存金额。** 表现：数据库列定义为 `DOUBLE`，或 JS 中 `0.1 + 0.2` 后直接存库。日积月累的尾差使月度对账永远差几分钱。纠正：数据库用 `DECIMAL(20,8)` 或整数分列；JS 用字符串传输 + Decimal 库运算。

**错误二：允许负数表示支出。** 表现：老版本客户端写入 `amount=-50`，统计求和时支出收入相互抵消，报表全错。纠正：校验层强制非负，方向由类型字段表达；存量负值数据迁移时按类型翻转符号。

**错误三：忽略币种小数位。** 表现：日元记录出现 `3000.50`，入库成功，聚合时被四舍五入到 `3001`，与银行流水对不上。纠正：维护币种元数据表（代码 → 小数位），校验与换算统一引用。

**错误四：展示格式回写。** 表现：前端把格式化后的 `"1,234.50"` 直接 PUT 回服务端。纠正：编辑控件内部维护原始规范字符串，仅渲染层做格式化。

**错误五：四舍五入分摊。** 表现：100.00 元三人分摊，每人 33.33，丢弃了 0.01。纠正：整数分摊 + 尾数归最后一份。

**错误六：字符串比较金额大小。** 表现：`"9" > "10"` 为真（字典序），导致阈值过滤错误。纠正：比较前必须解析为 Decimal/整数，禁止字典序比较。

## 第四章 currency 字段

### 4.1 定义

`currency` 是记录金额所使用的货币币种标识，采用 **ISO 4217 货币代码**表示。它赋予 `amount` 数值以计量语义：同样是 `"100"`，配 `CNY` 是 100 元，配 `JPY` 是 100 日元，二者价值悬殊。

`currency` 的职责包括：

**计量归属。** 声明金额的计价单位，是金额参与任何汇总、换算、对账的前提。没有 currency 的 amount 在业务上是残缺数据。

**展示依据。** 前端根据货币代码确定货币符号（¥ / $ / €）、小数位数、千分位规则与摆放位置（如法郎符号后置）。注意：货币符号只用于展示，**符号不能替代代码**——`¥` 同时被 CNY 与 JPY 使用，仅凭符号无法消歧。

**换算输入。** 跨币种统计（如用户持有多币种账目，看统一折算的本币总额）时，currency 是查询汇率、执行换算的键。

**合规与对账边界。** 与银行/支付渠道对账时，币种是流水匹配的必要条件；错币种匹配会产生严重的资损误判。

本系统支持 ISO 4217 中的常用法定货币及少量高精度货币，不支持虚构币种代码；加密货币如需支持，走扩展机制并使用独立命名空间，不占用 ISO 4217 码位。

### 4.2 类型

**规范类型：3 字符大写拉丁字母字符串**，格式 `^[A-Z]{3}$`，即 ISO 4217 alphabetic code。例如 `CNY`、`USD`、`EUR`、`JPY`、`GBP`、`HKD`、`BHD`。

**存储：** 数据库以 `CHAR(3)` 定长列存储，配合字符集校验；并建议与币种元数据表（代码、英文名、本地化名、符号、小数位、启用状态）做外键或应用层引用校验，杜绝“格式对但不存在”的代码（如 `XXX` 虽是合法 ISO 代码“无货币”，业务上是否允许需单独决策，本系统默认禁用）。

**接口传输：** 一律大写三字母。输入为小写（`cny`）或混合大小写（`Cny`）时，规范入口（创建/更新接口）应拒绝并返回明确错误；查询过滤入口可选地做大小写归一以提高容错，但归一结果必须记录在日志中。

**辅助属性（存于元数据表，不存于记录）：** numeric code（数字码，如 CNY=156）、minor unit（小数位）、symbol、 displayName 的各语言翻译。记录本体只存三字母代码，其余属性按需关联查询，避免记录膨胀与元数据多副本不一致。

### 4.3 约束

1. **格式：严格匹配 `^[A-Z]{3}$`。** 长度必须为 3，必须全大写拉丁字母，禁止数字（那是 numeric code 的职责）、禁止空格与连字符。
2. **必须命中币种元数据表且状态为“启用”。** 格式合法但未启用/已停用的代码（如历史遗留的旧国代码货币）拒绝写入。
3. **与 amount 的联合校验。** 见第三章约束 3：amount 的小数位数不得超过 currency 的小数位。币种变更时必须连带重校 amount。
4. **记录创建后默认不可变更。** 币种是金额语义的一部分，改币种等于换了一笔账。确需变更走“作废重建”或“红冲重建”流程。
5. **同币种归一。** `CNY` 与 `cny` 在系统内只能存在一种规范形态（大写），任何入口不允许产生第二种形态的持久化数据。
6. **跨币种禁止直接算术。** 不同 currency 的 amount 不得直接相加减比较，必须先经显式换算（使用带时间戳的汇率），换算中间值保留精度。
7. **默认值策略。** 用户未显式选择币种时，可按应用 locale 预填默认币种（如 zh-CN → CNY），但预填值必须在界面上可见可改，不得静默写入。
8. **禁止特殊代码。** `XXX`（无货币）、`XTS`（测试代码）默认禁用；测试环境如需 XTS，必须显式开启配置开关。

### 4.4 示例

合法示例：

```json
{ "currency": "CNY", "amount": "88.50" }
{ "currency": "USD", "amount": "12.99" }
{ "currency": "JPY", "amount": "1500" }
{ "currency": "EUR", "amount": "0.01" }
{ "currency": "BHD", "amount": "3.500" }
```

非法示例：

```json
{ "currency": "cny" }    // 小写
{ "currency": "CN" }     // 两位，这是国家代码不是货币代码
{ "currency": "USDT" }   // 四位
{ "currency": "RMB" }    // 民间俗称，非 ISO 4217 代码（正确为 CNY）
{ "currency": "¥" }      // 符号不是代码
{ "currency": "" }       // 空
{ "currency": " US" }    // 含空格
```

联动校验示例：请求 `{ "currency": "JPY", "amount": "100.50" }` → 返回 400，错误信息：“币种 JPY 的小数位为 0，金额 100.50 的小数位数超出限制。”

换算示例：用户将 100 USD 记账折算为 CNY 报表——取当日汇率 7.18（记录换算时刻），整数域计算 10000 分 × 7.18 = 71800 分 = 718.00 CNY，换算快照随报表缓存，汇率更新不追溯已生成的历史报表。

### 4.5 常见错误

**错误一：大小写不归一。** 表现：老客户端上传 `cny`，新客户端上传 `CNY`，GROUP BY 后出现两个“币种”，报表重复。纠正：入口强校验大写；存量数据一次性迁移归一；数据库列加 `CHECK` 约束兜底。

**错误二：用货币符号当币种字段。** 表现：iOS 端存了 `"¥"`，导致 CNY 与 JPY 记录无法区分。纠正：符号仅存在于展示层映射表，持久化只存三字母代码。

**错误三：使用非 ISO 俗称。** 表现：`RMB`、`NT`、`HK` 混入代码集。纠正：维护白名单校验，校验失败返回“建议代码”提示（如 `RMB → CNY`）。

**错误四：换算后直接舍入存储。** 表现：0.01 KWD 折算 CNY 后被截断为 0.02，尾差累积。纠正：换算全程高精度（建议保留 8 位中间精度），仅在最终落账位按业务规则（银行家舍入）收敛一次。

**错误五：漏配小数位元数据。** 表现：新增币种只加进下拉框，忘了元数据表的小数位字段，默认按 2 位校验，导致 BHD 的 `3.500` 被误拒。纠正：币种新增必须完整登记元数据，校验器对“元数据缺失”直接报错而非取默认值。

**错误六：跨币种直接求和。** 表现：报表把 100 CNY 与 100 USD 相加得 "200"，单位不明。纠正：聚合入口强制分组维度含 currency，或强制指定折算目标币种与汇率快照。

## 第五章 tags 字段

### 5.1 定义

`tags` 是一笔记录的标签集合，承载用户的分类、标记与检索诉求。与 `amount`、`currency` 不同，tags 不影响金额语义，它是**描述性、可演化的元数据**。

**集合语义。** tags 是一个**无序、去重**的字符串集合。`["餐饮","午餐"]` 与 `["午餐","餐饮"]` 语义等价。任何依赖数组顺序的逻辑（排序展示除外）都视为设计缺陷。

**多值并列。** 一条记录可同时持有多个标签，如一笔同事聚餐可同时打 `餐饮`、`团建`、`报销`，与单选的“分类”字段互补。

**自由与管控的平衡。** 本系统允许用户自建标签（受格式与数量约束），但提供系统推荐标签集以引导规范。标签不强制来自固定字典——这是它与“分类”字段的关键差异，也决定了它必须有更严格的规模与格式约束，防止滥用。

**检索与报表入口。** tags 支持精确匹配与多标签 AND/OR 组合查询；周报、月报可按标签聚合。因此标签的规范化程度直接决定报表质量：`聚餐`、`聚餐 `（尾随空格）、`聚餐！` 会被视为三个不同标签，统计被人为割裂。

**版本化与历史。** 标签重命名（如 `餐饮` 改为 `吃喝`）通过标签实体层的别名机制实现，记录内存储的标签字符串保持写入时原值或由系统统一迁移——迁移必须原子，禁止同一批数据新旧标签混存于一个统计周期。

### 5.2 类型

**规范类型：字符串数组**，JSON 形如：

```json
{ "tags": ["餐饮", "午餐", "报销"] }
```

- 数组元素类型：字符串，单个标签 1–24 个字符（按 Unicode 码点计），允许中文、拉丁字母、数字、连字符 `-`、下划线 `_`、点 `.`；首尾不得为空白；禁止控制字符与表情符号（避免字体与排序兼容性问题）。
- 数组长度：0–10 个。`[]` 合法，表示未打标签；超过 10 个拒绝写入。
- 去重：写入前按 NFC Unicode 规范化 + 去除首尾空白 + 精确去重，重复项静默合并。
- **顺序约定：逻辑无序。** 持久化与接口返回时按**码点字典序**排序输出（规范化输出），前端如需展示顺序（如按用户使用频率）应在展示层另行排序，不得依赖存储顺序。
- **存储：** 关系型场景使用关联表 `(record_id, tag)`，主键 `(record_id, tag)`；文档型场景直接内嵌数组，但需为数组建多键索引以支撑标签查询。
- **明确禁止：** 嵌套对象元素（`[{"name":"餐饮","color":"red"}]`——样式属性属于标签实体层，不属于记录内嵌值）；逗号拼接的单字符串（`"餐饮,午餐"`）；`null` 元素。

### 5.3 约束

1. **元素数 0–10，单标签 1–24 字符**，超出即整体拒绝（不做静默截断，避免用户不知情丢失标签）。
2. **写入时三步规范化：NFC 规范化 → trim → 精确去重。** 规范化后为空字符串的元素导致请求拒绝。
3. **禁止保留字前缀 `sys:`。** 该命名空间保留给系统标签（如 `sys:对账完成`），用户输入含 `sys:` 前缀的标签一律拒绝。
4. **数量限额。** 单用户自定义标签总数上限 200 个；达到上限后新建标签被拒并提示管理已有标签，防止标签爆炸稀释统计价值。
5. **删除记录不删标签实体。** 标签实体与记录多对多；记录删除仅解除关联，标签字典保留（含使用计数），用户可显式清理零使用标签。
6. **查询组合约束。** 单次查询 AND 条件数 ≤ 5，防止组合爆炸拖垮索引；查询接口对不存在的标签返回空结果集而非报错（标签存在性是常态变化）。
7. **迁移原子性。** 标签重命名/合并是元数据事务：先建别名映射，再批量更新关联，最后更新字典；过程中报表查询走读旧一致性视图，避免半更新状态。
8. **聚合口径稳定。** 报表按标签聚合时使用“查询时刻的关联快照”，用户事后改标签不追溯已发出的历史报表。

### 5.4 示例

合法示例：

```json
{ "tags": [] }
{ "tags": ["餐饮"] }
{ "tags": ["餐饮", "午餐", "报销"] }
{ "tags": ["2024-旅行", "日本", "交通"] }
{ "tags": ["grocery.weekly"] }
```

规范化效果示例：

```
输入: [" 午餐", "午餐", "午餐"]        // 首空格 + 重复 + 另一标签
输出: ["午餐", "午餐"]
```

```
输入: [" café", "café"]   // 组合字符 NFC 归一后相同
输出: ["café"]
```

非法示例：

```json
{ "tags": "餐饮,午餐" }            // 字符串而非数组
{ "tags": ["餐饮", ""] }           // 规范化后空元素
{ "tags": ["a", "b", "c", "d", "e", "f", "g", "h", "i", "j", "k"] }  // 11 个超限
{ "tags": ["sys:已对账"] }         // 保留字前缀
{ "tags": [null, "餐饮"] }         // null 元素
{ "tags": [{"name": "餐饮"}] }     // 对象元素
```

查询示例：`GET /records?tags=餐饮,报销&match=and` 返回同时含两标签的记录；`match=or` 返回含任一标签的记录。

### 5.5 常见错误

**错误一：把 tags 当有序数组使用。** 表现：前端取 `tags[0]` 当作“主分类”，而存储序无保障，同一条记录在不同端显示的主分类不同。纠正：主分类是独立概念，若业务需要应设专门的单值字段；tags 逻辑无序，输出固定按码点排序。

**错误二：不规范化直接入库。** 表现：`"餐饮 "`（尾空格）与 `"餐饮"` 并存，按标签统计时数字分裂。纠正：写入层统一 NFC + trim + 去重；同时提供一次性的历史数据清洗任务。

**错误三：用逗号拼接字符串塞进单元素数组。** 表现：`["餐饮,午餐,报销"]` 成为一个 12 字符的“标签”，查询 `餐饮` 查不到该记录。纠正：客户端拆分逻辑修正在发送侧；服务端检测元素内含逗号即拒绝并提示。

**错误四：无限建标签。** 表现：用户两年积累上千个标签，标签云与下拉框不可用，报表碎片化。纠正：总量限额 + 建议复用 + 零使用标签清理入口。

**错误五：删除记录时级联删标签字典。** 表现：清理 50 条历史记录后，标签字典里常用标签消失，其他仍在使用这些标签的记录显示异常。纠正：解除关联而非删除实体；删除实体仅允许显式管理操作且校验使用计数为零。

**错误六：对象元素污染。** 表现：某端把样式信息（颜色、图标）内嵌进数组元素，其他端解析崩溃。纠正：元素必须是纯字符串，样式归属标签实体层，记录侧仅存名称引用。

**错误七：重命名非原子。** 表现：改名任务中途失败，一半记录用新名、一半用旧名，当月报表两个标签各占一半金额。纠正：元数据事务 + 一致性视图 + 失败自动回滚。

## 第六章 字段协同与联合校验要点

四个字段并非孤立，以下联合规则在所有写入与变更路径上必须整体执行：

1. **原子完整性。** 创建请求四个字段必须同时在场且全部通过校验，任一失败则整条拒绝，不产生半成品记录。
2. **amount × currency 联合校验。** 小数位上限取自 currency 元数据（见第三、四章）。
3. **tags 规范化先于唯一性判定。** 判重、索引、统计均基于规范化后的集合。
4. **变更传播。** currency 不可变更；amount 修正走红冲；tags 可自由增删但受数量与格式约束；id 永不变更。
5. **校验顺序建议：** id 格式 → currency 格式 → currency 元数据存在性 → amount 格式 → amount × currency 联合校验 → tags 规范化 → tags 约束。先便宜的格式校验，后昂贵的元数据查询。

本手册四个字段、每字段五节（定义、类型、约束、示例、常见错误）内容至此全部呈现完毕。各团队在实现中如遇本手册未覆盖的边界情形，应先按“定义”一节的精神推导语义，再提交规范评审补充条款，禁止在实现层私自发明语义。
