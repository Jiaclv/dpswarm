# 迷你记账字段参考手册

**版本：1.0　适用系统：迷你记账　文档性质：字段级技术参考**

---

## 前言

本手册是《迷你记账》系统中交易记录核心数据字段的权威参考文档，面向系统开发者、数据工程师、测试工程师以及负责数据清洗与迁移的运维人员。手册系统性地覆盖四个核心字段：`id`、`amount`、`currency`、`tags`，每个字段均按统一结构展开为五个小节：定义、类型、约束、示例、常见错误。阅读本手册后，读者应能够准确理解每个字段的语义边界、格式要求与校验规则，并能在实际开发、联调与数据治理工作中正确地生成、解析与校验这些字段。

本手册所描述的字段规格自 1.0 版起冻结为稳定接口契约。任何对字段语义或格式的变更，必须先修订本手册并同步版本号，方可实施。文中出现的所有 JSON 片段均为示意性表述，实际传输编码以系统接口规范为准。

## 字段一：id

### 1.1 定义

`id` 是迷你记账系统中每一条交易记录的唯一标识符，是整个数据模型的主键。它在系统内部承担三项职责：其一，作为记录的身份锚点，使任何一条交易在空间维度上（跨表、跨服务、跨端）和时间维度上（增删改、同步、审计回溯）都可被无歧义地定位；其二，作为外键引用的来源，分类流水、账户余额调整、对账记录、附件索引等派生数据均通过 `id` 与交易记录建立关联；其三，作为幂等性控制的依据，客户端在弱网环境下重试写入时，服务端依据 `id` 判定是否为重复请求，从而避免同一笔交易被重复入库。

`id` 的语义是"标识"而非"描述"：它不携带任何业务含义，不得用于表达交易时间、交易类别、用户属性等信息。系统明确禁止从 `id` 中推导任何业务结论——例如禁止假设 `id` 的字典序等于创建时间顺序、禁止从 `id` 中截取子串当作时间戳使用。这一"无语义化"设计使系统在更换存储引擎、分库分表、跨区域同步时不受标识符结构变化的牵制。

### 1.2 类型

`id` 在逻辑上为**字符串类型**（UTF-8 编码），采用 UUID v4 格式作为推荐实现：由 32 个十六进制字符组成，按 8-4-4-4-12 的分组以连字符连接，总计 36 个字符。UUID v4 由密码学安全的随机源生成，碰撞概率在工程上可忽略，且生成过程无需中央协调节点，天然适配离线记账与多端同步场景。

在底层存储中，`id` 以定长字符串或 128 位二进制（取决于存储引擎）保存；在接口层，`id` 永远以字符串形式出现，即使某些存储引擎内部将其表示为二进制或整数，序列化为接口报文时必须还原为标准字符串格式。系统不允许将 `id` 实现为自增整数：自增整数在多端写入时会引发主键冲突，且会向外部泄露记录规模信息。

### 1.3 约束

- **唯一性**：在同一用户的数据域内，`id` 必须全局唯一，任何写入操作若检测到重复 `id` 且请求非幂等重放，必须拒绝。
- **不可变性**：`id` 一经生成，终身不变。不允许以任何理由（包括数据修复、账户合并）修改已有记录的 `id`；确需"替换"标识时，采用新记录 + 归档旧记录的方式，并保留映射关系。
- **格式**：必须匹配正则 `^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`（小写十六进制，标准连字符）。
- **长度**：固定 36 字符，禁止前后空白字符，禁止大小写混用。
- **非空**：`id` 为必填字段，缺失即视为非法报文。
- **随机性来源**：生成时必须使用密码学安全随机数生成器，禁止使用基于时间戳、计数器或可预测种子的伪随机方案。
- **引用完整性**：被任何派生数据引用中的 `id` 对应记录不得物理删除，只允许逻辑删除。

### 1.4 示例

合法示例：

```
"id": "3f8a2c1e-9b4d-4e7a-8c2f-1d6b9a0e5c34"
"id": "a1b2c3d4-e5f6-4a7b-8c9d-0e1f2a3b4c5d"
```

非法示例（用于对照）：

```
"id": "12345"                                  ← 非UUID格式
"id": "3F8A2C1E-9B4D-4E7A-8C2F-1D6B9A0E5C34"   ← 大写，违反小写规范
"id": "3f8a2c1e9b4d4e7a8c2f1d6b9a0e5c34"       ← 缺少连字符
"id": "3f8a2c1e-9b4d-9e7a-8c2f-1d6b9a0e5c34"   ← 版本位非法（v9不存在）
```

生成与校验的参考流程：客户端在创建交易草稿时即生成 `id`；提交前本地校验格式；服务端接收后二次校验格式与唯一性；同步链路上，两台设备离线各自生成的 `id` 因随机性而天然不冲突。

### 1.5 常见错误

1. **大小写不一致**：同一记录在不同端分别以大写与小写形式出现，导致唯一性判断失效。规范要求一律小写，入库前统一归一化。
2. **重复生成**：部分旧代码使用 `Math.random()` 拼接时间戳伪造 UUID，随机熵不足，在批量导入时出现碰撞。必须改用标准 UUID v4 库。
3. **二次修改**：数据迁移时为了"规整"而批量重新生成 `id`，导致派生数据的外键全部悬空。`id` 不可变是硬性红线。
4. **当作排序键**：报表模块按 `id` 排序并误当作时间序展示，随机 UUID 的字典序与时间无关，必须显式按时间字段排序。
5. **类型漂移**：某些序列化框架将纯数字开头的字符串误转为数值类型，丢失精度并破坏格式。接口层必须显式声明字符串类型。
6. **空白污染**：手工录入或复制粘贴引入首尾空格与不可见字符，校验失败且错误难定位。解析层应先 trim 再校验。

## 字段二：amount

### 2.1 定义

`amount` 表示一笔交易的金额数值，是迷你记账系统业务语义的核心。它统一表达两类方向的交易：正数表示收入（资金流入），负数表示支出（资金流出），零值在业务上仅允许出现在冲销或占位记录中。`amount` 永远以"该币种的最小货币单位"的整数形式表达——即对人民币、美元、日元等按元/角/分体系计价的币种，`amount` 以"分"为单位存储（例如 12.34 元存储为 1234）；这一整数化设计从根本上规避了浮点运算的精度陷阱。

`amount` 的符号语义与交易类型字段解耦：系统不依赖"金额恒为正数 + 单独的方向字段"的表达方式，而是将方向编码进符号。这种设计的优势在于：求和、净额计算、对账平衡校验可以直接使用算术运算，无需按方向字段分支处理；劣势在于要求所有读写路径严格保证符号约定一致。本手册将其确立为唯一合法表达。

### 2.2 类型

`amount` 在逻辑与存储上均为**64 位有符号整数**（int64），单位为最小货币单位（分）。选择整数而非浮点数或十进制字符串的依据如下：

- **精度**：二进制浮点数（IEEE 754 double）无法精确表示 0.1 等十进制小数，累加运算会产生累积误差，记账系统对"分毫不差"有硬性要求，浮点方案被明确排除。
- **范围**：int64 可表示约 ±9.22×10¹⁸ 分，即约 ±922 亿亿元，远超任何个人记账场景的量级，不会溢出。
- **性能与确定性**：整数运算在所有平台上结果一致，无跨平台浮点差异。

在接口层，`amount` 同样以整数（JSON number，且必须为整数值）传输，禁止传输 "12.34" 这类小数形式的金额。金额的"元-分"换算只发生在展示层：展示层取 `amount` 除以 100（按币种精度，见 currency 字段章节）得到显示值。

### 2.3 约束

- **类型约束**：必须为 int64 整数，接口报文中出现小数、字符串、null、布尔值均非法。
- **符号约束**：正数表示收入，负数表示支出；`0` 仅允许出现在冲销、期初占位等经过审批的特殊记录中，普通交易禁止为 0。
- **非零约束**：常规录入路径上，`|amount| ≥ 1`（即至少一分钱），杜绝无意义零金额流水。
- **上限约束**：单笔金额绝对值不得超过 999999999999（对应 99.99 亿余元的显示值），超出该阈值的录入需走大额复核流程。
- **币种精度耦合**：`amount` 的最小单位必须与配对 `currency` 字段的最小单位一致。对于无小数位的币种（如日元），`amount` 直接以"元"为单位整数存储，换算倍率为 1 而非 100。
- **不可变与修正**：已入账交易的 `amount` 不可原地修改；发现错误必须以一笔符号相反、金额相等的冲销记录加一笔正确记录来修正，保证账目审计链完整。
- **求和溢出**：聚合计算时必须使用 int64 或更高位宽的累加器，禁止使用 double 累加。

### 2.4 示例

合法示例：

```
{"amount": 12500, "currency": "CNY"}    ← 收入 125.00 元
{"amount": -3999, "currency": "CNY"}    ← 支出 39.99 元
{"amount": 500,   "currency": "JPY"}    ← 收入 500 日元（无小数位币种）
{"amount": -105,  "currency": "USD"}    ← 支出 1.05 美元
```

非法示例：

```
{"amount": 12.34,  "currency": "CNY"}   ← 小数形式，必须换算为 1234
{"amount": "12500", "currency": "CNY"}  ← 字符串类型，非法
{"amount": 0,      "currency": "CNY"}   ← 常规路径零金额，非法
{"amount": 9999999999999, "currency": "CNY"} ← 超出单笔上限
```

换算演示：用户在界面输入 88.50 元选择人民币 → 系统换算 88.50 × 100 = 8850 → 存储 `amount: 8850`；展示时反向运算 8850 ÷ 100 = 88.50 → 渲染为 "¥88.50"。

### 2.5 常见错误

1. **浮点污染**：早期版本曾用 double 存储金额，出现 0.1 + 0.2 ≠ 0.3 类的经典误差，导致月度对账差一分钱。已强制整数化，历史数据迁移时必须四舍五入到分并人工抽检。
2. **换算倍率错误**：对日元等无小数币种错误地乘以 100，导致金额放大百倍。倍率必须由 `currency` 字段的精度定义驱动，不得硬编码。
3. **符号滥用**：个别模块将支出存为正数并在查询时取负，与其他模块口径冲突。符号约定全系统唯一：正收入、负支出。
4. **字符串金额**：为"保留前导零"或"避免精度丢失"而传输字符串金额，破坏了类型契约，应在序列化层显式声明整数类型。
5. **原地改金额**：用户编辑已入账交易时直接覆盖 `amount`，破坏了对账快照。必须走"冲销 + 重录"流程。
6. **展示层截断**：展示层用整数除法丢弃小数（8850 ÷ 100 显示 88 而非 88.50），应使用格式化函数保留两位小数。

## 字段三：currency

### 3.1 定义

`currency` 表示一笔交易金额所计价的币种，采用 ISO 4217 标准的三位字母货币代码作为唯一表达形式。它与 `amount` 字段构成不可分割的语义整体：脱离币种的金额数字是不完整的，"1000" 在日元语境下是一顿便饭，在人民币语境下是一笔大额消费。`currency` 的存在使迷你记账系统支持多币种记账、汇率换算与跨币种汇总报表。

`currency` 的取值域是封闭集合，由系统内置的币种字典定义，字典中每个条目包含：三位代码、货币名称、符号、小数位数（精度）、是否可用状态。字典版本随系统版本发布，用户不能自创币种代码。对于已停用的币种（历史交易仍在引用），字典采用"停用但保留"策略，保证历史数据可读，同时禁止新交易使用停用代码。

### 3.2 类型

`currency` 为**枚举型字符串**，取值限定为 ISO 4217 三位大写字母代码，如 `CNY`、`USD`、`EUR`、`JPY`、`GBP`、`HKD`。系统以枚举校验而非自由文本校验处理该字段：任何不在字典中的字符串一律拒绝。

精度信息是 `currency` 的派生属性而非独立字段：系统按 ISO 4217 定义维护每个代码的小数位数——人民币、美元、欧元为 2 位（最小单位为分/美分/欧分），日元为 0 位（最小单位为日元），科威特第纳尔为 3 位（最小单位为费尔）。该精度直接决定 `amount` 字段的换算倍率，是两个核心字段之间的契约纽带。

### 3.3 约束

- **格式**：必须为恰好 3 个大写拉丁字母（A-Z），匹配正则 `^[A-Z]{3}$`，禁止小写、数字、空白与混合字符。
- **枚举封闭**：必须命中系统币种字典中的有效条目；格式正确但字典未收录的代码同样拒绝。
- **必填**：`currency` 为必填字段，不允许缺省或 null；系统不提供"无币种"语义。
- **默认值策略**：客户端可依据用户偏好设置预填默认币种，但预填不等于免校验——用户显式修改后按新值校验。
- **与 amount 的一致性**：`amount` 的换算倍率必须取自该币种的精度定义；跨币种汇总前必须完成汇率换算，禁止把不同币种的 `amount` 直接相加。
- **历史稳定**：历史交易的 `currency` 一经写入不可修改；涉及币种更正时采用冲销重录流程。
- **停用兼容**：字典中标记为停用的代码，只允许出现在既有历史记录的读取路径上，写入路径必须拒绝。

### 3.4 示例

合法示例：

```
{"currency": "CNY", "amount": 2000}     ← 人民币 20.00 元
{"currency": "USD", "amount": -1500}    ← 美元支出 15.00
{"currency": "JPY", "amount": 800}      ← 日元收入 800
{"currency": "KWD", "amount": 250}      ← 第纳尔 0.250（3位精度）
```

非法示例：

```
{"currency": "cny"}      ← 小写，非法
{"currency": "CNY1"}     ← 含数字，非法
{"currency": "XYZ"}      ← 格式正确但不在字典中，非法
{"currency": ""}         ← 空串，非法（必填）
{"currency": "人民币"}    ← 中文名称非法，必须用 ISO 代码
```

多币种换算演示：账本内有两笔记录——`{amount: -500, currency: "EUR"}` 与 `{amount: -3000, currency: "CNY"}`。生成人民币汇总报表时，系统按当日汇率将 EUR 记录换算为 CNY 等值后再求和，原始记录保持原币种与原金额不变。

### 3.5 常见错误

1. **大小写混用**：接口对接方传入小写代码，服务端严格校验拒绝。应在文档中强调大写规范，或在边界层做大写归一化后再校验。
2. **直接相加跨币种金额**：报表模块忽略币种直接求和，产生无意义数值。汇总前必须换算为统一目标币种。
3. **精度硬编码**：代码中假定所有币种都是 2 位精度，处理日元或第纳尔时金额错误。精度必须查表获取。
4. **使用非标准代码**：自造 "RMB"（非 ISO 代码，正确为 CNY）或 "US$" 等表达，导致校验失败与数据不一致。
5. **修改历史币种**：用户将历史交易的币种从 USD 改为 CNI 试图"换币种记账"，破坏原币语义。应引导用户新建记录。
6. **默认值吞没显式输入**：客户端在用户未感知的情况下静默使用默认币种，导致外币消费被记成本币。录入界面必须显式展示当前币种。

## 字段四：tags

### 4.1 定义

`tags` 是一笔交易的标签集合，用于承载自由度高于固定分类维度的补充语义，例如"报销""旅行-东京""妈妈生日"等。与单一、树状的分类字段不同，`tags` 允许一条交易同时挂载多个标签，且标签之间是扁平的多对多关系——一个标签可以被任意多条交易引用，一条交易也可以引用任意多个标签。这种设计让用户能够按正交维度交叉筛选，例如"本月所有带有『报销』标签的餐饮支出"。

`tags` 的语义定位是**用户自定义的轻量元数据**，服务于检索、筛选与统计切片；它不承担账务计算职责——汇总金额时系统按交易本身的分类与金额计算，标签只作为过滤条件参与。标签文本由用户创建与管理，系统维护全局标签字典以保证拼写一致，避免"报销"与"报消"分裂为两个标签。

### 4.2 类型

`tags` 为**字符串数组**（UTF-8），即有序但语义上视作集合的字符串列表。数组中每个元素为一个独立标签文本；空数组 `[]` 是合法值，表示该交易未打任何标签。单个标签在逻辑上是短文本（建议 1–12 个字符），支持中文、字母、数字与连字符；系统禁止标签文本中包含空白字符与控制字符，含空格的组合词应改用连字符书写（如 `trip-tokyo`）。

在存储层面，交易记录与标签通过关联结构实现多对多映射：交易侧保存标签 ID 列表或经规范化后的标签名列表，标签字典侧维护每个标签的引用计数，以支持"未引用标签清理"等治理功能。接口层统一以字符串数组形式表达。

### 4.3 约束

- **元素类型**：数组每个元素必须为非空字符串，禁止 null、数字、嵌套数组或对象混入。
- **单标签长度**：每个标签 1–24 个字符（UTF-8 码点位计），超出拒绝。
- **数量上限**：单笔交易最多 10 个标签，防止标签滥用导致筛选与统计性能劣化。
- **去重**：数组内不得出现重复标签；写入前按精确匹配去重，重复元素视为非法输入并拒绝（而非静默去重，以保证客户端行为可预期）。
- **字符集**：仅允许中文、拉丁字母、数字、连字符（-）与下划线；禁止空格、逗号、引号等分隔符类字符，避免与导入导出格式冲突。
- **规范化**：写入前对标签做 Unicode NFC 规范化与首尾 trim，防止形近但编码不同的字符串分裂为两个标签。
- **字典一致性**：标签必须命中全局标签字典或随本次写入同步创建；接口不隐式创建未声明的新标签（具体以写模式参数为准，默认严格模式）。
- **顺序无关**：语义上标签集合无序，系统在比对与去重时忽略顺序，但返回时按创建序或字典序列出以保证展示稳定。

### 4.4 示例

合法示例：

```
{"tags": ["报销"]}                          ← 单标签
{"tags": ["旅行", "东京", "交通"]}           ← 多标签，多维交叉
{"tags": ["trip-tokyo", "2025"]}            ← 连字符组合词
{"tags": []}                                ← 空数组，合法
```

非法示例：

```
{"tags": "报销"}              ← 字符串而非数组，非法
{"tags": ["报销", "报销"]}     ← 重复元素，非法
{"tags": [""]}                ← 空字符串元素，非法
{"tags": ["餐 饮"]}            ← 含空格，非法
{"tags": [null, "餐饮"]}       ← 混入 null，非法
{"tags": ["旅行","东京","美食","购物","住宿","交通","门票","小费","手信","药妆","/misc"]} ← 超过10个，非法
```

交叉筛选演示：查询"本月分类为餐饮且含『报销』标签的支出"时，引擎先按分类与金额过滤交易，再检查候选交易的 `tags` 数组是否包含"报销"，最后汇总 `amount`，输出可报销餐饮总额。

### 4.5 常见错误

1. **类型误用**：把单个标签直接传字符串而非单元素数组，校验拒绝。客户端应在序列化层统一包装为数组。
2. **分隔符混入**：用户输入"旅行，东京"被整串存为一个标签，交叉筛选失效。录入界面应提供独立标签输入控件而非自由文本框。
3. **重复与近似重复**：全角/半角、NFC/NFD 差异产生的"视觉相同但编码不同"的标签分裂统计口径。写入前必须规范化并按精确匹配去重。
4. **标签爆炸**：用户为每笔交易新建唯一标签（如把备注当标签写），字典膨胀。应引导用户区分"标签"与"备注"职责，并执行数量与数量级治理。
5. **以标签参与计算**：某报表按标签求和时遗漏了未打标签的交易，得出偏小结果。需明确"未打标签"与"空集合"语义一致，报表应显式包含。
6. **静默去重掩盖问题**：服务端静默丢弃重复元素而不报错，客户端误以为提交了 2 个标签。严格模式下应拒绝并返回明确错误码。
