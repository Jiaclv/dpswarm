# 迷你记账字段参考手册

## 文档说明

本手册是“迷你记账”应用核心数据字段的权威参考文档，面向开发、测试、运维及数据治理相关人员。手册覆盖 id、amount、currency、tags 共 4 个核心字段，每个字段依次包含定义、类型、约束、示例、常见错误五个小节。手册末尾附有完整性校验和，用于确认文档传输与存储过程中的完整性。请各团队在接口设计、数据库建模、数据校验实现时以本手册为唯一字段规范依据；若本手册与历史设计文档冲突，以本手册为准，并请相关负责人员及时向上游同步修订意见。

---

## 一、id 字段

### 1.1 定义

id 是记账记录的唯一标识字段，用于在系统全生命周期内唯一地区分每一条记账条目。它既是数据库中的主键，也是跨服务调用、日志追踪、数据同步、冲突消解时引用某条记账记录的标准句柄。id 在记录创建时由服务端一次性生成，此后在整个数据生命周期内保持不变，任何一方不得修改、复用或回收已发布的 id 值。删除记录后，其 id 应被视为“已消费”，即使记录被物理清除，也不应将该 id 重新分配给新记录，以避免下游缓存、离线副本、第三方导出文件中出现同一 id 指向不同业务实体的歧义。在分布式部署场景下，id 的生成应保证跨节点全局唯一，推荐采用雪花算法或带节点标识的 UUID 方案，禁止依赖“最大值加一”这类在并发与分库分表环境下必然碰撞的策略。

### 1.2 类型

- 数据库层：定长字符串 CHAR(32) 或 BIGINT，二选一并全库统一；推荐字符串型 UUID（32 个十六进制字符，不带连字符），便于跨系统交换。
- 传输层（JSON）：string。即使底层为 BIGINT，也必须序列化为字符串，防止 JavaScript 环境下超过 2^53 的整数精度丢失。
- 校验正则：`^[0-9a-f]{32}$`（UUID 方案）或 `^[1-9][0-9]{0,17}$`（自增长整型方案）。
- 可空性：不可为空（NOT NULL），不可有默认值由客户端随意填充。

### 1.3 约束

1. 全局唯一性：全表、全库、全集群范围内不得重复，数据库层面通过主键或唯一索引强制。
2. 不可变性：创建后禁止 UPDATE 该字段；ORM 层应将该字段标记为只读。
3. 格式合法性：必须完全匹配既定正则，不允许前后空格、大小写混用（UUID 统一小写）。
4. 长度限制：字符串形式定长 32 字符；整型形式不超过 19 位十进制数字。
5. 非语义性：id 不得编码业务含义（如日期、用户号），避免因业务规则变更导致历史 id 语义失效。
6. 客户端预生成：允许客户端在离线记账时预生成 UUID 并随记录上送，服务端必须校验唯一性，冲突时返回 409 而非静默覆盖。
7. 引用完整性：其他表、其他服务以 id 引用记账记录时，删除原记录应采用软删除或级联清理策略，不得留下悬空引用。

### 1.4 示例

合法示例（UUID 方案）：
- `"id": "3f8a1c2e9b0d4e5f6a7b8c9d0e1f2a3b"`
- `"id": "0a1b2c3d4e5f60718293a4b5c6d7e8f9"`

合法示例（自增长整型方案，传输层字符串化）：
- `"id": "1000000000000000001"`
- `"id": "42"`

非法示例及原因：
- `"id": "3F8A1C2E"` —— 长度不足且含大写，不符合 UUID 小写 32 位规范。
- `"id": 12345678901234567890123` —— 数值型且超长，传输层必须是字符串。
- `"id": ""` —— 空字符串，违反不可空约束。
- `"id": " abc "` —— 含首尾空格，格式校验不通过。

### 1.5 常见错误

1. 精度丢失：后端 BIGINT 直接以 JSON number 返回，前端 JavaScript 将末尾几位变为 0，导致“查不到这条记录”。修正方法：序列化为字符串。
2. 大小写不统一：某些链路返回大写 UUID，某些链路返回小写，字符串比较失败。修正方法：生成与传输环节统一小写，入库前 `toLowerCase()`。
3. 复用已删除记录的 id：批量导入工具用“自增从 1 开始”重建数据，与线上历史 id 冲突，引发数据错乱。修正方法：导入工具必须复用原 id 或重新生成全新 id 并同步更新引用。
4. 客户端伪造 id：客户端上送他人 id 覆盖他人记录。修正方法：服务端校验 id 归属权（记录 owner 与当前会话用户一致）。
5. 主键缺索引却按 id 高频查询：分表后未建立全局 id 路由，全表扫描。修正方法：按 id 哈希分片并建立路由表。
6. 日志中泄漏完整 id 却未做上下文关联：排查问题时无法把多条日志串起来。修正方法：统一 trace 日志格式，附带 id 字段名与值。

## 二、amount 字段

### 2.1 定义

amount 是记账记录的金额字段，表示该笔交易涉及的资金数量，是记账应用最核心的业务数值。amount 的正负语义必须在全系统内统一约定：本手册规定，支出记账 amount 记为正值，收入记账 amount 同样记为正值，收支方向由独立的类型字段（或 tags 中的方向标签）表达；如产品形态采用“收入为正、支出为负”的有符号方案，则必须在接口文档与本手册之间做显式映射说明，禁止各端各自理解。amount 永远表示以 currency 字段所指币种为单位的数量，二者必须成对出现、成对校验，不允许脱离币种单独解释金额。金额涉及资金安全，属于强一致、强校验字段，任何舍入、截断、单位换算都必须发生在明确规定的环节，禁止在各链路中隐式发生。

### 2.2 类型

- 数据库层：DECIMAL(18,4)，即最多 18 位有效数字、4 位小数。禁止使用 FLOAT 或 DOUBLE 存储金额，浮点二进制表示无法精确表达十进制小数，会产生累积误差。
- 传输层（JSON）：string 形式的十进制数（推荐），或整数形式的最小货币单位（如“分”）。两种方案二选一，全接口统一。
- 应用层：Java 使用 BigDecimal，Python 使用 decimal.Decimal，JavaScript 使用 bigint 化的分值或 decimal 库，禁止使用 number 直接运算。
- 精度规范：小数位最多 4 位；展示层可按币种习惯缩至 2 位，但存储层始终保留 4 位。

### 2.3 约束

1. 非空：每条记账记录必须携带 amount，缺省即校验失败。
2. 数值范围：0 < amount < 10^14（即最大一百万亿，含 4 位小数时数据库上限为 99999999999999.9999），超出返回参数校验错误。
3. 禁止负值与零值：本手册采用正值方案，amount ≤ 0 一律拒绝；退款、冲正通过独立的业务类型表达，而不是写入负数。
4. 禁止科学计数法与特殊浮点值：不允许 "1e5"、NaN、Infinity 等形式，传输层只接受纯十进制数字字符串（可含一个小数点）。
5. 小数位上限 4 位：多于 4 位小数的输入直接拒绝，不做静默四舍五入，由客户端在提交前完成用户确认后的舍入。
6. 与 currency 联动：amount 的整数部分上限对部分超大面额币种（如越南盾）需在展示层做换算提示，但存储层不做币种差异化限制，以保持模型简单。
7. 不可变性：记账记录一经确认，amount 不可原地修改，只能通过“冲正 + 新记录”流程变更，保证审计链完整。
8. 汇总口径：跨币种汇总前必须先按汇率折算到统一币种，禁止直接把不同 currency 的 amount 数值相加。

### 2.4 示例

合法示例：
- `"amount": "12.3400"` —— 精确到 4 位小数。
- `"amount": "0.0001"` —— 最小非零精度。
- `"amount": "99999999999999.9999"` —— 上边界值，合法。
- `"amount": "88"` —— 整数形式，隐含 ".0000"，合法。

非法示例及原因：
- `"amount": 12.34`（JSON number）—— 传输层必须是字符串，浮点直接传输有精度隐患。
- `"amount": "-50.00"` —— 负值，违反正值方案。
- `"amount": "1.005e2"` —— 科学计数法，非法。
- `"amount": "12.34567"` —— 5 位小数，超出精度上限。
- `"amount": "0"` / `"amount": "0.0000"` —— 零金额记账无业务意义，拒绝。

### 2.5 常见错误

1. 浮点求和误差：前端用 number 累加 0.1 + 0.2 得到 0.30000000000000004，月度汇总对不上账。修正方法：全链路 decimal 化，前端以“分”为整数运算后再格式化。
2. 静默截断：某些链路把 12.3456 截成 12.34、另一些链路四舍五入成 12.35，同一笔记录在不同报表出现两个值。修正方法：入库前统一校验拒绝超精度输入，展示层统一用同一舍入模式（建议 HALF_UP）。
3. 单位混乱：接口 A 传“元”、接口 B 传“分”，金额相差百倍。修正方法：接口文档明确单位，字段命名体现单位（amountYuan / amountFen）或在元数据中声明 scale。
4. 负数语义冲突：老版本把支出记为负数，新版本把支出记为正值，统计时正负抵消，账目清零。修正方法：升级时写数据迁移脚本统一符号约定，并在接口版本说明中标注 breaking change。
5. 千分位分隔符污染："1,234.56" 直接入库校验失败或被错误解析成 1.234。修正方法：传输层剥离格式化符号，仅在接受层面校验纯数字格式，展示层才添加千分位。
6. 跨币种直接求和：把 100 CNY 与 100 USD 相加得 200，严重错账。修正方法：所有汇总必须先经汇率服务折算。

## 三、currency 字段

### 3.1 定义

currency 是记账记录的币种字段，声明 amount 所使用的货币单位。本字段采用 ISO 4217 标准的三字母大写字母代码作为唯一取值形式，例如 CNY 表示人民币、USD 表示美元、EUR 表示欧元、JPY 表示日元。currency 决定了金额的小数位习惯（大多数币种 2 位，日元、韩元等 0 位，本系统存储层统一 4 位以兼容特殊币种）、展示层的符号与格式（如 ¥、$、€ 及其前后位置），以及跨币种汇总时的汇率折算路径。currency 与 amount 是强绑定字段，二者共同构成完整的金额语义；脱离 currency 的 amount 没有业务意义。多币种记账是该应用的核心能力之一，因此 currency 的取值合法性、与汇率服务的对齐、历史数据的币种稳定性都是数据治理重点。

### 3.2 类型

- 数据库层：CHAR(3)，存储 ISO 4217 三字母代码，配合 CHECK 约束或外键字典表校验。
- 传输层（JSON）：string，3 个大写英文字母。
- 校验正则：`^[A-Z]{3}$`，且取值必须存在于币种字典表。
- 字典表结构建议：code（主键）、英文名、中文名、符号、默认小数位、启用状态、生效日期、失效日期。
- 可空性：不可为空；未显式传币种时按用户资料中的默认币种在服务端补全，补全逻辑必须留痕。

### 3.3 约束

1. 取值域封闭：只接受 ISO 4217 代码，且必须命中币种字典表中“启用”状态的条目；已退市币种（如已兑换前的旧码）只能用于历史数据读取，不能用于新建记账。
2. 大小写规范：必须全大写；接受层遇到小写可直接拒绝，或统一转大写后校验（二选一，全系统一致）。
3. 不可变性：记账记录确认后 currency 不可修改；用户记错币种应通过冲正重记处理，避免历史汇率口径混乱。
4. 与汇率服务对齐：任何可用于跨币种折算的 currency 必须在汇率服务中存在对应汇率源；新增币种需先接入汇率，再开放记账。
5. 默认值策略：用户未选币种时取其资料默认币种；新用户默认币种取注册地区映射，映射表需可配置。
6. 特殊代码排除：金衡盎司 XAU、测试代码 XTS、无币种 XDR 之外的特殊用途代码默认不在记账可用范围；XTS 仅可用于测试环境。
7. 展示格式绑定：展示层按币种字典的 symbol 与小数位渲染，禁止硬编码 "¥" 到所有记录。

### 3.4 示例

合法示例：
- `"currency": "CNY"` —— 人民币。
- `"currency": "USD"` —— 美元。
- `"currency": "JPY"` —— 日元（零小数位币种）。
- `"currency": "EUR"` —— 欧元。

非法示例及原因：
- `"currency": "cny"` —— 小写，违反大写规范（若选择“直接拒绝”策略）。
- `"currency": "人民币"` —— 中文名称，必须是 ISO 代码。
- `"currency": "RMB"` —— 民间惯用缩写，非 ISO 4217 代码，人民币正确代码为 CNY。
- `"currency": "US"` —— 两位，长度不符。
- `"currency": ""` 或缺省且无默认币种可补全 —— 校验失败。

### 3.5 常见错误

1. RMB 与 CNY 混用：部分历史数据以 "RMB" 入库，导致按 CNY 汇总时遗漏这批记录。修正方法：数据清洗统一为 CNY，接口层拒绝 RMB。
2. 大小写不一致导致分组失败：报表按币种 GROUP BY 时 cny、Cny、CNY 分成三组。修正方法：入库前统一规范化为大写。
3. 小数位误显示：给 JPY 记录显示 ".00"，给 CNY 记录显示 0 位小数。修正方法：严格按字典表“默认小数位”渲染。
4. 退市币种仍可新建记账：某币种退出汇率服务后用户仍能选择，导致金额无汇率可折算，跨币种报表报错。修正方法：字典表启用状态与汇率服务可用性联动，定时任务校验。
5. 修改历史记录币种“纠错”：用户把本应 USD 的记录直接改成 CNY，历史汇率快照失真。修正方法：禁止改币种，走冲正流程。
6. 测试代码泄漏到生产：联调时用 XTS 造数未清理，生产报表出现未知币种。修正方法：XTS 仅允许在测试环境字典中启用，生产字典不含 XTS。

## 四、tags 字段

### 4.1 定义

tags 是记账记录的分类标签字段，以字符串数组形式存储用户为一笔账目附加的一个或多个分类标记，例如 `["餐饮","午餐"]`、`["交通","地铁","通勤"]`。tags 支撑账单的分类统计、筛选检索、预算关联与个性化报表，是连接原始记账数据与用户分析视角之间的桥梁。与单一“分类（category）”字段不同，tags 采用多值模型，允许一笔记录同时归属多个维度（如一笔“和同事聚餐”的开销可同时打上“餐饮”与“社交”）。tags 分为预置标签（系统内置、用户只读，如“餐饮”“交通”“居住”）与自定义标签（用户自建），二者在同一数组内混存时以标签对象或命名前缀区分。标签语义由标签本身承载，标签的增删不影响已有记账记录的金额与时间等事实数据。

### 4.2 类型

- 数据库层（推荐范式化设计）：记录—标签关联表（record_id, tag_id）多对多，加标签字典表（tag_id, name, type, owner, status）。
- 数据库层（简单实现）：JSON 数组列或以分隔符拼接的字符串列（如 `餐饮,午餐`），仅限标签查询需求简单的场景。
- 传输层（JSON）：array of string，例如 `"tags": ["餐饮", "午餐"]`；扩展形态为 array of object（含 name 与 type）。
- 元素约束：每个元素为 1–20 个字符的非空字符串，可含中文、字母、数字、连字符、下划线。
- 可空性：允许为空数组 `[]`（表示未分类），但不允许为 null（统一用空数组表达“无标签”，降低各端判空分支差异）。

### 4.3 约束

1. 数量上限：单条记录最多 10 个标签，超出拒绝或由客户端截断提示。
2. 元素唯一性：同一记录的 tags 数组内不得出现重复标签（比较前先做 trim 与规范化）。
3. 字符与长度：单个标签 1–20 字符；禁止仅含空白字符；禁止含逗号（简单拼接存储方案下逗号是分隔符，入库元素含逗号会破坏解析）。
4. 规范化规则：存储前 trim 首尾空格；系统提供可选的大小写折叠配置（拉丁字母场景），中文标签不受影响。
5. 预置标签保护：预置标签的 name 与标识不可被用户修改或删除；用户自定义标签可与预置标签同名时必须通过 type 字段区分，禁止静默合并。
6. 删除语义：删除自定义标签仅解除其与记录的关联（或将其标记为“已归档”），不得物理删除导致历史记录标签凭空消失且无法解释。
7. 查询一致性：筛选接口对 tags 的匹配语义必须明确（AND / OR），默认 OR 并在接口文档中显式声明参数。
8. 总量限制：单用户自定义标签总数建议上限 200 个，超出提示整理，防止标签体系碎片化。

### 4.4 示例

合法示例：
- `"tags": []` —— 无标签，合法。
- `"tags": ["餐饮"]` —— 单个预置标签。
- `"tags": ["餐饮", "社交"]` —— 多维度标签。
- `"tags": ["交通", "地铁-通勤"]` —— 含连字符的自定义标签。
- `"tags": ["旅行2024"]` —— 字母数字混合。

非法示例及原因：
- `"tags": null` —— 应使用空数组而非 null。
- `"tags": ["餐饮", "餐饮"]` —— 数组内重复。
- `"tags": [""]` —— 空字符串元素。
- `"tags": "餐饮,午餐"` —— 字符串而非数组，类型错误。
- `"tags": ["餐饮,午餐"]` —— 元素含逗号，拼接存储方案下解析歧义。
- `"tags": ["a", "b", …（共 12 个）]` —— 超过 10 个上限。

### 4.5 常见错误

1. null 与空数组混用：部分接口返回 null、部分返回 []，前端判空逻辑频繁出错。修正方法：统一空值表达为 []，序列化层禁止输出 null。
2. 重复标签：客户端快速连点添加两个“午餐”，统计中该分类金额被双倍计入。修正方法：添加前查重 + 服务端唯一性校验。
3. 逗号拆分事故：用户自定义标签“餐,饮”入库后按逗号解析成“餐”和“饮”两个标签。修正方法：元素禁止逗号，或改用 JSON 列/关联表存储。
4. 删除标签导致历史账目“裸奔”：直接物理删除标签行，历史记录的标签关联成孤儿数据，报表前后不一致。修正方法：软删除/归档，报表按“归档时快照”渲染。
5. 预置标签被改名：用户把内置“餐饮”改成“吃货”，统计口径与预算规则（绑定“餐饮”）脱钩。修正方法：预置标签只读，用户想改名引导其创建自定义标签。
6. 大小写与空格产生近似重复标签：“coffee”、“Coffee”、" coffee" 三个标签并存，筛选漏数据。修正方法：入库前统一 trim，提供标签合并工具。
7. AND/OR 语义未声明：用户以为多选筛选是“同时满足”，实现是“任一满足”，客诉筛选不准。修正方法：接口显式 matchMode 参数并默认注明。

## 五、字段协作与整体校验

四个字段并非孤立：id 唯一锚定记录，amount 与 currency 共同构成金额语义，tags 提供分析维度。创建接口的复合校验顺序建议为：先 id 格式与唯一性，再 amount 格式与范围，随后 currency 字典校验，最后 tags 结构与规范化；任一环节失败即整体拒绝，保证入库记录要么完全合法要么不存在，避免半成品数据。批量导入场景按行级校验、逐行反馈错误明细，不得因单行失败回滚整批或静默跳过。
